# 第 3 章 L1 静态令牌：哪些该跟主题，哪些永远不跟

> 本章成稿目标字数：1800–2400 ｜ 预计阅读 9 分钟 ｜ 前置：第 1、2 章

## 本章要解决的问题

**92 处硬编码，哪些必须改、哪些必须留着？**

这一章把第 2 章的分级结论变成可执行规则，并给出一个反直觉但正确的判断：**在换肤系统里，「不跟主题」的地方和「跟主题」的地方一样重要**。

## 读者收获

1. 三条判定规则（A/B/C 三类），能对任意一处颜色引用当场定级；
2. 理解「默认主题包回退 `$r`」这个设计为什么保住了深浅色；
3. 知道为什么令牌对照页保留 `$r` 不是妥协而是正解。

---

## 正文要点

### 3.1 令牌层能做什么、不能做什么

`$r('app.color.qj_brand')` 这类资源引用的能力边界非常清晰：

| 能 | 不能 |
|---|---|
| 随 `resources/dark/` 限定词自动切换深浅色 | 随「用户在设置页改的颜色」变化 |
| 编译期校验（名字写错立刻报错） | 运行期改指向的值（无公开 API） |
| 零运行时开销、可被系统主题材质对齐 | 表达「一套主题包」的多色关系 |

所以 L1 的正确定位是：**承载「不随换肤变、但要随深浅色变」的那部分颜色**，以及**必须精确控制、不接受任何覆盖**的那部分（语义色、演示对照）。

### 3.2 规则一：品牌主体 → 改读运行时

判定：**这个颜色的语义是「品牌强调」，且换肤后应当跟着变**。

典型：首页大卡的图标 chip 底、场景页强调块、选中态底、加载动画的主色。

改法不是「删掉 `$r` 换 hex」，而是**改读取源**：页面装饰色改读 `theme.brandColor()` / `theme.brandSoftColor()`（第 5 章）。这样它同时获得了两件事：随主题变、且默认主题包时仍回退令牌（深浅色照常工作）。

### 3.3 规则二：演示/对照 → 保持 `$r` 写死

判定：**这个颜色展示的对象就是令牌本身**。

典型：`DesignTokensView`（令牌总览）、`ComponentGalleryView` 里的「令牌对照」区块。

这条规则容易被当成「没改干净」。反过来想：令牌总览页的功能是「让我看到 `qj_brand` 到底长什么样」。如果它跟着主题变，那它就变成了「当前主题色的自拍」——**功能被破坏**。

同理，第 10 章的 ArkTS 卡片保留 `$r` 也属于这一类：卡片框架只支持 V1（`@Entry` / `@Component` / `@LocalStorageProp`），接不上 V2 的 `@Local` 单例。在「卡片必须显示、主题色拿不到」的约束下，保留令牌是唯一正确解——它至少保证深浅色正确。

### 3.4 规则三：语义色 → 永远不跟主题

判定：**这个颜色表达的是「状态」，不是「品牌」**。

典型：危险（删除/错误）、成功、警告、中性灰。

语义色跟主题走会产生真实事故：切换到「高对比」主题包（`#0A0A0A`）时，若危险红被主题色覆盖，用户就**看不出这是危险操作**。

本仓的实现纪律是：语义色一律 `$r`，且不进入任何注入面。`A8-components-teal2.png` 里可以验证——「危险」按钮仍是红、「成功」标签仍是绿，只有品牌类（主操作/次操作/加载中/品牌标签）转成青碧。

### 3.5 一个关键设计：默认主题包回退 `$r`

`UiThemeManager.brandColor()` 里有一段看起来「多此一举」的判断：

```
若 无强调色 且 presetId === 默认主题包 → 返回 $r('app.color.qj_brand')
否则 → 返回具体 hex
```

为什么不让它永远返回 hex？因为**默认主题包必须保住深浅色**。默认主题包（品牌蓝 `#0A59F7`）在暗色模式下需要一个提亮版本，而提亮逻辑由 `resources/dark/element/color.json` 的限定词承担。如果这里返回写死的 `#0A59F7`，暗色下就会得到「暗底 + 偏暗蓝」，观感发闷。

代码注释把这条动机写得很清楚：「非默认主题包必须给具体色，否则换包对这类组件完全无效」。两句话合起来就是完整的取舍：

> **默认包走令牌（要深浅色）；非默认包走 hex（要换肤生效）。**

### 3.6 由此带来的已知偏差（要敢于承认）

这条取舍有一个必然的副作用：**非默认主题包在暗色模式下，自绘品牌色不会自动提亮**——因为它返回的是同一个 hex，没有走 `dark` 限定词。

系统组件层不受影响（L4 的 `darkColors` 会提亮，第 6 章），但自绘层会与系统层出现轻微明度差。这是**已知偏差**，不是 bug；处理方式有两种：

1. 接受它（自绘品牌色用在中低面积，明度差可容忍）；
2. 在 L3 里补一层「按当前色彩模式选择 hex」的逻辑（会引入对 `ColorModeManager` 的依赖，破坏 VitalUI 的零 `@kit` 纪律）。

本仓选择方案 1，并在第 13 章的验收清单里把它列为「可接受偏差」。

### 3.7 主题包数据结构：为什么只声明一个色

`AppThemePreset` 只有三个字段：`id` / `label` / `baseHex`。

**一套主题包 = 一个品牌色**，其余层（强调底 / 描边 / 选中态）由 `AppThemeController` 按比例派生（第 6 章）。这个设计换来两个好处：

- 新增一套主题 = 加一行数据（`#RRGGBB`），不需要手写几十个 token；
- 派生规则唯一，不会出现「A 主题的强调底偏亮、B 主题的偏暗」这种不一致。

代价是：**无法精细控制某套主题的特殊对比度**。高对比主题（`#0A0A0A`）就是典型——它靠「近黑品牌色」+ L4 的 `darkColors` 兜底，而不是靠一套手调 token。

`B1-presets-5.png` 展示了完整 5 套：品牌蓝 / 靛紫 / 青碧 / 桃粉 / 高对比。注意每个 chip 里的 16vp 圆点用的就是 `preset.baseHex`——**这是唯一允许直接把 `baseHex` 当背景色的地方**（它就是色卡本身）。

## 需复核 / 已知限制

- §3.6 的「非默认主题包在暗色下不自动提亮」由 `brandColor()` 实现直接推出，并已在真机暗色下目视确认；但**未做像素级取色 A/B**，正式发布前建议补一张暗色对比截图。
- `brandSoftColor()` 在非默认主题包时返回 `effectiveAccent()`（**满强度色**，而非柔和层）——这与方法名语义不符。`B1-presets-5.png` 中「品牌标签」底偏深，与此一致。**需复核**：这是有意为之（简化）还是遗留缺陷，发布前须裁定并在正文口径统一。

## 版本注记

- v3.44 起，页面装饰色从 `$r` 迁移到 `theme.brandColor()`；本仓称之为「L1 并入 L3」，但 B/C 两类保留 L1，故 L1 层未消失。
