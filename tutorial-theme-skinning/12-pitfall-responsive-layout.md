# 第 12 章 坑 8–9：响应式不能按窗口断点算栏宽/列数，页签不能按断点切位置

> 本章成稿目标字数：2400–3000 ｜ 预计阅读 12 分钟 ｜ 前置：第 7 章

## 本章要解决的问题

这两个坑看起来是「布局问题」，与换肤无关——但它们在真机走查里**和主题问题混在一起**，让「主题没生效」的错觉成倍放大。

- **坑 8**：宽屏（`bp=lg`）分栏后，左栏实际只有约 420vp；按窗口断点算「lg = 4 列」会把卡片压到 ~100vp，标题截成「设…」。
- **坑 9**：宽屏时把 `HdsTabs.barPosition` 切成 `Start`，页签会飞到左栏**顶部**，夹在标题与列表之间。

## 读者收获

1. 分清「窗口断点」（设备形态）与「容器宽」（我实际能画多宽）；
2. 掌握「宿主下传容器宽 + 子视图按容器宽分档」的模式；
3. 知道 `barPosition` 在分栏下为什么必须恒定。

## 坑 8：窗口宽 ≠ 你有的宽度

### 根因：分栏把可用宽度切走了

入口页在宽屏下进入 `NavigationMode.Split`：

```
.mode(this.breakpoint.isWide() ? NavigationMode.Split : NavigationMode.Stack)
```

一旦分栏，**左栏（navBar）只占窗口宽度的一部分**——而 `Navigation` 的默认左栏宽度在阔折叠这类设备上只有约 **320vp**。于是：

- 断点仍然是 `lg`（窗口足够宽）；
- 但页面实际容器只有 ~320–420vp。

如果子视图用「断点 → 列数」映射（`lg` → 4 列），列数按「大屏」给，容器按「小屏」算 → **每列被压扁**。

### 正解一：把左栏宽度显式定下来

入口页不再依赖默认值，而是按「窗口宽的 32%，clamp 到 340–420vp」：

| 断点 | 左栏宽度 |
|---|---|
| `lg` / `xl` | `clamp(340, 窗口宽 × 0.32, 420)` |
| `md` | `44%`（比例，随窗口缩） |
| `sm` 及以下 | 不分栏（`Stack`） |

同时用 `navBarWidthRange({ minWidth: 300, maxWidth: 440 })` 兜住边界，避免极端窗口下越界。

为什么是 32% + clamp？因为**比例保证随窗口缩放，clamp 保证两端不发散**：窗口很宽时左栏不至于跟着无限变宽（420 封顶），窗口中等时也不至于被压到不可读（340 兜底）。

### 正解二：把「容器宽」下传给子视图

关键设计：入口把**数值宽度**（`navPaneWidthVp()`，未分栏时返回 0）作为 `@Param paneWidthVp` 传给子视图。子视图按它分档：

| 容器宽 | 列数 |
|---|---|
| < 480 | 2 |
| < 760 | 3 |
| ≥ 760 | 4 |
| 宽为 0（拿不到） | 退回断点判断（sm=2 / md=3 / 其他=4） |

这套规则的要害是第一条：**420vp 的容器落到「< 480 → 2 列」**，于是修复了挤扁问题——`E4-pura-tools-fixed.png` 就是 2 列的结果。

### 正解三（配套）：网格高度要自己算

`Grid` 被放进 `Scroll` 时不会自动撑高，会塌成 0 高度。本仓的处理是按「行数 × 行高 + 行间距」显式计算：

```
rows = ceil(条目数 / 列数)
height = rows × 卡片高 + (rows − 1) × 间距
```

注意这段计算**依赖列数**——列数一改，高度必须跟着改。这也是为什么「列数按容器宽算」必须和「高度显式计算」放在同一个视图里：两者是同一个决策的两个输出。

### 一条可复用的判断规则

> **断点回答「设备是什么形态」（要不要分栏）；容器宽回答「我这一块有多少地方画」（列数、间距、字号档）。**

把这两件事混用，就会出现「大屏上被压扁、小屏上留白过多」的典型错位。

## 坑 9：`HdsTabs.barPosition` 不能按断点切

### 现象

宽屏（分栏）下，底部页签「跑了」：`示例 / 学习 / 开发工具` 出现在**左栏顶部**，横在页面标题与内容卡片之间，看起来像一组次级导航。

`E2-pura-navwide.png` 就是这个现场（该图还是「网格已按容器宽修好、页签位置未修」的中间态）。

### 根因：误把「宽屏」理解成「页签该在上方」

原写法是：

```
.barPosition(this.breakpoint.isWide() ? BarPosition.Start : BarPosition.End)
```

意图是「宽屏时页签放到上面，更符合平板习惯」。但在**分栏**语境下，`HdsTabs` 的容器已经不是整屏，而是**左栏**。此时 `Start` 把页签放到左栏顶部——正好插在标题与列表之间，既不像顶部导航，也不再是底部页签。

### 正解：恒为 `BarPosition.End`

```
.barPosition(BarPosition.End)      // 恒定，不随断点变化
```

结果：分栏时页签落在**左栏底部**（浮动胶囊形态），与 2in1 端一致。`G0-pura-tabbar-bottom.png` 与 `G2-toggle-on-teal.png` 都能看到这个形态。

### 为什么不是「宽屏时改成左侧竖排」

那是另一种设计（rail 导航），需要配套：图标+文字重排、宽度预算、选中指示器方向、内容区让位。**改 `barPosition` 一个属性得不到 rail**，只会得到「位置错了的底部页签」。要做 rail 就得单独设计组件。

### 一个附带的观感细节

页签用了 `barOverlap(true)`（内容延伸到页签之下）+ 悬浮样式。因此底部页签会**覆盖在列表之上**——这是沉浸光感的既有设计，不是遮挡 bug：滚动到末尾时最后一行仍能完整看到（因为列表有底部 padding 预留）。改这块前先确认这个前提，否则容易把「设计意图」当成「布局缺陷」去修。

## 两个坑的共同教训

1. **真机走查要按「形态」分组**：手机竖屏 / 阔折叠展开（分栏）/ 2in1 宽屏 / 平板，每组的容器宽差异巨大，同一套断点逻辑在其中几组上必然出错。
2. **主题问题与布局问题必须分开取证**：先修布局（列数/页签位置），再看颜色。否则「文字被截断」会被误读为「主题把字变没了」。
3. **`E*` 与 `G*` 系列截图不可混用**：`E4` 修的是列数（此时页签仍在顶部），`G0/G2` 才是页签修复后的状态。写文档时标清「哪张图对应哪次修复」，否则会得出「改了 A 同时修好了 B」的错误因果。

## 需复核 / 已知限制

- 「`Navigation` 默认左栏约 320vp」这一数值来自真机观察与走查记录，**未做像素级标定** → **需复核**（不同设备/版本可能不同）。
- 32% / 340–420 / 44% 这组参数是**经验调优值**，未做系统性的多设备矩阵验证（当前覆盖：阔折叠、2in1、手机） → **需复核**。
- `barOverlap(true)` 下「列表末端完整可见」依赖底部 padding 预留；若某页漏加 padding，会出现「最后一行被页签压住」 → **需逐页复核**。
- `ToolsView` 之外的其它网格页是否都已按容器宽分档 → **需复核**（本章只覆盖已验证的三项工具网格）。
