# 第 8 章 坑 1–2：切主题包「没反应」与「只改单例按钮仍蓝」

> 本章成稿目标字数：2400–3200 ｜ 预计阅读 12 分钟 ｜ 前置：第 5 章

## 本章要解决的问题

两个症状，一个共同点——**代码跑了，但优先级盖住了效果**。

- **坑 1**：点「青碧」，外观页的选中态变了，但界面颜色几乎没动。
- **坑 2**：把主题色注入到单例后，大部分按钮变了，**VitalUI 的原语按钮仍然是蓝的**。

两个坑都不是「没接上」，而是「接上了，但被别人覆盖」。

---

## 坑 1：切主题包没反应

### 现象

外观页点青碧 → 主题包 chip 的选中描边确实转成青碧 → 但**预览区、首页、组件页的主要颜色几乎没变**，观感像「只换了个选中框」。

`A1-appearance.png` 是这个问题最容易复现的状态：主题包选中的是「品牌紫」，而下方取色块显示 `#6c4de8`——**界面显示的颜色由强调色决定，主题包只是个背景设定**。

### 根因：强调色优先级更高，而它没被清掉

系统的取值优先级是固定的：

```
强调色（非空） > 主题包 baseHex
```

所以「切主题包」这个动作，如果不动强调色，就等于「改了一个优先级更低的变量」——**结果当然没变化**。

更糟的是当时的 `setAccentColor` 实现是**严格校验**式的：

```
若 输入是合法 '#RRGGBB' → 赋值
否则                    → 忽略（保持原值）
```

空串落进了「否则」分支。于是「想清空强调色」这件事**在 API 层就做不到**——不是页面忘了清，而是没有能力清。

### 正解：把空串定义为一个语义

改动很小，但语义变化很大：

```
空串 → accentColor = ''      // 显式清除覆盖，回退到主题包基准色
合法 hex → 赋值
非法输入 → 忽略
```

三态而非两态。这条改动让「清除」成为一个**可表达的操作**，而不是「什么都不做」。

### 正解（续）：页面侧也要配合——切包时清强调色 + 清持久化

只改 API 还不够，业务侧要显式表达「切包 = 重置微调」：

```
切包动作 = setAccentColor('') → setPresetId(id) → applyPreset(id)
           + 写入 theme_preset
           + 把 accent_color 写成 ''      ← 容易漏
```

最后一步最容易漏，漏了会得到一个**只在重启后复现**的 bug：当前会话看着对，杀进程重进——`restoreTheme()` 读到旧强调色，又把主题包裹住了。

源码注释把这条动机写得很直白：

> 切包时**清掉强调色覆盖**：强调色是「在主题包之上的单点微调」，若保留上一套的强调色，用户切包后会看到颜色几乎没变（强调色优先级更高），这是实测踩到的真实困惑点。

### 为什么这个坑值得写进教程

因为它是一个**语义层缺陷伪装成 UI 缺陷**的典型：现象在界面上，根因在「空串该不该算合法输入」。排查时你会一直盯着页面代码，而真正要改的是单例的一个 `if` 分支。

排查口诀：**「某个设置项改了没效果」时，先问「有没有更高优先级的设置项还非空」**。

## 坑 2：只改单例，VitalUI 原语按钮仍然蓝

### 现象

按第 5 章把 `UiThemeManager` 建好，`AppComponent` 的控件工厂（`AppToggle` / `AppCheckbox` / `AppSlider`…）全部跟着变了——但 `CommonButton` 渲染出来的「主操作」按钮、`CommonTag` 的「品牌标签」**依然是默认品牌蓝**。

`A8-components-teal2.png` 是修复后的状态：主操作/次操作/加载中/品牌标签全部转青碧。

### 根因：原语库是「零 @kit 的纯组件」，没有观测上下文

`VitalUI` 的设计纪律是零 `@kit`、只做表现原语。改造前它的按钮取色直接是 `$r('app.color.qj_brand')`——**它压根不认识 `UiThemeManager`**。

而当时的注入面统计（第 2 章）恰好会误导人：它列出「VitalUI 原语 5 个」在注入面上，但那指的是**通过 `@Param accentColor` 由页面传色**这条路径。**页面不传，原语就不变色**——而绝大多数页面都没传。

于是得到一个很典型的错觉：**「我已经把注入面覆盖了」，但注入面依赖调用方主动喂色**。

### 正解：原语自己持有单例，同时保留外部覆盖口子

两件事同时做：

```
① @Local theme = UiThemeManager.getInstance()        // 自己建立观察
② @Param accentColor: string = ''                     // 保留页面覆盖能力
③ 取色 = accentColor 非空 ? accentColor : this.theme.brandColor()
```

为什么不是「只靠 `@Param`」？因为让所有页面都记得传 `accentColor` 是不可能的（漏传无编译错误、无运行时告警）。
为什么不是「只靠单例」？因为原语需要「这一处我想特调成别的色」的能力（例如危险场景用红色按钮但形状相同）。

**两者都要，且回退目标必须是 `brandColor()` 而不是 `$r`**——否则会掉进第 5 章 §5.4 那个陷阱（漏掉主题包层）。

### 与坑 3 的区别（重要，别混）

| | 坑 2 | 坑 3（第 9 章） |
|---|---|---|
| 写法 | 原语**没读**单例，只读 `$r` | 原语读了单例，但读在 **`@Param` 默认值**里 |
| 结果 | 永远不响应 | 改色时**不重渲染**（首次求值后固定） |
| 修法 | 加 `@Local theme` | 把读取从「默认值」搬到「`build`/取色方法」 |

坑 2 是「没连上」，坑 3 是「连上了但不观察」。两者的现象几乎一样，修法完全不同——这是本教程把 `@Param` 陷阱单独成章的原因。

### 为什么这个坑值得写进教程

因为它揭示了「注入面」这个指标的一个盲区：**注入面统计的是「谁读了单例」，不是「谁最终显示品牌色」**。

一个更可靠的度量是：**改动一次主题色，逐屏截图对比，看哪些像素变了**。这条方法在第 13 章的验收清单里被固化成「逐页 A/B 截图」。

## 修正后的调用链（两张图看懂）

**改造前**：

```
页面 ──?──> CommonButton ──> $r('app.color.qj_brand')      // 永远蓝
页面 ────> AppToggle      ──> UiThemeManager               // 跟随
```

**改造后**：

```
页面 ──(可选 accentColor)──> CommonButton
                                ├─ accentColor 非空 → 用它
                                └─ 否则 → @Local theme.brandColor()
                                             ├─ 有强调色 → hex
                                             ├─ 默认包   → $r（深浅色）
                                             └─ 非默认包 → baseHex（换肤生效）
```
