鸿蒙工程目录设计指南

基线：API 23（compatibleSdkVersion 6.1.0(23)，targetSdkVersion 26.0.0）· 状态管理 V2 · UI 组件 HDS（UIDesignKit）
配套范例工程：hm_blueprint/（模板骨架）与 hm_partynow/（实装后工程），两者结构完全一致且均已编译通过。

0. 适用范围

本指南描述一套经过实机验证的 HarmonyOS 应用工程组织方式，适用于需要同时覆盖 手机 / 平板 / 2in1 / TV / 手表 的多端应用，也适用于单设备应用（可裁剪掉多余入口模块）。

三条硬约束（本指南的所有结论都建立在其上）：

约束内容依据
C1同一应用、同一设备类型只允许一个 entry 类型 HAP官方 FAQ faqs-package-structure-28
C2断点阈值由平台定义，业务代码禁止硬编码像素值最佳实践 bpta-multi-device-responsive-layout
C3HDS 组件有明确的设备支持矩阵，不支持时回退原生组件并登记例外SDK api-version/UIDesignKit.json 实测

1. 顶层设计原则

编号原则说明
P1目录名 = 模块名 = 包名三者同名可消除"看到 import 不知道对应哪个目录"的认知成本
P2严格单向依赖entry → features → commons，禁止反向与跨 feature 直连
P3能力下沉、差异上浮通用能力沉到 commons；设备/断点差异留在入口层与页面层
P4一个入口一个 module设备形态差异用 module 隔离，不用 if (deviceType) 在页面里分叉
P5状态管理统一 V2新代码只用 V2 装饰器，禁止新增 V1 用法
P6样式令牌集中在 AppScope颜色等设计令牌放应用级资源，模块内不重复定义
P7可编译是底线任何结构方案都必须能通过 devecocli build 并产出签名 HAP

3. 分层职责

层目录职责明确不做的事
应用级AppScope/bundleName、版本、应用图标、设计令牌不放任何 ArkTS 代码
入口层entry entry_tv entry_wearable生命周期、窗口、系统能力初始化、路由分流、形态专属布局不写业务规则；不直接被其他模块依赖
业务特性层features/<业务域>一个业务域一个模块：页面视图、ViewModel、Repository不直接依赖其他 feature；不碰系统能力（走 commons）
基础设施层commons/foundation日志、异常、错误码、Result、断言、脱敏不依赖 ArkUI，不含业务语义
运行环境层commons/runtime断点、颜色模式、能力检测、设备信息、兼容不含业务语义与 UI
公共组件层commons/uikit通用组件、动效规范、组件 API 约定不依赖任何 feature
配置层根目录 json5 / hvigor构建、签名、产品、检查规则—

归属判据（放进哪一层？）

  1. 这段代码只有某个设备形态才需要 → 入口层。
  2. 这段代码只有某个业务域才需要 → 该 feature。
  3. 这段代码多个业务域都要用 → commons。
  4. 这段代码和业务无关、是系统能力的封装 → commons/runtime。
  5. 这段代码连系统能力都不涉及（日志、异常、纯计算）→ commons/foundation。
  6. 拿不准 → 先放 feature，出现第二个使用方时再上移（禁止提前抽象）。

5.3 禁止项清单（硬性）

编号禁止原因正确做法
F1feature 反向依赖 entry入口是叶子，反向依赖会形成环需要入口状态时，用 commons/runtime 的单例或具名路由
F2feature 之间直接互相 import业务域耦合，拆包即断共享逻辑上移到 commons；跨域跳转走具名路由
F3commons 依赖任何上层；或 foundation 反向依赖 runtime破坏单向依赖依赖方向只能是 entry → features → runtime → foundation
F4在 commons/foundation 或 commons/runtime 写业务逻辑基础层被业务污染后无法复用业务语义放 feature
F5循环依赖编译期报错、运行期未定义抽公共部分下沉
F6深链其他模块内部路径 xxx/src/main/ets/...破坏封装，重构即断只从对方 Index.ets 导入
F7在页面里硬编码颜色值深浅色失效用 $r('app.color.bp_*') 令牌
F8在业务代码硬编码断点像素阈值设备阈值可能被产品化调整用 UIContext.getWindowWidthBreakpoint()
F9用 deviceInfo.deviceType 做布局分支同一设备多窗口形态会判断错布局只依据断点；设备类型只用于能力检测
F10新增 V1 状态装饰器与 V2 混用会产生双重代理陷阱统一 V2
F11在 @Entry 组件里放业务规则入口只做装配逻辑放 ViewModel
F12Tab 用原生 Tabs、导航用原生 Navigation（除已登记例外）与设计系统不一致HdsTabs / HdsNavigation

6. 多设备入口组织

6.1 入口划分（依据 C1：同设备类型只允许一个 entry HAP）

入口 moduledeviceTypes覆盖形态首页
entryphone / tablet / 2in1手机、平板、2in1（统一入口）pages/Index.ets
entry_tvtv智慧屏pages/TvIndex.ets
entry_wearablewearable智能穿戴pages/WearableIndex.ets

三者的 deviceTypes 互不重叠，因此不违反 C1，可以共存于同一应用。

6.3 入口分流链路

设备安装应用
  → 系统读取各 HAP 的 module.json5.deviceTypes
  → 与当前设备类型匹配的唯一 entry HAP 被安装
  → 该 HAP 的 mainElement Ability 启动
  → 加载各自 pages/profile/main_pages.json 的首个页面
  → 页面内再按断点切换布局

关键点：分流发生在安装期（deviceTypes 匹配），不是运行期 if。 运行时只需要处理断点，不需要处理"我是什么设备"。

6.4 各形态 UI 组织差异

形态导航内容组织交互
phone / tablet / 2in1HdsTabs（sm/md 底部；lg/xl 侧边）+ HdsNavigation 分栏列表（md 2 列、lg+ 3 列）触摸
TV原生 Tabs（HDS 例外）横向内容带（content rail）遥控器方向键 + 焦点
手表无 Tab，单页单列、首屏出结论旋钮 / 手势

7. 断点系统

7.1 断点定义（官方阈值，按应用窗口宽度）

断点窗口宽度（vp）典型形态栅格列数
xs< 320智能穿戴4
sm[320, 600)手机竖屏、小折叠4
md[600, 840)平板竖屏、手机横屏、折叠展开8
lg[840, 1440)平板横屏、智慧屏12
xl≥ 14402in1 全屏、折叠电脑12

纪律（C2）：取值一律来自 UIContext.getWindowWidthBreakpoint() / getWindowHeightBreakpoint()，不自己写 if (width < 600)。

7.2 实现（commons/runtime）

  • constant/BreakpointConstants.ets：把平台枚举映射为语义名 + 栅格列数 + isWide()。
  • service/BreakpointManager.ets：@ObservedV2 单例，监听 windowSizeChange，把断点写入 @Trace 字段。
  • 初始化位置：EntryAbility.onWindowStageCreate 的 loadContent 回调内（此时断点查询才有效）。
// 订阅侧（V2 组件）—— 声明 @Local 后直接读 @Trace 字段即自动刷新
@Local breakpoint: BreakpointManager = BreakpointManager.getInstance();
// build 中：
Text(`breakpoint = ${this.breakpoint.breakpoint}`)
List().lanes(this.viewModel.columns(this.breakpoint.breakpoint))

7.3 断点驱动布局示例

entry/src/main/ets/pages/Index.ets 中：

.mode(this.breakpoint.isWide() ? NavigationMode.Split : NavigationMode.Stack)
.barPosition(this.breakpoint.isWide() ? BarPosition.Start : BarPosition.End)

7.4 监听手段选择

手段用途本项目定位
window.on('windowSizeChange') + UIContext.getWindowWidthBreakpoint()断点主链路主链路
display.on('change')旋转 / 分辨率（时序早于 window）旋转专用
display.on('foldStatusChange')折叠态变化折叠专用
@Env(SystemProperties.BREAK_POINT)（API 22+）组件内声明式读断点可选补充，不作为唯一断点源

15. 异常处理 · 代码健壮性 · 日志规范

15.0 一句话总纲

基础层提供能力，业务层只表达意图，边界统一兜底。

具体说：日志与异常的全部原语（Logger / AppError / Result / 断言 / 脱敏）由 commons/foundation 提供；业务代码只负责"用 Result 表达可预期失败、用 AppError 表达意外失败"；真正的 try-catch 只允许出现在能力边界上，由 GlobalErrorHandler 兜住最后一道。

15.1 目录落位

目录职责关键文件依赖
commons/foundation/src/main/ets/log/日志：分级、结构化、可插拔输出LogLevel.ets · LogSink.ets · Logger.ets无
commons/foundation/src/main/ets/error/异常：错误码、错误类型、映射、全局兜底ErrorCode.ets · AppError.ets · ErrorMapper.ets · GlobalErrorHandler.ets仅 log
commons/foundation/src/main/ets/result/可预期失败的返回值表达Result.ets仅 error
commons/foundation/src/main/ets/util/纯工具：无状态、无副作用Assert.ets · MaskUtil.ets无

为什么这么分：日志与异常是"基础设施"，不属于任何业务域，也不依赖 ArkUI，所以放 foundation 而不是跟断点、颜色模式混在一起。这样 runtime、uikit、features、entry 都能安全依赖它，且不会形成反向依赖。

15.2 异常分级：先决定"该不该 throw"

这是异常设计里最关键的一步。不是所有失败都该抛异常：

级别什么情况表达方式调用方该做什么是否上报
EXPECTED（可预期）校验不通过、无数据、未登录、重复提交Result.fail(AppError.expected(...))，不要 throw直接处理（显示空态/提示），属正常业务分支❌ 不上报
RECOVERABLE（可恢复）网络超时、临时失败、能力不可用throw AppError.recoverable(...)重试 / 降级 / 兜底✅ 上报
FATAL（致命）数据损坏、状态不可恢复、不可继续throw AppError.fatal(...) 并上抛跳到全局兜底，页面做安全降级✅ 必上报

决策流程（照这个走就不会错）：

这个失败是"业务设计的一部分"吗？
  ├─ 是（无数据、校验不过）→ 用 Result 返回，不 throw
  └─ 否 → 它能被调用方恢复吗？
           ├─ 能（重试/降级能解决）→ throw AppError.recoverable
           └─ 不能（继续执行会错得更离谱）→ throw AppError.fatal

为什么这样分：如果把"无数据"也当异常抛，日志里会塞满噪音，真正的线上故障被淹没；反过来，如果网络超时只返回个 null，调用方就不知道该重试还是该放弃。分级的意义是让"必须处理"在类型和日志上都可见。

15.3 throw 规范（硬性 8 条）

#规则反例
T1只允许 throw AppError（或其子类）~~throw '加载失败'~~、~~throw new Error('x')~~
T2构造 AppError 必须给 domain，否则无法归因~~AppError.recoverable(1, 'fail')~~（缺 domain）
T3预期内的失败不 throw，用 Result~~拿不到数据就 throw AppError.expected(...)~~
T4禁止空 catch~~catch (e) {}~~
T5禁止用 catch 掩盖版本差异~~try { newApi() } catch { }~~ → 应用能力检测 + 降级分支
T6异步必须处理：await 或 .catch()，或上抛到边界~~doAsync();（不 await 不 catch）~~
T7异常信息不许拼敏感数据~~AppError.recoverable(1, 'token=' + token)~~
T8抛出前不需要记日志，由边界统一记~~catch(e){ Logger.error(...); throw e; }~~（会重复记录）
T8 容易被忽略：同一异常只记一次日志，位置在边界或全局兜底，不是在每一层 catch 里。

15.4 错误码规范

编码规则：域(2位) * 10000 + 序号(4位)，共 6 位。

域值示例
COMMON00 未知；1 入参非法；2 状态非法；3 能力不可用；4 超时
NETWORK10100001 连接失败
STORAGE20200001 写入失败
PERMISSION30300001 未授权
UI40400001 渲染异常
BUSINESS50500001 业务规则拒绝

约定：错误码一经发布不得改变语义，废弃只做注释不复用；业务域错误码由各 feature 在自己的常量类里按同一规则申请，不要都堆进 foundation。

// commons/foundation/.../error/ErrorCode.ets
export enum ErrorDomain { COMMON = 0, NETWORK = 10, STORAGE = 20, PERMISSION = 30, UI = 40, BUSINESS = 50 }

export class ErrorCode {
  static readonly UNKNOWN: number = 0;
  static readonly PARAM_INVALID: number = 1;
  static readonly ILLEGAL_STATE: number = 2;
  static readonly CAPABILITY_UNAVAILABLE: number = 3;
  static readonly TIMEOUT: number = 4;

  static make(domain: ErrorDomain, sequence: number): number {
    return domain * 10000 + sequence;
  }
}

15.5 try-catch 只允许出现在 4 类边界

边界位置做什么
① 系统 API 调用commons/runtime/**捕获 BusinessError → ErrorMapper.fromBusiness()
② 网络 / 数据访问features/*/data/**捕获后转 Result.fail(AppError)，不让异常穿透到 ViewModel
③ 跨模块调用feature 之间、feature → 运行时同上，模块边界必须翻译成自己的错误语义
④ 全局兜底GlobalErrorHandler接住所有漏网异常，落日志 + 上报

内部纯逻辑不要 try-catch：让异常自然上抛到边界，这样代码干净，且异常不会被中途"吞掉"。

// features/demo/.../data/DemoRepository.ets —— 边界②的标准写法
async fetchItems(): Promise<Result<DemoItem[]>> {
  Logger.info(DOMAIN, TAG, 'fetchItems start');
  try {
    const items = await this.request();          // 可能抛系统异常
    if (items.length === 0) {
      return Result.fail(AppError.expected(1, 'empty data set', DOMAIN));  // 可预期失败
    }
    return Result.ok(items);
  } catch (err) {
    return Result.fail(ErrorMapper.from(err, DOMAIN, 'fetchItems'));       // 意外失败 → Result
  }
}

15.6 全局兜底与上报

// 每个入口 Ability 的 onCreate 里调用一次
GlobalErrorHandler.install();

// 接入崩溃/埋点平台（应用侧自己接）
GlobalErrorHandler.addReporter((error: AppError) => {
  // 上报 error.code / error.domain / error.level / error.toLog()
});

职责边界：GlobalErrorHandler 保证一定有日志、一定有机会上报、EXPECTED 级别不上报。

实测踩坑：ErrorObserver 类型未通过 @kit.AbilityKit 导出，直接 import '@ohos.app.ability.ErrorObserver' 会报模块无法解析。因此工程里用结构化匹配的普通类（具备 onUnhandledException / onException 两个方法）传给 errorManager.on('error', ...)。

15.7 日志规范

级别语义（写的时候按这个判断）：

级别用在哪例子发布版
DEBUG开发期细节：入参出参、状态流转select id=3默认裁剪
INFO关键业务节点页面进入/退出、流程开始/结束、配置生效保留
WARN可自动恢复、走了降级syscap 不可用走兜底、重试第 2 次保留
ERROR需人工介入的失败接口失败、解析失败、状态非法保留
FATAL进程级致命未捕获异常、数据损坏保留

四条硬性要求：

  1. 必须给 domain + tag：Logger.info('demo', 'DemoViewModel', 'loaded 4 items')。没有 domain 的日志在线上等于没有。
  2. 禁止业务代码直连 hilog：否则无法统一裁剪、上报、脱敏。
  3. 敏感信息必须脱敏：手机号/邮箱/token/姓名过 MaskUtil；hilog 的 %{public}s 只放非敏感内容。
  4. 禁止在循环体内打 DEBUG：批量数据只打汇总（loaded 4 items），不要逐条打。

结构化 + 可插拔：

// 默认输出到 hilog；需要落盘或上报时追加 sink，业务代码零改动
Logger.addSink(new MemorySink());        // 本地诊断/单测
// Logger.setMinLevel(LogLevel.WARN);    // 发布版裁剪 DEBUG

该打与不该打：

✅ 该打❌ 不该打
页面/能力生命周期节点循环体内逐条数据
关键分支（走了降级、命中缓存）每帧/每次滑动
失败（带错误码与 domain）完整用户隐私数据
耗时（开始/结束配对）为了"方便调试"长期保留的临时日志

15.8 异常与日志的分工

一句话：异常负责"传递与处理"，日志负责"留痕与归因"，两者不要互相替代。

场景谁负责说明
可预期失败Result 返回给调用方不产生异常日志
意外失败AppError 上抛由边界或全局兜底记一次日志
需要人工介入ERROR 日志 + 上报走 GlobalErrorHandler.notify()
调试细节DEBUG 日志发布版裁剪

15.9 健壮性检查清单

写任何"会失败"的代码前，逐条过：

  • [ ] 入参是否用 Assert 校验了？（fail fast，别让非法值传播）
  • [ ] 这个失败是 EXPECTED 还是 RECOVERABLE / FATAL？分类对吗？
  • [ ] 调用系统 API / 网络前，是否先做了能力检测（CapabilityManager.hasSysCap）？
  • [ ] 超时、重试、降级策略写了吗？（集中在 data 层，不要散落）
  • [ ] 返回值是否可能为 undefined/null？空值语义是否显式处理？
  • [ ] 异步是否都被 await 或 catch？有没有"发了不管"的 Promise？
  • [ ] 状态非法（未初始化就调用）是否有明确报错，而不是静默返回？
  • [ ] 失败路径是否都有日志，且带 domain + code？
  • [ ] 是否有重复记录同一异常（层层 catch 各记一次）？
  • [ ] 用户可见的失败是否有 UI 呈现（走 StateContainer）？

1throw '加载失败'ArkTS 禁止 throw 任意类型；且无法归因throw AppError.recoverable(100001, 'load failed', 'demo')
2catch (e) {}异常被吞，线上无从查起catch (e) { return Result.fail(ErrorMapper.from(e, DOMAIN)); }
