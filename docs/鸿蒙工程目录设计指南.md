# 鸿蒙工程目录设计指南

> 基线：**API 23**（compatibleSdkVersion `6.1.0(23)`，targetSdkVersion `26.0.0`）· 状态管理 **V2** · UI 组件 **HDS（UIDesignKit）**
> 配套范例工程：`hm_easystart/`（EasyStart 仓 HarmonyOS 模板线工程根；**v3.4+ 权威模板（v3.14 起内置完备设置页模板：设置主页两入口行 + 主题外观/通用设置两二级子页 + 关于/政策/许可三子页；v3.15 起 AppComponent 内置主题化原生控件工厂、运行时换肤全局生效），15 模块**：3 共享 HAR（@quizzyjoy/*，v3.11 起独立顶层目录 `quizzyjoy/`，与应用私有层物理隔离、未经授权不可修改）+ 5 应用级 HAR（@easystart/*：AppCommon 编排 / AppPreferences 偏好契约 / AppRoutes 路由 / AppSettings 设置 / AppComponent 应用组件）+ 3 特性 HAR（HomeFeature MVVM 示范 / DemoFeature 基建演示 / WidgetCommon 卡片数据域）+ 4 入口 HAP；212 tasks 构建与四形态运行验证均通过）。`hm_partynow/` 为 v1 历史实装工程，保留作对照，不再随本指南演进。

---

## 0. 适用范围

本指南描述一套经过实机验证的 HarmonyOS 应用工程组织方式，适用于需要同时覆盖 **手机 / 平板 / 2in1 / TV / 手表** 的多端应用，也适用于单设备应用（可裁剪掉多余入口模块）。

**三条硬约束（本指南的所有结论都建立在其上）**：

| 约束 | 内容 | 依据 |
|---|---|---|
| C1 | 同一应用、**同一设备类型只允许一个 entry 类型 HAP** | 官方 FAQ `faqs-package-structure-28` |
| C2 | 断点阈值**由平台定义**，业务代码禁止硬编码像素值 | 最佳实践 `bpta-multi-device-responsive-layout` |
| C3 | HDS 组件有明确的**设备支持矩阵**，不支持时回退原生组件并登记例外 | SDK `api-version/UIDesignKit.json` 实测 |

## 0.1 v2 变更记录（2026-09-23 融合改造）

本轮把 `hm_blueprint` 从"三段公共层 + 平铺入口"的 v1 骨架，升级为吸收 `MyApplication` 资产后的**多端快速启动权威模板**。原则、约束、依赖方向不变，变化集中在结构与能力密度：

| # | 变更 | 动因 |
|---|---|---|
| 1 | 三个入口收进 **`product/`** 目录 | 入口层与公共层物理隔离；根 `build-profile.json5` 用 `./product/*` 路径管理 |
| 2 | 公共层扩为 **5 段**：新增 `DesignTokens`（数值令牌唯一真相源）与 `Data`（网络/存储/权限/国际化/窗口五项能力） | 令牌散落是样式漂移根源；五项能力是所有业务域的共同底座 |
| 3 | 模块目录与 module 名统一 **PascalCase**；包名统一 `@quizzyjoy/*` **kebab-case** | 目录名=模块名可 grep；包名小写与 import 解耦 |
| 4 | `features/demo` 演化成 **`HomeFeature`** 真实特性（列表/组件画廊/主题设置/设备能力四视图） | 演示壳无法示范 Repository→ViewModel→View 全链路 |
| 5 | UIKit 扩容：CommonButton / CommonTag / CommonToast / CommonDialog / CommonSearchBar / RefreshList / UiColorPicker + UiThemeManager | 从 MyApplication 移植并完成 V2 化，提供开箱组件语义 |
| 6 | AppScope 颜色令牌扩至 **17 个 `qj_*`**（含语义色/按钮禁用/填充体系） | 覆盖常用页面 90% 颜色引用，减少硬编码诱惑 |
| 7 | 手表入口**依赖瘦身**：仅 Foundation/Runtime/DesignTokens，页面纯原生原语 | 手表包体降至 260 KB（约为主入口一半） |
| 8 | 新增主题双机制：应用级深浅色令牌（自动）+ 运行时强调色预设（用户可选、持久化） | 深浅色是底线，个性化是产品诉求，两层互不冲突 |

> `hm_partynow/` 与 `Common/MyApplication` 本轮未做任何改动；前者保留作 v1 对照。

### 0.2 v2.1 变更记录（2026-09-24 三库收敛 + 项目 Common）

以"**减少库数量、增强命名语义**"为方向，公共层五段收敛为三段，并实建项目 Common 示范：

| # | 变更 | 动因 |
|---|---|---|
| 1 | **Runtime + Data 合并为 Platform**（`@quizzyjoy/platform`） | Data 名不副实（权限/i18n/窗口非 data 且无数据访问实现）；WindowAdapter 与 BreakpointManager 同属窗口状态却分居两库；「Runtime 无状态 / Data 有状态」的边界站不住 |
| 2 | **DesignTokens 并入 Foundation**（`token/` 子目录） | 数值令牌是"与业务无关的工程原语"，与日志/异常同级；少一个模块少一次心智切换 |
| 3 | **Platform 成为所有 @ohos/@kit 系统调用的唯一发生地**：GlobalErrorHandler / ErrorMapper 自 Foundation 迁入（errorManager 是系统调用）；并再导出 `window` / `UIContext` / `common` 系统类型供上层使用 | 语义判据可 grep：UIKit / features / AppCommon 内 `from '@kit.'` 零命中（纪律 F13/F14） |
| 4 | **UIKit 严格零 @kit**：CommonToast 删除全局 promptAction 弃用兜底，改为入口 Ability 闭包注入 | 组件层不触碰系统 API；弃用告警清零 |
| 5 | **新增三能力**：OrientationManager（锁方向）、ScreenManager（常亮/窗口亮度）、HapticManager（三档震动，失败仅 WARN） | 覆盖视频/游戏/阅读类产品诉求；全部走降级路径 |
| 6 | **实建 `commons/AppCommon`**（项目 Common 示范）：AppBootstrap 承担三入口的 prepare/attachWindow/detachWindow/destroy 装配链；**不依赖 UIKit**（手表可用） | 示范"共享库 vs 项目 Common"判据：装配是项目决策（换 app 不能原样用），放项目 Common |
| 7 | 手表入口改走 AppBootstrap 全链（新增 ColorMode/Preferences/Network），不再独享瘦身链 | 统一装配路径；包体 331.6 KB（+11%，仍远低于主入口） |
| 8 | 纪律 grep 常态化：旧包名 `@quizzyjoy/{runtime,data,design-tokens}` 全工程零命中 | 重命名可验证，不留暗桩 |

## 1. 顶层设计原则

| 编号 | 原则 | 说明 |
|---|---|---|
| P1 | **目录名 = 模块名 = 包名** | 三者同名可消除"看到 import 不知道对应哪个目录"的认知成本 |
| P2 | **严格单向依赖** | `entry → features → commons`，禁止反向与跨 feature 直连 |
| P3 | **能力下沉、差异上浮** | 通用能力沉到 `commons`；设备/断点差异留在入口层与页面层 |
| P4 | **一个入口一个 module** | 设备形态差异用 module 隔离，不用 `if (deviceType)` 在页面里分叉 |
| P5 | **状态管理统一 V2** | 新代码只用 V2 装饰器，禁止新增 V1 用法 |
| P6 | **样式令牌集中在 AppScope** | 颜色等设计令牌放应用级资源，模块内不重复定义 |
| P7 | **可编译是底线** | 任何结构方案都必须能通过 `devecocli build` 并产出签名 HAP |

## 3. 分层职责

| 层 | 目录 | 职责 | 明确不做的事 |
|---|---|---|---|
| 应用级 | `AppScope/` | bundleName、版本、应用图标、**颜色设计令牌** | 不放任何 ArkTS 代码 |
| 入口层 | `product/entry` `product/entry_pc` `product/entry_tv` `product/entry_wearable` | 生命周期、窗口、路由分流、**形态专属布局**、调用 AppBootstrap 装配、Extension Ability（备份/卡片） | 不写业务规则；不直接被其他模块依赖 |
| 业务特性层 | `features/<业务域>` | 一个业务域一个模块：页面视图、ViewModel、Repository | 不直接依赖其他 feature；不碰系统能力（走 Platform） |
| 应用级公共 | `commons/AppCommon`（编排）+ `commons/AppRoutes` + `commons/AppSettings`（按域分模块，§3.1） | 本应用的启动装配决策与项目级公共（路由名注册表/设置域）；按域需求驱动增包 | 不放可跨应用复用的能力；AppCommon 不依赖 VitalUI |
| 应用级 Common（**fork 工程**按需建） | `commons/Common`（`@<应用名>/common`，与 AppCommon 平级，§12.3 / §17.1） | 本 app 多 feature 复用的系统能力封装与通用工具——应用自己的 platform 延伸层（EasyTools 实证 17 类：安全随机/剪贴板/扫码/媒体选择/OCR/传感器/设备信息等）；可依赖三库复用 Logger/ErrorMapper | 模板自身不建（无具体 app 语义）；不放业务玩法（→feature 域内 util）；**不改三库** |
| 基础设施层 | `quizzyjoy/Foundation` | 日志、异常原语、Result、断言、脱敏、数值令牌 | 不依赖 ArkUI；**零 @ohos/@kit 导入**（唯一豁免：LogSink 内部 hilog） |
| 平台能力层 | `quizzyjoy/Platform` | 断点、颜色模式、能力检测、设备信息、形态因子、兼容、网络、存储、权限、国际化、窗口、方向、屏幕、震动、错误映射与全局兜底；**跨应用通用系统能力的复用域**（换 app 还能用；类型/稳定工具 import 各层放开——v3.8） | 不含业务语义与 UI |
| 公共组件层 | `quizzyjoy/VitalUI` | 通用组件（含 Canvas 图表五件套、取色器、Loading）、动效规范、主题管理、组件 API 约定 | 不依赖任何 feature；**零脆弱能力调用**（Toast 等系统实现由入口闭包注入；类型/稳定工具 import 放开——v3.8） |
| 配置层 | 根目录 json5 / hvigor | 构建、签名、产品、检查规则 | — |

**归属判据（放进哪一层？）**

1. 这段代码**只有某个设备形态才需要** → 入口层。
2. 这段代码**只有某个业务域才需要** → 该 feature。
3. 这段代码**多个业务域都要用** → 应用级 `commons/`（`@<应用名>/*`，§3.1 / §17）；若同时跨 app 通用且无业务痕迹，提上游轮次进 `quizzyjoy/`（§12.3 四档）。
4. 这段代码**和业务无关、跨应用通用（换 app 还能用）的系统能力** → `quizzyjoy/Platform`（无论有无状态）。
5. 这段代码**连系统能力都不涉及**（日志、异常、纯计算、纯数值常量）→ `quizzyjoy/Foundation`。
6. 这段代码**是"本应用"的决策而非通用能力**（装配链、品牌语义、多能力编排）→ 项目 Common（`commons/AppCommon`），判据详见 §17。
7. 拿不准 → 先放 feature，出现第二个使用方时再上移（禁止提前抽象）。

> **适用范围（v3.11.1）**：判据 4/5 只回答「语义上属于哪一层」，**仅在本模板工程 趣开发 EasyStart 内可直接落位 `quizzyjoy/`**——那是上游模板轮次动作。fork 应用工程中 `quizzyjoy/` **只读**：判据命中三库时按 §12.3 四档分流（单 feature 用 → 域内 `util/`；本 app 多 feature 复用 → `@<应用名>/common`；确认跨 app 通用 → 提上游轮次），禁止就地改三库。判据 3 的 `commons/` 指应用级 `@<应用名>/*`，不是三库。

### 4.7 注释纪律：块注释内标识符紧邻 `*/` 的提前终止坑（2026-10-02 裁定落盘）

**机理**：块注释以**第一个** `*/` 序列终结。注释文字里列举 API/常量名时，若标识符尾紧贴 `*/`，词法分析器将其判为注释终结符——注释提前截断，**后续文档内容被当作代码解析**，产生大量报错位置在远处的连环编译错（极具误导性，排障成本高）。

**事故档案（两次）**：
- v2.4（`856eb4b`）：注释内写 `lock`+`/`+`unlock` 组合（锁定 API 对描述），触发 **48 连环编译错**
- v3.0（`32283ee`）：注释内写 `BLUR_`+`/` 型常量组列举，同型复现（MEMORY 已录仍复现——证明仅靠「记录」防不住）

**安全写法**：注释内列举以 `/` 结尾或含 `/` 的标识符（API 名、常量组、路径）时——①标识符与后续文字间加空格/顿号（写「BLUR_ 与 OFFSET_Y_ 前缀」而非连写）；②或改行内注释 `//`；③或重排语序避免 `/` 尾邻。

**机器自检（commit 前可跑 / 未来接 CI）**：

```powershell
# 检出「字字符紧邻 */」的风险序列（正常注释终结为空格或换行前导，不会命中）
Get-ChildItem -Recurse -Include *.ets -Path commons,features,product |
  Where-Object { $_.FullName -notmatch 'build|oh_modules' } |
  Select-String -Pattern '[A-Za-z0-9_]\*/'
```

说明：`code-linter.json5` 的 arkts-* 规则集无注释内容检查类规则，linter 帮不上；编译器能抓但报错雪崩在远处——**grep 自检是唯一低成本机器防线**。

> 应用级域包（AppRoutes / AppSettings / AppComponent）**应用语义封装彼此禁止互相依赖**——按域独立，域间协同一律经入口装配。**例外（v3.22）**：AppComponent 的**系统组件基础封装**（CommonDialog / CommonToast / CommonSearchBar，纯系统原语套令牌、零应用语义）可被 AppSettings 等兄弟域依赖，不破「应用语义域包互禁」——基础封装是「系统组件换肤/换色的公共层」，语义封装（AppDialog 组合语义、AppSnackBar 反馈语义、AppSection 分区规范）仍互禁。`AppPreferences` 是**零依赖契约包**（偏好键/字号系数/强调色校验单一真相源，v3.18），位于最底层、被 AppCommon 与 AppSettings 依赖，不参与域包互禁（类比 AppRoutes 被 features 依赖的叶子模式）。
> **v3.12 判例**：设置页分组（组标题/卡片排布）不得为复用 `AppSection` 而让 AppSettings 依赖 AppComponent——在域内用 Foundation 令牌（AppFontSize/AppSpacing/AppRadius/DesignToken）+ 原生布局原语自绘（见 SettingsView）；跨域复用诉求经入口装配或提上游评估，不破域包互禁。
>
> **v3.13 判例（@kit 豁免边界，F16）**：AppSettings 设置行直接 import `@kit.UIDesignKit` 的 HDS 表现组件（HdsListItemCard 等），不经 Platform 包装、不进 VitalUI——表现组件是纯 UI 无脆弱能力语义，应用级域包（不含 AppCommon/三库/features）可直接使用；`@kit.ArkTS` 稳定工具（util.TextDecoder）同口径放行。但行点击触发的**系统能力**（市场跳转 startAbility、缓存文件清理）属跨应用通用 → 落 Platform（MarketHelper/CacheManager），域包只调 Manager。即「**表现组件可直达，跨应用通用能力落 Platform**」。
> 手表入口不依赖 VitalUI / HomeFeature / AppSettings / AppComponent 是**主动设计**：手表页面只用原生原语压体积；若手表确实需要某能力，先评估用 Platform 直连，再考虑解禁并登记。

## 6. 多设备入口组织

### 6.1 入口划分（依据 C1：同设备类型只允许一个 entry HAP）

| 入口 module | deviceTypes | 覆盖形态 | 首页 |
|---|---|---|---|
| `entry` | `phone` / `tablet` | 手机、平板（统一入口） | `pages/Index.ets` |
| `entry_pc` | `2in1` | 2in1 PC（v2.3.2 独立，对齐官方 products/pc） | `pages/PcIndex.ets` |
| `entry_tv` | `tv` | 智慧屏 | `pages/TvIndex.ets` |
| `entry_wearable` | `wearable` | 智能穿戴 | `pages/WearableIndex.ets` |

四者的 `deviceTypes` **互不重叠**，因此不违反 C1，可以共存于同一应用。

**2in1 独立入口（v2.3.2 已按用户决断执行拆分）**：官方 sample_in_harmonyos 按「形态 = 入口」彻底执行——phone 入口仅 phone+tablet，pc 入口仅 2in1 且复制全套 Ability（PcAbility / PcBackupAbility / PcFormAbility）。本模板已对齐：`product/entry_pc` 装配链与 entry 同源（AppBootstrap 编排），`PcIndex` 保留完整断点逻辑（自由窗口可任意缩放，拉窄即回 sm/md 布局），PC 专属交互（键鼠 hover、右键菜单、快捷键）在业务视图内按 CapabilityManager 分支扩展。原拆分判据保留，供其他形态同类决策参考：

1. 需要独立的 Ability 生命周期或多窗口/多实例行为（PC 自由窗口语义与手机不同）
2. 专属交互规模化，断点布局无法表达
3. 包裁剪需求：某形态需排除其他形态专属 feature（拆分后共享层零改动，按依赖裁剪）
4. 发布节奏差异：某形态单独灰度/版本

### 6.3 入口分流链路

```
设备安装应用
  → 系统读取各 HAP 的 module.json5.deviceTypes
  → 与当前设备类型匹配的唯一 entry HAP 被安装
  → 该 HAP 的 mainElement Ability 启动
  → 加载各自 pages/profile/main_pages.json 的首个页面
  → 页面内再按断点切换布局
```

**关键点：分流发生在安装期（deviceTypes 匹配），不是运行期 `if`。** 运行时只需要处理断点，不需要处理"我是什么设备"。

### 6.4 各形态 UI 组织差异

| 形态 | 导航 | 内容组织 | 交互 |
|---|---|---|---|
| phone / tablet / 2in1 | `HdsTabs`（sm/md 底部；lg/xl 侧边）+ `HdsNavigation` 分栏；设置为 titleBar 菜单齿轮进入的独立子页（v3.12） | 列表（md 2 列、lg+ 3 列） | 触摸（2in1 另有键鼠） |
| TV | 原生 `Tabs`（HDS 例外 E1）+ `HdsNavigation` 宿主承载子页（v3.12；HdsNavigation 矩阵含 tv），header 自绘齿轮 | 横向内容带（content rail） | 遥控器方向键 + 焦点 |
| 手表 | 无 Tab，单页 | 单列、首屏出结论 | 旋钮 / 手势 |

### 6.5 Extension Ability 模板位（v2.3.1，官方对标实证）

Extension Ability（FormAbility / UIExtensionAbility / BackupAbility 等）的 `srcEntry` 必须指向**所属入口模块内**的文件（module.json5 同模块声明，跨模块不生效）——这决定了物理落位：

| 内容 | 落位 | 官方实证 |
|---|---|---|
| FormAbility 类 | 入口模块 `ets/<module>formability/` | `phoneformability/`（phone）、`pcformability/`（pc）——**每入口一份**，不共享 |
| UIExtensionAbility 类 | 入口模块 `ets/uiextensionability/` | 仅 phone 入口有（按需） |
| 卡片 UI 页面 | 入口模块 `ets/widget/pages/` + extensionAbilities metadata | `widget/pages/` |
| 跨入口共享的卡片 VM / 数据更新 / Form 助手 | features 公共层（§17.5） | abilitycommon 的 ArticleServiceCardVM / UpdateFormData / FormAbilityHelper |

**本模板现状（v2.3.3）**：`entry` / `entry_pc` / `entry_wearable` 已各预建一套卡片骨架——`EntryFormAbility` / `PcFormAbility` / `WearableFormAbility`（onAddForm 返回静态数据，onUpdate/onRemove/onCastToNormalForm 仅日志）+ 各自 `widget/pages/WidgetCard.ets`（2*2 静态卡，不进 main_pages，由 form_config.json 指定）。可编译、系统已注册（bm dump 实证 extensionAbilities 含 ohos.extension.form），**不接业务**；接业务时数据绑定经卡片页 LocalStorage（卡片框架当前仅支持 V1 装饰器，登记为 P5 例外），跨入口共享逻辑迁往 features 公共层；手表卡片形态受限（静态、有限尺寸），supportDimensions 按手表文档调整。**TV 永不建卡片**——智慧屏系统不支持服务卡片（官方 tv 入口亦无 formability）；TV 亦无 backup（官方 tv 同样没有），wearable backup 骨架 v2.3.3 已补齐对齐官方。

## 7. 断点系统

### 7.1 断点定义（官方阈值，按**应用窗口宽度**）

| 断点 | 窗口宽度（vp） | 典型形态 | 栅格列数 |
|---|---|---|---|
| `xs` | < 320 | 智能穿戴 | 4 |
| `sm` | [320, 600) | 手机竖屏、小折叠 | 4 |
| `md` | [600, 840) | 平板竖屏、手机横屏、折叠展开 | 8 |
| `lg` | [840, 1440) | 平板横屏、智慧屏 | 12 |
| `xl` | ≥ 1440 | 2in1 全屏、折叠电脑 | 12 |

**纪律（C2）**：取值一律来自 `UIContext.getWindowWidthBreakpoint()` / `getWindowHeightBreakpoint()`，不自己写 `if (width < 600)`。

### 7.2 实现（`quizzyjoy/Platform`）

- `breakpoint/BreakpointConstants.ets`：把平台枚举映射为语义名 + 栅格列数 + `isWide()`。
- `breakpoint/BreakpointManager.ets`：`@ObservedV2` 单例，监听 `windowSizeChange`，把断点写入 `@Trace` 字段。
- 初始化位置：`EntryAbility.onWindowStageCreate` 的 `loadContent` 回调内（经 `AppBootstrap.attachWindow()` 统一触发，此时断点查询才有效）。

```ts
// 订阅侧（V2 组件）—— 声明 @Local 后直接读 @Trace 字段即自动刷新
@Local breakpoint: BreakpointManager = BreakpointManager.getInstance();
// build 中：
Text(`breakpoint = ${this.breakpoint.breakpoint}`)
List().lanes(this.viewModel.columns(this.breakpoint.breakpoint))
```

### 7.3 断点驱动布局示例

`product/entry/src/main/ets/pages/Index.ets` 中：

```ts
.mode(this.breakpoint.isWide() ? NavigationMode.Split : NavigationMode.Stack)
.barPosition(this.breakpoint.isWide() ? BarPosition.Start : BarPosition.End)
.lanes(this.viewModel.columns(this.breakpoint.breakpoint))   // sm=1 / md=2 / lg,xl=3
```

### 7.4 监听手段选择

| 手段 | 用途 | 本项目定位 |
|---|---|---|
| `window.on('windowSizeChange')` + `UIContext.getWindowWidthBreakpoint()` | 断点主链路 | **主链路** |
| `display.on('change')` | 旋转 / 分辨率（时序早于 window） | 旋转专用 |
| `display.on('foldStatusChange')` | 折叠态变化 | 折叠专用（HoverStore 采折叠形态 + 刷新折痕；OrientationManager 采重申栈顶策略；**off 必须传回调精确解绑**） |
| `@Env(SystemProperties.BREAK_POINT)`（API 22+） | 组件内声明式读断点 | 可选补充，不作为唯一断点源 |

### 8.2 三方依赖集中版本管理（v2.3 起）

三方库版本**单一来源**：根目录 `VersionFile.json5` 集中声明，各 oh-package.json5 用 `@param:` 注入引用：

```json5
// VersionFile.json5
{ "version": "1.0.0", "dependencies": { "hypium-version": "1.0.25", "hamock-version": "1.0.0" } }

// 根 oh-package.json5（必含 parameterFile 声明，否则 ohpm 报 00622014）
{
  "devDependencies": { "@ohos/hypium": "@param:dependencies.hypium-version" },
  "parameterFile": "VersionFile.json5"
}
```

- **何时用**：引入第二个三方库（如 imageknife）起，版本一律进 VersionFile；升级三方库只改这一处。
- **踩坑**：`parameterFile` 声明缺失时 ohpm install 报 `00622014 Parameter File Not Config Error`（v2.3 实测，复核报告 #43）。
- 借鉴来源：官方 sample_in_harmonyos 根目录同款机制。

### 8.3 混淆规则（v2.3.1 起，官方对标采纳）

**接线**：混淆只在 release 生效，由各入口 build-profile.json5 的 `buildOptionSet.release` 声明，规则文件 `obfuscation-rules.txt` 与 build-profile 同级（四入口同款）：

```json5
"buildOptionSet": [{
  "name": "release",
  "arkOptions": { "obfuscation": { "ruleOptions": { "enable": true, "files": ["./obfuscation-rules.txt"] } } }
}]
```

**规则基线**（对齐官方 phone 入口）：`-enable-property-obfuscation` / `-enable-toplevel-obfuscation` / `-enable-export-obfuscation` 三开；`-enable-filename-obfuscation` 默认关（动态加载/资源路径风险）。keep 清单按需追加（JSON 反序列化字段、反射全局名），**禁止预防性堆积——新增 keep 必须附触发原因**。

**与官方的差异（及理由）**：

- 官方每个模块（含 HAR）都配 ruleOptions + consumerFiles；本模板 HAR **不接线**——本地源码 HAR 在 HAP 打包时被入口规则全量混淆；consumer-rules 仅发布二进制 HAR 到 ohpm 时需要（官方 consumer-rules.txt 实测全空，机制占位）
- 官方 phone 有 `runtimeOnly.packages`（HSP 动态导入的防混淆保留）；本模板全 HAR 无 HSP，不抄
- 官方根 build-profile 配 7 套 product 环境（dev/uat/beta/prod...）；本模板单 default，多环境需求出现时按官方 targets×applyToProducts 模式扩展

**产物归档**：release 构建在 `outputs/default/symbol/release/` 生成 `xxx-nameCache.json`（混淆名映射）与 sourceMaps——**必须随版本归档**，否则线上崩溃栈不可反解。验证证据（release 139 tasks SUCCESS、尺寸 −49.8%、混淆产物真机全链路通过）见 §16.8。

#### 9.4.3 消费纪律

1. 组件/页面一律 `$r('app.color.<令牌名>')` 或 Foundation 常量类；**禁止硬编码**色值/圆角/字号/间距字面量，**禁止算术逃逸**（`CAPTION+1`、`SM+2` 类）；
2. 新增色先入 §9.4.1 表再消费；改 `ChartData.ets` 色板必须同步资源表；
3. `app_state_*` 是叠加层色，叠在目标底色上，不做独立底色；
4. 半透明文本四级的兜底：叠底异常时局部换 `app_gray_5/6` 不透明档，禁止新造灰色；
5. 圆角按组件映射选档（§9.4.2 + 设计文档 §II.2），嵌套遵守同心律（外层 = 内层 + 内边距）；
6. 阴影克制：同屏 ≤2 档，TV 弱化；间距多端差异走 `DesignToken` 语义方法（pagePadding/cardPadding/screenEdgePadding 等）；
7. **令牌豁免登记（v3.7 起）**：域固有、无法映射刻度的常量（图表色板、取色器色相学常量、品牌 seed 色等）必须提为命名常量，并在**文件头登记豁免理由 + 先例引用**（先例：`ChartData.ets` 图表色板、`CommonColorPicker.ets` 色相学常量）；**未登记的散落字面量即违规**，grep 验收按此口径执行。

## 11. 状态管理 V2 规范

### 11.1 装饰器清单

| 装饰器 | 用途 | 本项目用法 |
|---|---|---|
| `@ComponentV2` | V2 组件 | 所有新组件 |
| `@Local` | 组件内部可变状态 | `@Local viewModel`、`@Local breakpoint` |
| `@Param` | 父传子的不可变参数 | `@Param title: string = ''` |
| `@Event` | 子通知父的回调 | `@Event onAction: () => void` |
| `@ObservedV2` + `@Trace` | 可观测模型（细粒度） | `DemoViewModel`、`BreakpointManager` |
| `@Monitor` | 深度监听变化 | 需要副作用时 |
| `@Computed` | 派生值 | 列数、是否宽屏 |
| `@Provider` / `@Consumer` | 跨层级注入 | 子树隔离 / 单测注入假断点 |

### 11.2 V1 → V2 对照

| V1 | V2 等价 | 迁移要点 |
|---|---|---|
| `@State` | `@Local` | 直接替换 |
| `@Prop` | `@Param` | V2 的 `@Param` 默认不可变；需可变则配合 `@Once` 或本地副本 |
| `@Link` / `@ObjectLink` | `@Param` + `@Event`（双向用手动回传） | 子组件不再直接改父状态 |
| `@Provide` / `@Consume` | `@Provider` / `@Consumer` | 语义基本一致 |
| `@Observed` + `@ObjectLink` | `@ObservedV2` + `@Trace` | 观测粒度更细，可按字段刷新 |
| `@Watch` | `@Monitor` | 支持多字段监听 |
| `AppStorage` | `AppStorageV2` | V2 专用全局存储 |
| `ForEach` | `Repeat` | 大数据量列表优先 `Repeat` |

### 11.3 硬性规则

1. **不新增 V1 用法**；存量 V1 需登记并排期迁移。
2. 禁止在同一个 `@ObservedV2` 类中出现 V1 装饰器。
3. 跨 V1/V2 传递对象时需消除双重代理（`UIUtils.enableV2Compatibility`）。
4. 组件只读 `@Trace` 字段即完成订阅，**不需要** `@ObjectLink` 或逐层透传。

### 11.4 现状核验（grep 实测）

骨架工程中状态装饰器分布：`@ComponentV2` 6 · `@ObservedV2` 4 · `@Local` 9 · `@Param` 15 · `@Event` 3 · `@Trace` 10，**V1 装饰器 0 处**。

## 12. 分包方案

### 12.1 何时拆

| 信号 | 动作 |
|---|---|
| 单个 feature 编译 > 30s 且改动频繁 | 拆成独立 HAP（动态特性） |
| 只在特定场景使用的大体积能力（如某个 Kit 全家桶） | 拆成 HSP 按需加载 |
| 多产品共用同一能力 | 抽成 HSP（单例共享内存） |

### 12.2 HAR vs HSP

| 维度 | HAR（静态共享包） | HSP（动态共享包） |
|---|---|---|
| 打包方式 | 编译进使用方 | 独立打包、运行时加载 |
| 是否单例 | 否（每个使用方一份） | **是**（全局一份） |
| 典型用途 | 二方/三方库、组件库 | 元服务分包预加载、按需加载、需单例的状态 |
| 本项目定位 | `quizzyjoy/Foundation`、`quizzyjoy/Platform`、`quizzyjoy/VitalUI`（共享三库）+ `commons/AppCommon`（项目 Common） | 若需全局单例能力，改 HSP |

### 12.3 包命名规范（作用域语义，v2.2 起）

包名作用域回答"**这个包归谁**"，一眼区分可跨应用复用的资产与本项目私有模块：

| 类别 | 作用域规则 | 本模板实例 | 复制模板到新应用时 |
|---|---|---|---|
| 共享三库（跨应用复用） | 组织作用域 `@quizzyjoy/*` | `@quizzyjoy/foundation`、`@quizzyjoy/platform`、`@quizzyjoy/vitalui` | **原样保留**（可发布、可多 app 共用；或迁至独立公共仓库） |
| 应用自有 HAR（本项目私有） | 仓库名末段作用域 `@<repo>/*` | `@easystart/app-common`、`@easystart/app-preferences`、`@easystart/app-routes`、`@easystart/app-settings`、`@easystart/app-component`、`@easystart/home-feature`、`@easystart/demo-feature`（仓库名 `EasyStart` 末段） | 整体替换为新应用作用域（如 PartyNow 应用 → `@partynow/*`） |
| 入口 HAP | 无作用域裸名 | `entry` / `entry_pc` / `entry_tv` / `entry_wearable` | 一般沿用 |

> **三共享库是组织级多项目公共库**：`@quizzyjoy` 是组织作用域，趣开发 EasyStart 仓库只是**暂存地**——未来抽出独立仓库时，EasyRandom、PartyNow 及后续 app 可直接依赖同一份公共库。VitalUI 的组件谱系本就源自 EasyRandom 的同名库，这条路径已被实践过一次。
>
> 判据：包名前缀即复用边界——`@quizzyjoy/` 前缀的包换一个 app 仍可用（§17 共享库判据）；`@easystart/` 前缀的包含本项目决策，复制模板时应当被审视甚至重写。oh-package-lock 与全部 import 需同步（构建自动再生 lock，import 需 grep 清零旧名）。

**三库修改权（2026-10-08 用户裁定；v3.11 目录物理隔离强化）**：

- **物理位置即授权边界（v3.11）**：三大件在本模板中位于**独立顶层目录 `quizzyjoy/`**（v3.11 自 `commons/` 迁出并 git mv 保留历史），与应用私有层 `commons/`（仅 `@easystart/*` 四包）物理隔离；`quizzyjoy/README.md` 是目录内授权约束宣言。fork 出的应用工程（hm_easytools、hm_partynow 等）复制该目录后**同名同权**。
- **`@quizzyjoy/*` 三大件（Foundation / Platform / VitalUI）是跨项目级资产**——fork 出的应用工程（hm_easytools、hm_partynow 等）**只消费、无权修改**：不新增文件、不改既有文件、不在其 Index.ets 加导出、不改其 oh-package/build-profile 接线。应用侧发现的缺陷与增强需求，回上游（趣开发 EasyStart / 未来独立公共仓）以模板轮次统一演进，不在应用仓就地改；本模板仓内对三大件的修改也只能以模板轮次提交（`[bp]`），不夹带应用侧决策。
- **应用级通用封装落位**：应用需要、三大件尚未提供的能力（如 EasyTools 的安全随机/剪贴板/扫码），一律建**应用级 Common 包**——包名 `@<应用名>/common`（如 `@easytools/common`），目录 `commons/Common`，与 AppCommon（启动装配）平级。它可依赖三大件（复用 ErrorMapper/Logger 等），是「应用自己的 platform 延伸层」。
- 违例判别：`git diff` 触及 `quizzyjoy/{Foundation,Platform,VitalUI}` 任一路径的应用仓提交即为越权（上游同步轮次除外）。

- **纯算法不等于可进 Foundation——落位四档判据（2026-10-08 摩斯双轨裁定补写）**：零系统调用只是进 Foundation 的必要条件、不是充分条件；Foundation 只收「与业务无关的工程基础原语」（日志/Result/断言/脱敏/设计令牌）。带业务或玩法语义的能力按以下顺序落位：① **单一 feature 使用 → 域内 `util/`（域内为主）**；② 两个及以上 feature 复用且无业务语义 → 应用级 `@<应用名>/common`；③ 跨 app 复用的工程原语 → 提上游轮次进三大件；④ 任何情况都不允许应用仓就地改三大件。
  - 摩斯电码案例（EasyTools）：CalcFeature（文本 ↔ 摩斯码转换）与 SensorFeature（手电筒闪光摩斯）都需要摩斯能力，裁定**域内为主、不上移**——`CalcFeature/util/MorseUtil.ets` 为文本转换主线，`SensorFeature/util/MorseEngine.ets` 为闪光时序编码，两份码表同源（ITU-R M.1677）、改表时两处同步；曾误放入 `@quizzyjoy/foundation/util/MorseEngine.ets` 的副本已删除。

### 12.4 动态分包要点

- feature 型 HAP 设 `"deliveryWithInstall": false`，由主包按需安装。
- 跨 HAP 跳转用系统路由表 `router_map.json` + `NavPushPathHelper`，**不要**用 Navigation 直接跨 HAP 跳转（会失败）。
- 详细手动创建步骤见配套文档《分包手动创建清单》。

## 15. 异常处理 · 代码健壮性 · 日志规范

### 15.0 一句话总纲

**基础层提供能力，业务层只表达意图，边界统一兜底。**

具体说：日志与异常的**原语**（Logger / AppError / Result / 断言 / 脱敏）由 `quizzyjoy/Foundation` 提供；**系统调用侧**（errorManager 监听、BusinessError 映射）由 `quizzyjoy/Platform` 的 ErrorMapper / GlobalErrorHandler 承担（v2.1 迁入，因为它们是跨应用通用的真实 @ohos 系统调用）；业务代码只负责"用 Result 表达可预期失败、用 AppError 表达意外失败"；真正的 try-catch 只允许出现在**能力边界**上，由 `GlobalErrorHandler` 兜住最后一道。

### 15.1 目录落位

| 目录 | 职责 | 关键文件 | 依赖 |
|---|---|---|---|
| `quizzyjoy/Foundation/src/main/ets/log/` | 日志：分级、结构化、可插拔输出 | `LogLevel.ets` · `LogSink.ets` · `Logger.ets` | 无 |
| `quizzyjoy/Foundation/src/main/ets/error/` | 异常**原语**：错误码、错误类型 | `ErrorCode.ets` · `AppError.ets` | 仅 log |
| `quizzyjoy/Foundation/src/main/ets/result/` | 可预期失败的返回值表达 | `Result.ets` | 仅 error |
| `quizzyjoy/Foundation/src/main/ets/util/` | 纯工具：无状态、无副作用 | `Assert.ets` · `MaskUtil.ets` | 无 |
| `quizzyjoy/Platform/src/main/ets/error/` | 异常**系统调用侧**：BusinessError 映射、全局兜底 | `ErrorMapper.ets` · `GlobalErrorHandler.ets` | foundation |

**为什么这么分**：日志与异常原语是"基础设施"，不依赖 ArkUI、不触碰系统 API，放 `Foundation`；而 ErrorMapper / GlobalErrorHandler 必须调用 `@ohos.app.ability.errorManager`，按 F14（跨应用通用系统能力落 Platform）迁入 `Platform`。这样 `Platform`、`VitalUI`、`features`、`product/*` 都能安全依赖 Foundation，且**日志与异常类型仍单一来源于 Foundation**，任何一层都不允许自建日志出口或错误类型。

### 15.2 异常分级：先决定"该不该 throw"

这是异常设计里最关键的一步。**不是所有失败都该抛异常**：

| 级别 | 什么情况 | 表达方式 | 调用方该做什么 | 是否上报 |
|---|---|---|---|---|
| **EXPECTED**（可预期） | 校验不通过、无数据、未登录、重复提交 | `Result.fail(AppError.expected(...))`，**不要 throw** | 直接处理（显示空态/提示），属正常业务分支 | ❌ 不上报 |
| **RECOVERABLE**（可恢复） | 网络超时、临时失败、能力不可用 | `throw AppError.recoverable(...)` | 重试 / 降级 / 兜底 | ✅ 上报 |
| **FATAL**（致命） | 数据损坏、状态不可恢复、不可继续 | `throw AppError.fatal(...)` 并上抛 | 跳到全局兜底，页面做安全降级 | ✅ 必上报 |

**决策流程（照这个走就不会错）**：

```
这个失败是"业务设计的一部分"吗？
  ├─ 是（无数据、校验不过）→ 用 Result 返回，不 throw
  └─ 否 → 它能被调用方恢复吗？
           ├─ 能（重试/降级能解决）→ throw AppError.recoverable
           └─ 不能（继续执行会错得更离谱）→ throw AppError.fatal
```

**为什么这样分**：如果把"无数据"也当异常抛，日志里会塞满噪音，真正的线上故障被淹没；反过来，如果网络超时只返回个 null，调用方就不知道该重试还是该放弃。分级的意义是**让"必须处理"在类型和日志上都可见**。

### 15.3 throw 规范（硬性 8 条）

| # | 规则 | 反例 |
|---|---|---|
| T1 | 只允许 `throw AppError`（或其子类） | ~~`throw '加载失败'`~~、~~`throw new Error('x')`~~ |
| T2 | 构造 AppError 必须给 `domain`，否则无法归因 | ~~`AppError.recoverable(1, 'fail')`~~（缺 domain） |
| T3 | 预期内的失败不 throw，用 `Result` | ~~拿不到数据就 `throw AppError.expected(...)`~~ |
| T4 | 禁止空 catch | ~~`catch (e) {}`~~ |
| T5 | 禁止用 catch 掩盖版本差异 | ~~`try { newApi() } catch { }`~~ → 应用能力检测 + 降级分支 |
| T6 | 异步必须处理：`await` 或 `.catch()`，或上抛到边界 | ~~`doAsync();`（不 await 不 catch）~~ |
| T7 | 异常信息不许拼敏感数据 | ~~`AppError.recoverable(1, 'token=' + token)`~~ |
| T8 | 抛出前不需要记日志，由边界统一记 | ~~`catch(e){ Logger.error(...); throw e; }`~~（会重复记录） |

> T8 容易被忽略：**同一异常只记一次日志**，位置在边界或全局兜底，不是在每一层 catch 里。

### 15.4 错误码规范

编码规则：`域(2位) * 10000 + 序号(4位)`，共 6 位。

| 域 | 值 | 示例 |
|---|---|---|
| COMMON | 0 | `0` 未知；`1` 入参非法；`2` 状态非法；`3` 能力不可用；`4` 超时 |
| NETWORK | 10 | `100001` 连接失败 |
| STORAGE | 20 | `200001` 写入失败 |
| PERMISSION | 30 | `300001` 未授权 |
| UI | 40 | `400001` 渲染异常 |
| BUSINESS | 50 | `500001` 业务规则拒绝 |

约定：错误码**一经发布不得改变语义**，废弃只做注释不复用；业务域错误码由各 feature 在自己的常量类里按同一规则申请，不要都堆进 `foundation`。

```ts
// quizzyjoy/Foundation/.../error/ErrorCode.ets
export enum ErrorDomain { COMMON = 0, NETWORK = 10, STORAGE = 20, PERMISSION = 30, UI = 40, BUSINESS = 50 }

export class ErrorCode {
  static readonly UNKNOWN: number = 0;
  static readonly PARAM_INVALID: number = 1;
  static readonly ILLEGAL_STATE: number = 2;
  static readonly CAPABILITY_UNAVAILABLE: number = 3;
  static readonly TIMEOUT: number = 4;

  static make(domain: ErrorDomain, sequence: number): number {
    return domain * 10000 + sequence;
  }
}
```

### 15.5 try-catch 只允许出现在 5 类边界

| 边界 | 位置 | 做什么 |
|---|---|---|
| ① 系统 API 调用 | `quizzyjoy/Platform/**` | 捕获 `BusinessError` → `ErrorMapper.fromBusiness()` / `ErrorMapper.from()`；Platform 层捕获后转 `Result.fail(AppError)` 或返回兜底值 |
| ② 网络 / 数据访问 | `features/*/data/**` | 捕获后转 `Result.fail(AppError)`，不让异常穿透到 ViewModel |
| ③ 跨模块调用 | feature 之间、feature → 运行时 | 同上，模块边界必须翻译成自己的错误语义 |
| ④ UI 系统调用（弹窗/Toast） | `@easystart/app-component` 的 CommonToast/CommonDialog、页面对话框 | 捕获 `openCustomDialog` 同步异常与 Promise reject，转用户可见提示，不中断流程 |
| ⑤ 全局兜底 | `GlobalErrorHandler` | 接住所有漏网异常，落日志 + 上报 |

**内部纯逻辑不要 try-catch**：让异常自然上抛到边界，这样代码干净，且异常不会被中途"吞掉"。

```ts
// features/HomeFeature/.../data/HomeRepository.ets —— 边界②的标准写法
async fetchItems(): Promise<Result<HomeItem[]>> {
  Logger.info(DOMAIN, TAG, 'fetchItems start');
  try {
    const items = await this.request();          // 可能抛系统异常
    if (items.length === 0) {
      return Result.fail<HomeItem[]>(AppError.expected(1, 'empty data set', DOMAIN));  // 可预期失败
    }
    return Result.ok<HomeItem[]>(items);
  } catch (err) {
    return Result.fail<HomeItem[]>(ErrorMapper.from(err, DOMAIN, 'fetchItems'));       // 意外失败 → Result
  }
}
```

### 15.6 全局兜底与上报

```ts
// commons/AppCommon 的 AppBootstrap.prepare() 内部调用（各入口 Ability 不再直接调用）
GlobalErrorHandler.install();

// 接入崩溃/埋点平台（应用侧自己接）
GlobalErrorHandler.addReporter((error: AppError) => {
  // 上报 error.code / error.domain / error.level / error.toLog()
});
```

职责边界：`GlobalErrorHandler` 保证**一定有日志**、**一定有机会上报**、**EXPECTED 级别不上报**。

> 实测踩坑：`ErrorObserver` 类型**未通过 `@kit.AbilityKit` 导出**，直接 `import '@ohos.app.ability.ErrorObserver'` 会报模块无法解析。因此工程里用**结构化匹配的普通类**（具备 `onUnhandledException` / `onException` 两个方法）传给 `errorManager.on('error', ...)`。

### 15.7 日志规范

**级别语义（写的时候按这个判断）**：

| 级别 | 用在哪 | 例子 | 发布版 |
|---|---|---|---|
| DEBUG | 开发期细节：入参出参、状态流转 | `select id=3` | 默认裁剪 |
| INFO | 关键业务节点 | 页面进入/退出、流程开始/结束、配置生效 | 保留 |
| WARN | 可自动恢复、走了降级 | syscap 不可用走兜底、重试第 2 次 | 保留 |
| ERROR | 需人工介入的失败 | 接口失败、解析失败、状态非法 | 保留 |
| FATAL | 进程级致命 | 未捕获异常、数据损坏 | 保留 |

**四条硬性要求**：

1. **必须给 domain + tag**：`Logger.info('demo', 'DemoViewModel', 'loaded 4 items')`。没有 domain 的日志在线上等于没有。
2. **禁止业务代码直连 hilog**：否则无法统一裁剪、上报、脱敏。
3. **敏感信息必须脱敏**：手机号/邮箱/token/姓名过 `MaskUtil`；hilog 的 `%{public}s` 只放非敏感内容。
4. **禁止在循环体内打 DEBUG**：批量数据只打汇总（`loaded 4 items`），不要逐条打。

**结构化 + 可插拔**：

```ts
// 默认输出到 hilog；需要落盘或上报时追加 sink，业务代码零改动
Logger.addSink(new MemorySink());        // 本地诊断/单测
// Logger.setMinLevel(LogLevel.WARN);    // 发布版裁剪 DEBUG
```

**该打与不该打**：

| ✅ 该打 | ❌ 不该打 |
|---|---|
| 页面/能力生命周期节点 | 循环体内逐条数据 |
| 关键分支（走了降级、命中缓存） | 每帧/每次滑动 |
| 失败（带错误码与 domain） | 完整用户隐私数据 |
| 耗时（开始/结束配对） | 为了"方便调试"长期保留的临时日志 |

### 15.8 异常与日志的分工

一句话：**异常负责"传递与处理"，日志负责"留痕与归因"，两者不要互相替代。**

| 场景 | 谁负责 | 说明 |
|---|---|---|
| 可预期失败 | Result 返回给调用方 | 不产生异常日志 |
| 意外失败 | AppError 上抛 | 由**边界或全局兜底**记一次日志 |
| 需要人工介入 | ERROR 日志 + 上报 | 走 `GlobalErrorHandler.notify()` |
| 调试细节 | DEBUG 日志 | 发布版裁剪 |

### 15.9 健壮性检查清单

写任何"会失败"的代码前，逐条过：

- [ ] 入参是否用 `Assert` 校验了？（fail fast，别让非法值传播）
- [ ] 这个失败是 EXPECTED 还是 RECOVERABLE / FATAL？分类对吗？
- [ ] 调用系统 API / 网络前，是否先做了能力检测（`CapabilityManager.hasSysCap`）？
- [ ] 超时、重试、降级策略写了吗？（集中在 data 层，不要散落）
- [ ] 返回值是否可能为 undefined/null？空值语义是否显式处理？
- [ ] 异步是否都被 await 或 catch？有没有"发了不管"的 Promise？
- [ ] 状态非法（未初始化就调用）是否有明确报错，而不是静默返回？
- [ ] 失败路径是否都有日志，且带 domain + code？
- [ ] 是否有重复记录同一异常（层层 catch 各记一次）？
- [ ] 用户可见的失败是否有 UI 呈现（走 `StateContainer`）？

### 15.10 反例对照

| # | 反例 | 为什么错 | 正例 |
|---|---|---|---|
| 1 | `throw '加载失败'` | ArkTS 禁止 throw 任意类型；且无法归因 | `throw AppError.recoverable(100001, 'load failed', 'demo')` |
| 2 | `catch (e) {}` | 异常被吞，线上无从查起 | `catch (e) { return Result.fail(ErrorMapper.from(e, DOMAIN)); }` |
| 3 | 每层都 `catch` + `Logger.error` + 重新 throw | 同一异常被记 N 次，日志淹没 | 只在边界记一次，其余层直接上抛 |
| 4 | 无数据也 `throw` | 正常业务分支进了 ERROR 日志 | `Result.fail(AppError.expected(...))` |
| 5 | `Logger.info(TAG, 'msg')`（无 domain） | 日志无法按业务域检索 | `Logger.info(DOMAIN, TAG, 'msg')` |
| 6 | `Logger.info('user', 'login', \`phone=${phone}\`)` | 隐私泄漏到日志 | `MaskUtil.phone(phone)` 后再打 |
| 7 | 循环里逐条 `Logger.debug` | 日志量爆炸、拖慢主线程 | 循环外打汇总 |
| 8 | `if (version >= 15) { newApi() } else { oldApi() }` 散落在业务代码 | 版本判断逻辑散落 | 收敛进 `CompatManager.runByApi()` |
| 9 | 业务代码直接 `hilog.info(...)` | 绕过统一出口，无法裁剪/上报 | 一律走 `Logger` |
| 10 | `try { newApi() } catch { /* 忽略 */ }` 掩盖版本差异 | 真出错时静默失败 | 能力检测 + 显式降级分支 + WARN 日志 |

## 17. 共享库 vs 项目 Common

三段共享库（Foundation / Platform / VitalUI，住顶层 `quizzyjoy/`）回答"**换一个 app 还能用吗**"；项目 Common（AppCommon，住 `commons/`）回答"**这个 app 特有的决策是什么**"。v3.11 起两者物理分目录隔离，语义判据与修改权边界都不同（§12.3）。

### 17.1 判据表

| 问题 | 判断 | 落位 |
|---|---|---|
| 换一个 app，这段代码原样可用吗？ | 能 | 共享三库（Foundation / Platform / VitalUI） |
| 它封装的是系统能力，且与品牌、业务无关、跨应用通用？ | 是 | `Platform`（跨应用通用系统能力复用域） |
| 它连系统调用都不涉及（日志/异常/纯计算/数值）？ | 是 | `Foundation` |
| 它是纯 ArkUI 表现，可跨 app 复用？ | 是 | `VitalUI` |
| 它在本 app 内**跨 feature 复用**，但带本 app 设计语言/令牌约定，或不愿沉淀为组织资产？ | 是 | app 级组件库 **AppUI**（`@easystart/app-ui`，首个组件出现时创建，见 §17.4） |
| 它包含**本 app 的品牌语义**（名称、主题预设、文案）？ | 是 | 项目 Common 或 feature |
| 它是**多能力的编排决策**（启动链装什么、什么顺序）？ | 是 | 项目 Common（AppCommon） |
| 它只有某个业务域用？ | 是 | feature |

**fork 工程的第三类落位：应用级 Common 包（v3.11.1，EasyTools 实证）**。上表命中「共享三库」只说明语义归属，**不代表 fork 工程有权落位**——应用工程中 `quizzyjoy/` 只读（§12.3）：

- 本 app 需要、三库尚未提供的**非 UI 通用能力**（系统能力封装 / 通用工具）→ 建 `@<应用名>/common`（`commons/Common`，与 AppCommon 平级，可依赖三库复用 Logger / ErrorMapper）；EasyTools 已实证 17 类（安全随机 / 剪贴板 / 扫码 / 媒体选择 / OCR / 传感器 / 设备信息 / 权限申请器等）。
- **UI 组件**仍按 §17.4 三档：语义命中 VitalUI 但 fork 无权入库的，落应用级 AppComponent / AppUI。
- 单一 feature 的带业务语义能力 → 域内 `util/`（域内为主，摩斯双轨案例见 §12.3）。

### 17.2 为什么 AppBootstrap 不放共享库

启动装配本质是**项目决策**：装哪些能力、什么顺序、手表要不要 Toast——换个 app 答案就变了。放进共享库会把"可复用能力"和"本项目的选择"搅在一起，下一个项目只能复制粘贴再魔改。放项目 Common 则共享库保持纯净，新项目只需照判据表重写自己的装配层（AppCommon 本身也只有 ~70 行胶水）。

### 17.3 项目 Common 的纪律

1. **只做胶水，不造轮子**：能力实现一律调共享三库，AppCommon 里不直接调用系统能力（F14 同样适用；类型/稳定工具 import 放开——v3.8）。
2. **不依赖 VitalUI**：保证纯原生入口（手表）可复用同一装配链；表现层注入（Toast）由各入口 Ability 自行完成。
3. **生命周期严格配对**：`prepare ↔ destroy`、`attachWindow ↔ detachWindow`，与 Ability 回调一一对应，防监听泄漏。

### 17.4 AppCommon vs AppUI vs VitalUI（组件落位三档）

> **v3.4 落地标注**：AppUI 档已建成，实建名 **`commons/AppComponent`（@easystart/app-component）**——首批成员 AppSnackBar/AppDialog/AppSheet（反馈组件）+ Button/Text modifier 族（应用样式），分界判据与文件头落位注释见该包 Index.ets；参考 EasyMath modifier 模式但**分文件**（其 783 行单文件教训）。§17.4 预言名 AppUI 即此包，判据不变。

> **v3.15 追加标注（主题化原生控件工厂 control/）**：AppComponent 增 `control/` 族（AppToggle/AppSlider/AppProgress/AppCheckbox/AppRadio/AppSegment 共 7 组件），把 ArkUI 原生控件的选中/激活色统一绑 VitalUI `UiThemeManager.accentColor`，解决"自由页面裸用原生控件则运行时换肤不生效"。**落位判据**：它是"原生控件 + 本模板主题接线（读 UiThemeManager 单例、空串回退 qj_brand）"，带 VitalUI 主题约定、属 app 级组件，落 AppComponent 而非三库（三库保持原生组件纯净；fork 后同构复制）。**与 HDS 的分工**：设置页等系统范式页面用官方 HdsListItemCard 的 SuffixSwitch/SuffixSelect（系统色、不绑 accent，保原生感）；业务自由页面需要随强调色换肤的开关/滑杆/进度/勾选/单选/分段，用 control/ 工厂。**冷启动 accent 装配**："读"留 AppCommon（restoreAccentColor，不依赖 VitalUI 以保手表可用）、"注入"在 phone/pc/tv 三端 Ability onCreate（对照 CommonToast.attach 表现层装配范式），手表不接。

三共享库是**组织级公共库**（§12.3），因此组件准入的判据不是"谁在调用"，而是"**里面有没有装本 app 的东西、愿不愿意让它成为组织资产**"：

| 组件特征 | 去处 | 准入/创建条件 |
|---|---|---|
| 零语义纯表现，拷到**任何**新 app 不改一行能用，且愿意沉淀为组织资产 | **VitalUI** | 双判据：技术可移植 + 主观愿意；进库前参数化干净（语义经 props/闭包注入） |
| 本 app 内**跨 feature/跨页面**复用，但带本 app 痕迹（设计语言、令牌约定、交互习惯），或虽纯表现但不想沉淀给组织 | **AppUI**（`commons/AppUI`，`@easystart/app-ui`） | **首个真实跨 feature 组件出现时创建**，禁止提前建空模块（判据 §3-7） |
| 含业务语义，单业务域使用 | 该 feature | 出现第二个使用方时按上两行重新落位 |

**AppCommon 与 AppUI 的分工**：AppCommon 是**装配决策**（无 UI、不依赖 VitalUI、保手表瘦身路径）；AppUI 是 **app 级组件库**（可依赖 foundation+vitalui、被 features 消费、无手表约束——它不是入口的依赖项，不进入瘦身路径）。两者同属 `@easystart/*` 应用侧作用域，复制模板到新应用时都会被审视。

**创建 AppUI 的四步**（当且仅当首个合格组件出现）：① `commons/AppUI/` 按模块骨架创建（module name `AppUI`，type har）；② `oh-package.json5` name `@easystart/app-ui`，依赖 `@quizzyjoy/foundation` + `@quizzyjoy/vitalui`；③ 根 `build-profile.json5` 的 `modules` 追加；④ 需要的 feature 加 `file:` 依赖，组件经 `Index.ets` 导出（系统能力调用走 Platform，F14 同样适用）。

### 17.5 features 内公共层的拆分判据（v2.3.1，官方对标实证）

官方 features 层内预建三个公共 HAR：commonbusiness（跨 feature 业务组件/模型/VM，含 RouterParams、BaseHomeViewModel）、widgetcommon（卡片域）、abilitycommon（Ability 编排域：BaseAbilityHelper / FormAbilityHelper / Splash / InitCenter）。其 commonbusiness ≈ 本模板 AppUI 档 + 跨 feature 业务模型，印证 §17.4 三档判据；但官方选择「预建 + 按域分包」的激进路径，本模板维持**需求驱动**：

1. **首个跨 feature 共享的业务组件/模型出现** → 创建 `commons/AppUI`（§17.4 四步）；跨 feature 的纯业务模型（路由参数、列表基类 VM 等）同落此层
2. **卡片域或 Ability 编排域独立膨胀**（>10 文件且 ≥2 入口/feature 消费）→ 按域拆专用包（如 `features/WidgetCommon`），只依赖 commons，禁止依赖具体 feature
3. 禁止预建空包；features 内公共包一律 `@easystart/*` 应用作用域（§12.3），与 AppCommon/AppUI 同语义

依赖方向：features 内公共层仍属 features 层，遵守 `entry → features(含公共层) → commons（应用级）→ quizzyjoy（三库）`；公共层之间禁止互依赖（官方 widgetcommon/abilitycommon 分立印证）。

### 18.2 OpenHarmony 产品配置差异

```json5
// build-profile.json5 → app.products[]（product 级，非 app 级）
{
  "name": "default",
  "compatibleSdkVersion": "5.0.2(14)",   // 版本串映射以 DevEco SDK Manager 实际提供为准
```

- **SDK**：DevEco SDK Manager 另装 OpenHarmony SDK（与 HarmonyOS SDK 并存，工程切 product 时按 runtimeOS 取用）

- **分发**：无 AppGallery，按设备厂商通道（预置/hdc bm install/厂商商店）
