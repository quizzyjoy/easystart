## 一、颜色有四个来源

先看两张图。默认主题（品牌蓝）下的首页：

![默认主题下的首页：图标底、强调块都是品牌蓝](图片/B2-home-brandblue.png)

把它切成青碧，同一个页面：

![切到青碧后：品牌类全部转绿，危险色仍红、成功色仍绿](图片/A8-components-teal2.png)

对比之后你会发现，「变」和「不变」是成组的，而不是随机的：

| 你看到的位置 | 真正的来源 |
|---|---|
| 自己画的色块、图标底、按钮 | 你写的那行代码（令牌或字面量） |
| 用了 `AttributeModifier` 的样式 | modifier 类里那一刻读到的值 |
| 明确接入了运行时主题的组件 | 全局单例里的当前色 |
| 没有显式着色的系统控件 | ArkUI 全局主题表 |

**这四者不是"四个优先级"，而是四支不同的笔。** 哪支没换墨，那个位置就不会变，跟其它三支写得多好无关。

我最初就是把它们当成一件事：以为"设了主题色，全站自然跟着变"。实际上第三、第四支需要你主动去接。

判断口诀只有一句：**看到一块没变的像素，先问「这块是谁画的」。**

## 二、第一层：静态令牌，哪些该留、哪些要搬

最朴素的着色是资源令牌：

```ts
Text('标题').fontColor($r('app.color.qj_brand'))
```

好处是编译期就固化，深浅色还能靠 `resources/dark` 自动切；坏处也正是固化——运行时改主题，它纹丝不动。

所以第一件事是给工程里的品牌色引用分类。我用的标准就三条：

| 类型 | 处理 | 理由 |
|---|---|---|
| 页面品牌装饰色（图标底、强调块、选中态） | **搬走**，改读运行时色 | 它本来就该跟主题走 |
| 语义色（危险红、成功绿、警告黄） | **留着** | 危险就是危险，不该因换肤变绿 |
| 令牌对照页、设计规范演示 | **留着** | 这页的职责就是展示令牌，改了就没意义 |

一个容易忽略的点：**同一个色值可能既出现在该搬的位置，也出现在该留的位置**。所以别一键全局替换，先按语义过一遍。

## 三、第二层：样式函数拿不到新颜色怎么办

有些外观是复用的，比如「主按钮」的一整套样式。`AttributeModifier` 很适合：写一次，到处 `attributeModifier(new XxxModifier())`。

但它有个硬限制：

```ts
class XxxModifier implements AttributeModifier<ButtonAttribute> {
  applyNormalAttribute(instance: ButtonAttribute): void {
    instance.backgroundColor(???);   // 这里读什么？
  }
}
```

`AttributeModifier` 是**普通类**，不在组件的观察图里。你在里面读全局单例的 `@Trace` 字段，变化不会触发任何重渲染——因为没有组件"观察"了它。

我第一次遇到时以为是响应式坏了，查了很久才想通。

**解法：把最新色存进一个普通静态字段，等页面重建时再读一次。**

```ts
export class ThemeBridge {
  private static accent: string = '';        // 铺层时写入

  static brand(): ResourceColor {
    return ThemeBridge.accent.length > 0
      ? ThemeBridge.accent : $r('app.color.qj_brand');
  }
}
```

```ts
// modifier 里
instance.backgroundColor(ThemeBridge.brand())
```

代价要说清楚：**切主题后，屏幕上的 modifier 样式不会立刻变**，要等页面重建（返回再进、或系统重绘）才更新。

我接受这个代价，因为 modifier 一般用在结构性、不常变的样式上。如果某处必须即时跟随，**别用 modifier**，改成读 `@Local theme` 的自绘组件——这是唯一干净的路径。

## 四、第三层：一个能自动刷新的单例

这是整套方案的核心：用 `@ObservedV2` 单例存当前主题状态，组件读它就能当帧响应。

```ts
@ObservedV2
export class UiThemeManager {
  private static instance: UiThemeManager | undefined = undefined;

  @Trace presetId: string = DEFAULT_PRESET;   // 当前主题包
  @Trace accentColor: string = '';            // 强调色覆盖

  private constructor() {}

  static getInstance(): UiThemeManager {
    if (UiThemeManager.instance === undefined) {
      UiThemeManager.instance = new UiThemeManager();
    }
    return UiThemeManager.instance;
  }
}
```

三个关键点：

- `@ObservedV2` 是**类级**装饰器（不是 V1 的 `@Observed`），让字段可被观察；
- `@Trace` 标在字段上，表示"它变了要通知读过我的组件"；
- 构造器私有，全应用只有一份。

组件侧一行接入：

```ts
@Local theme: UiThemeManager = UiThemeManager.getInstance();
```

`@Local` 在这里不是复制数据，而是**建立依赖**：组件从此订阅了这两个字段，字段一变，读过它的地方当帧重渲染。

接好之后的效果是这样——外观页的预览区跟着变，页面里凡是接了单例的组件同时变：

![切到青碧后：取色块显示 #12A594，预览按钮同步变绿](图片/A5-teal-applied.png)

### 主题包和强调色是叠加，不是二选一

我最初把两者做成互斥（选了主题包就清强调色），结果用户切包时抱怨"我设的颜色没了"。这个反馈是对的，模型错了。

正确的是两层叠加：

```
最终色 = 强调色（有就用）→ 否则主题包基准色 → 否则静态令牌
```

```ts
brandColor(): ResourceColor {
  if (this.accentColor.length > 0) { return this.accentColor; }
  if (this.presetId === DEFAULT_PRESET) { return $r('app.color.qj_brand'); }
  return resolvePreset(this.presetId).baseHex;
}
```

注意默认主题包这一支**特意回退到 `$r` 令牌**，而不是硬编码同一个 hex——这样深浅色仍由 `resources/dark` 负责，两套机制不打架。

### 另外三个取色方法

用下来光有品牌色不够，我又补了三个：

| 方法 | 用途 | 实现要点 |
|---|---|---|
| `effectiveAccent()` | 拿当前生效的 hex 字符串 | 传给取色器、存偏好、打日志 |
| `onBrandColor()` | 品牌底上该用什么字 | 按感知亮度 `0.299R+0.587G+0.114B > 0.62` 选深或浅 |
| `brandSoftColor()` | chip 底、选中底这类柔和层 | 默认包回退浅令牌；自定义色用 15% 透明度 |

`onBrandColor()` 是最值的一个：没有它，用户把主题调成浅黄时，白字直接看不见。

主题包我一共做了五套，每套**只声明一个基准色**，其余 token 由算法派生：

```ts
new Preset('brand',    '品牌蓝', '#0A59F7'),   // 默认，与令牌同值
new Preset('teal',     '青碧',   '#12A594'),
new Preset('violet',   '靛紫',   '#6c4de8'),
new Preset('pink',     '桃粉',   '#D6409F'),
new Preset('contrast', '高对比', '#0A0A0A'),
```

外观页上它们排成一行，选中态用该主题色描边：

![五套主题包 chips，选中青碧，下面显示当前生效色 #12A594](图片/B1-presets-5.png)

五套 × 七个 token 若都手写就是 35 个值，维护成本立刻爆炸。**派生优于枚举。**

### 为什么不用 `AppStorage`

它能存全局状态，看起来更"官方"。不选它是因为我要求组件库保持**零 `@kit`**：`@ObservedV2` + `@Trace` 是纯 ArkTS 语言特性，`AppStorage` 属于 ArkUI 设施。组件库一旦 import kit，就不能原样搬到别的工程。

顺带好处是**字段级观测**：只有读了该字段的组件重渲染，而不是一改全树抖。

## 五、第四层：把系统组件的默认色也接管

前三层管的是"自己画的"。还有一类位置我们没画——原生控件、系统弹窗、滚动条，它们的默认色来自 ArkUI 全局主题表。

官方给了入口：

```ts
import { ThemeControl, CustomTheme } from '@kit.ArkUI';

ThemeControl.setDefaultTheme({
  colors: { brand: '#12A594' /* ... */ },
  darkColors: { brand: '#4FC3B5' /* ... */ }
} as CustomTheme);
```

我最后接了七个 token，够覆盖"看起来不对劲"的位置：

```ts
brand, fontEmphasize, iconEmphasize, backgroundEmphasize,
compEmphasizeSecondary, compEmphasizeTertiary, interactiveSelect
```

### 必须成对给 `darkColors`

这是我最想提醒的一条。只给 `colors` 的话，深色模式会继续用浅色那套——**亮底亮字**，看着像 bug，其实是漏了一对。

而且两者不能简单复制。我的做法是深色版把品牌色提亮一点（混 28% 白），柔和层再压暗，观感才对得上：

```
浅色：brand = 基准色；柔和层 = 基准色混 28% 黑
深色：brand = 基准色混 28% 白；柔和层 = 再混 82% 黑
```

两个实现细节：`setDefaultTheme` 要在 ArkUI 起来之后调（`loadContent` 回调里），并且**包 try/catch**——它失败不该让应用起不来，前三层还能用。

L4 生效后，连系统弹窗里的主按钮也会变成主题色：

![统一对话框：确认按钮跟着变成青碧主按钮](图片/A9-dialog-teal.png)

## 六、串起来：一次铺满，还要能冷启动恢复

### 一个方法铺两层

```ts
export class AppThemeApplier {
  private static currentAccent: string = '';

  static brandColor(): ResourceColor {                 // 给无状态样式用
    return AppThemeApplier.currentAccent.length > 0
      ? AppThemeApplier.currentAccent : $r('app.color.qj_brand');
  }

  static apply(presetId: string, accentHex: string): void {
    const theme: UiThemeManager = UiThemeManager.getInstance();
    theme.setPresetId(presetId);                              // 1. 先 L3
    theme.setAccentColor(accentHex);
    AppThemeApplier.currentAccent = theme.effectiveAccent();  // 2. 静态中转
    AppThemeController.applyPreset(theme.presetId, theme.accentColor);  // 3. 后 L4
  }
}
```

顺序有讲究：**必须先把单例写好、再算 `effectiveAccent()`**。反过来的话算到的是上一套颜色，L4 就被铺成旧主题。

`setDefaultTheme` 是幂等的（同色短路），所以这个方法可以放心重复调。

### 冷启动：只读，别急着注入

从偏好恢复主题时，我一开始让启动封装直接去调主题单例。结果那个封装立刻不能复用了——有些入口（比如手表）根本不需要 UI 主题。

改成分两步，问题消失：

```ts
// 启动封装：只读，返回纯数据
static async restoreTheme(): Promise<AppThemeState> { /* 读偏好 */ }

// 每个入口 Ability：自己注入
AppBootstrap.restoreTheme().then((state: AppThemeState): void => {
  AppThemeApplier.apply(state.presetId, state.accentHex);
});
```

铺完之后，整个窗口（包括宽屏分栏的左右两侧）应该是一套色：

![同一窗口切到青碧后：列表、内容、按钮是同一种绿](图片/D5-2in1-teal2.png)

后来我又在外观页的 `aboutToAppear()` 里补了一次幂等的 `apply()`。听着重复，其实是**防御式设计**：万一某个入口漏调，用户进一次外观页就补齐了。这比"保证每处都调对"更抗遗漏——漏掉的那种 bug，往往只在特定路径复现。

## 七、四个最值得记住的坑

我一共踩了八九个，但真正费时间的只有四个，其余都是这三类的变种。

### 坑 1：切主题包「没反应」，只换了个选中框

**现象。** 从「靛紫」切到「青碧」，选中框变了、预览色块也变了，页面颜色一动不动。

**原因。** 我的 `setAccentColor` 长这样：

```ts
if (lower.length === 7 && lower.startsWith('#')) { this.accentColor = lower; }
```

只接受 7 位 hex。而"切包时清掉强调色覆盖"要传空串——空串被这行直接忽略，上一套的强调色还在，它优先级更高，把新主题包盖住了。

![这个界面正是"强调色盖住主题包"的状态：色块显示的是强调色，不是主题包基准色](图片/A1-appearance.png)

**改法。** 把空串定义成第三种语义（"清除覆盖"），而不是非法输入：

```ts
setAccentColor(color: string): void {
  const lower: string = color.trim().toLowerCase();
  if (lower.length === 0) { this.accentColor = ''; return; }
  if (lower.length === 7 && lower.startsWith('#')) { this.accentColor = lower; }
}
```

切包时内存和落库一起清，否则重启后旧强调色又回来。

**教训。** 凡是"一个值存在未设置状态"的地方，设计 API 时就要把它做成一等公民。别指望 UI 层补救——UI 层补不了语义。

### 坑 2：只改单例，自绘按钮还是蓝

**现象。** 单例建好了，页面装饰色都跟着变了，但我自己的按钮、标签还是默认品牌蓝。

**原因。** 组件里写的是 `$r('app.color.qj_brand')`——它不认识单例。"跟随主题"只能靠调用方传参，而绝大多数调用方不会传。

**改法。** 让组件自己持有单例，同时保留外部覆盖的口子：

```ts
@Local theme: UiThemeManager = UiThemeManager.getInstance();   // 建立观察
@Param accentColor: string = '';                                // 允许覆盖

private accent(): ResourceColor {
  return this.accentColor.length > 0 ? this.accentColor : this.theme.brandColor();
}
```

为什么两个都留？只靠传参必然大量漏传（"注入面覆盖了"和"界面显示正确"是两件事）；只靠单例，就失去"某处特调成别的色"的能力。

**教训。** 「我改了全局状态」和「每个组件都读到了」之间隔着一次接线，接线得逐个做。

### 坑 3：读到了单例，却还是不响应

两种表现，根因是同一件事：**读单例的时机，不在组件的观察范围里。**

**表现 A：写在 `@Param` 默认值里。**

```ts
@Param accentColor: string = UiThemeManager.getInstance().effectiveAccent();  // ❌
```

默认值只在构造那一刻求值一次，之后单例怎么变它都不重算。改成 `@Local`，或写成方法在 `build()` 里调用。

**表现 B：写在顶层 `@Builder` 里。** 全局浮层常用顶层 `@Builder`，它既没有 `this`，也不在组件上下文里：

```ts
@Builder
function floatingBall(content: BallContent) {
  .backgroundColor(UiThemeManager.getInstance().brandColor())   // ❌ 编译不过 / 不响应
}
```

正解是**在调用侧读，把结果塞进内容对象**：

```ts
class BallContent {
  tint: ResourceColor = $r('app.color.qj_brand');
}

// 调用侧
const theme: UiThemeManager = UiThemeManager.getInstance();
content.tint = theme.brandColor();
```

**教训。** 响应式的本质是"读的时候登记依赖"。凡是求值时机不在渲染路径上的地方（默认值、顶层函数、无状态类），都得换成"调用侧读、传进去"。

### 坑 4：暗色模式下亮底亮字

**现象。** 浅色一切正常；切到深色后底色还是亮的、字也还是亮的，糊成一片。

**原因。** 只给了 `colors`，没给 `darkColors`。系统在深色模式拿不到对应值，就继续用浅色那套。

**改法。** 成对提供，深色用"提亮 + 压暗"重新算一遍（规则见第五节）。

**教训。** 任何颜色配置都要问一句：**深色模式呢？** 只写一半的配色，在白天的测试里几乎发现不了。

## 八、速查与自查

### 按症状定位

| 现象 | 大概率是 | 看哪节 |
|---|---|---|
| 切了主题包颜色没动，选中框却变了 | 强调色覆盖没清（空串被忽略） | 坑 1 |
| 页面装饰色变了，按钮/标签没变 | 组件读令牌，没读单例 | 坑 2 |
| 组件读了单例，还是不响应 | 求值时机不对（默认值 / 顶层 Builder） | 坑 3 |
| 深色模式下糊成一片 | 只给了 `colors`，漏了 `darkColors` | 坑 4 |
| 切主题后要退出页面再进才对 | 用了 modifier（无状态样式） | 第三节 |
| 某些原生控件颜色不变 | L4 没接 | 第五节 |

### 常用 API

| 方法 | 返回 | 什么时候用 |
|---|---|---|
| `effectiveAccent()` | `string`（hex） | 传给取色器、存偏好、打日志 |
| `brandColor()` | `ResourceColor` | 组件取品牌色（默认包回退令牌） |
| `onBrandColor()` | `ResourceColor` | 品牌底上的前景色 |
| `brandSoftColor()` | `ResourceColor` | chip 底、选中底 |
| `setAccentColor('')` | `void` | 清除强调色覆盖 |
| `setPresetId(id)` | `void` | 切主题包 |
| `reset()` | `void` | 强调色 + 主题包一起回默认 |

### 落地清单

- [ ] 1. 建 `@ObservedV2` 单例，两个 `@Trace` 字段
- [ ] 2. 给自绘组件加 `@Local theme` + `@Param accentColor`
- [ ] 3. 给无状态 modifier 加静态中转
- [ ] 4. 写 `buildTheme()`，`colors` 与 `darkColors` **成对**
- [ ] 5. 铺层器：先单例、再静态中转、最后 L4
- [ ] 6. 冷启动只读不注入（返回纯数据），注入留给入口
- [ ] 7. 外观页：chips + 取色器 + 切包清强调色
