## 这套教程解决什么问题

大多数鸿蒙应用的「换肤」最终都长这样：设置页改完颜色，回到首页——卡片图标还是蓝的、对话框按钮还是蓝的、设置页开关还是蓝的。开发者以为是自己漏改了某处，于是开始全仓搜索品牌色常量，越改越乱。

根因不是「漏改」，而是**颜色有四个互相独立的来源**，只动其中一个，必然只变一部分：

| 层 | 机制 | 谁在决定颜色 | 只改这一层时的表现 |
|---|---|---|---|
| **L1 静态令牌** | `$r('app.color.qj_*')` + `resources/dark` 限定词 | 资源编译器（编译期固化） | 只随深浅色变，不随主题变 |
| **L2 AttributeModifier** | `AttributeModifier` 族（无状态类） | 类里写死的值 | 完全不参与运行时换色 |
| **L3 运行时主题** | `UiThemeManager`（`@ObservedV2` 单例 + `@Trace`） | 运行时单例 | 只有「接了注入口」的组件会变 |
| **L4 系统组件默认色** | `ThemeControl.setDefaultTheme(CustomTheme)` | ArkUI 全局 token 表 | 不设则系统组件永远是系统蓝 |

本教程的主线就是把这四层**依次建起来、按正确顺序编排、用真机截图逐层取证**，最后把 9 个实测踩过的坑写成「问题 → 现象 → 正解」。

## 第 1 章 换肤只变一半的真相：四层颜色模型


### 本章要解决的问题

**为什么我在设置页改完颜色，回首页时「一部分变了、一部分没变」？**

这一章不写代码，只解决一个认知问题：把「颜色」拆成四个互不重叠的来源，让你在遇到「没变」时能立刻判断是哪一层没接上，而不是全仓搜索色值。

### 读者收获

1. 能用四层模型给任意一处「没跟着变」的颜色**归位**；
2. 知道为什么不存在「一个大 token 表解决一切」的方案；
3. 能看懂本仓 `theme/` 目录为什么要分「Foundation / Platform / VitalUI / AppComponent」四层放置（第 7 章展开）。

---

### 正文要点

#### 1.1 现象：一次改色，四种结果

设置页把品牌色改成青碧（`#12A594`），然后逐页检查，你会同时看到四种结果：

| 观察点 | 结果 | 说明 |
|---|---|---|
| 首页卡片图标底 | **变了** | 走运行时主题单例 |
| 首页大标题 / 正文 | **没变**（本来就该不变） | 文本色属于语义层，不跟品牌色 |
| 空态插画圆底、卡片强调块 | **变了** | 同上（运行时） |
| 统一对话框「确认」按钮 | **变了**（`A9-dialog-teal.png`） | 系统组件默认色被覆盖 |
| 组件示例页的按钮 / 标签 / Toast | **变了**（`A8-components-teal2.png`） | 自绘原语读了注入色 |
| 设置页 HDS 行卡片底色 / 分割线 / chevron | **没变**（`C2-hds-teal.png`） | HDS 私有 token，不吃系统主题（第 11 章） |
| ArkTS 卡片（桌面卡片） | **没变** | 卡片框架只有 V1，接不上 V2 单例（第 10 章） |

**同一屏里并存「变」与「不变」，这就是「只变一半」的观感来源。**

#### 1.2 为什么会这样：颜色有四个来源，且互不覆盖

把「某个像素最终是什么颜色」拆开，会落到四个不同的决策点：

**L1 静态令牌** —— `$r('app.color.qj_brand')`。值在**编译期**由资源限定词（`base` / `dark`）决定。它天然支持深浅色，但**永远不知道你在设置页点了什么**。它的权限边界是「编译期常量」。

**L2 AttributeModifier** —— `class AppXxxModifier implements AttributeModifier<XxxAttribute>`。它是**普通类实例**，不在 ArkUI 的观察依赖图里。它在 `applyNormalAttribute` 里写下什么，就是什么；改主题不会让它重跑，除非页面重建、重新 `new` 一个实例。

**L3 运行时主题** —— `UiThemeManager`（`@ObservedV2` 单例，字段带 `@Trace`）。只有**读了它**的组件才会在它变化时重渲染。这是一种「白名单式」生效：没读的组件保持原样。

**L4 系统组件默认色** —— `ThemeControl.setDefaultTheme(CustomTheme)`。它写的是 ArkUI 内部的 **token 表**，管的是「你没有显式指定颜色」的那些系统组件（对话框按钮、开关选中、填充按钮底色…）。它粒度粗、覆盖广，但对**显式 set 过颜色的属性无效**，对 HDS 私有 token 也无效。

一句话概括四层的权限边界：

> **L1 管编译期、L2 管样式封装、L3 管自绘组件的即时响应、L4 管系统组件的兜底默认。**

四者不互相替代，因为它们管的是**不同的对象**，而不是同一对象的不同优先级。

#### 1.3 为什么不能「合并成一个大 token 表」

一个常见的直觉是：把所有颜色都定义成 `app.color.brand`，改主题时改这个资源值——不就全变了吗？

这条路在 HarmonyOS 上走不通，原因有三条（均可验证）：

1. **资源值在编译期固化**，运行期没有「改 `$r` 指向的值」的公开 API；
2. 想模拟这个效果，只能让每处引用都变成「变量」（即 L3 的单例读取），那就等于把 L1 全量迁移到 L3，代价是全仓改动 + 每处都要有观察上下文；
3. 即便全量迁移，**系统组件与 HDS 组件仍不归你管**（它们读自己的 token），L4 依然不可省。

所以正确姿势不是「合并」，而是**分层 + 编排**：L4 兜底系统组件，L3 管自绘组件的即时性，L2 保留个别特调能力，L1 负责语义色与深浅色。

#### 1.4 四层与「深浅色」是正交的两件事

初学者最容易混的一点：

- **深浅色**（`ColorModeManager` → 系统 `ColorMode`）决定「底色是白还是黑」；
- **主题/换肤**（本教程的四层）决定「品牌色是什么」。

`A1-appearance.png` 与 `B1-presets-5.png` 是同一页的两种状态：前者主题包是品牌紫、取色块 `#6c4de8`；后者是青碧、取色块 `#12A594`。而两图右上角「显示模式：跟随系统」都没变——**换主题不动显示模式，换显示模式不动主题**。

这条正交性带来一个必然要求：L4 的 `CustomTheme` 必须**同时**提供 `colors` 与 `darkColors`。只给 `colors`，暗色模式下就会「亮底亮字」（第 10 章详解）。

#### 1.5 本仓怎么把四层放进工程结构

四层不是四个文件，而是**四个不同层次的模块**，这是被依赖规则逼出来的：

```
quizzyjoy/Foundation   ← 纯数据：5 套主题包（零 @kit）
quizzyjoy/Platform     ← @kit 触点收口：AppThemeController（ThemeControl 在这里）
quizzyjoy/VitalUI      ← 零 @kit 的原语库：UiThemeManager 单例 + CommonButton 等
commons/AppComponent   ← 同时依赖 VitalUI + Platform：AppThemeApplier 编排
commons/AppCommon      ← 只读偏好：AppBootstrap.restoreTheme（刻意不依赖 VitalUI）
product/entry*         ← 入口 Ability：调一次 AppThemeApplier.apply
```

关键约束：**VitalUI 不能依赖 Platform**（原语库要保持零 `@kit`），**AppCommon 不能依赖 VitalUI**（手表端要能用）。正是这两条约束，导致「编排」只能落在 `AppComponent`，「读偏好」与「注入表现层」必须拆开——这条设计因果链在第 7 章会完整复盘，它解释了为什么恢复主题要写成 `restoreTheme()` 读 + `apply()` 注入两段。

#### 1.6 用这张图判断「谁该修」

遇到「某处颜色没跟着变」时，按顺序自问：

1. 这个颜色是**语义色**（危险/成功/警告）吗？→ 是则**不该变**，收工。
2. 它是**系统组件**（Dialog / Toggle 轨道 / 填充 Button / SnackBar 动作）吗？→ 查 L4（第 6 章）。
3. 它是 **HDS 组件**（`HdsListItemCard` / `HdsTabs` 等）吗？→ L4 未必够，查 HDS 显式传色（第 11 章）。
4. 它是**自绘组件**读的色吗？→ 查它有没有读 `UiThemeManager`（L3，第 5 章）。
5. 它由 **AttributeModifier** 决定吗？→ 查静态中转值（L2，第 4 章）。
6. 以上都不是？→ 它大概率是 L1 硬编码，需要分级（第 3 章）。

## 第 2 章 全仓取证：把「注入面」量出来


### 本章要解决的问题

**在动手改任何一行颜色代码之前，怎么知道「到底有多少地方不在主题体系里」？**

凭直觉改会陷入两种失败：改了几十个文件仍然有漏网之鱼；或者把该保留的演示色也改掉了。本章给一套可复现的取证流程，产出三个数字和一个清单，作为整个改造的基线。

### 读者收获

1. 一套「递归计数而非抽样」的取证命令；
2. 能把颜色引用分成「必须跟主题 / 必须不跟主题 / 待定」三类；
3. 学会识别**注释与实现漂移**——它比代码 bug 更容易让人做错决策。

---

### 正文要点

#### 2.1 先取证，再改码：为什么顺序不能反

改造前，本仓的一次全仓取证给出了四个数字（2026-10-20 实测，改造前基线）：

| 指标 | 数值 | 含义 |
|---|---|---|
| `qj_brand` 硬引用 | **92 处 / 48 个文件** | 这些地方**不会**随运行时主题变 |
| 会读 `UiThemeManager` 的「注入面」 | **21 个文件**（13 个 AppComponent 控件工厂 + 5 个 VitalUI 原语 + 3 个入口/预览） | 只有这些会变 |
| `AttributeModifier` 使用点 | **34 处** | 全部写死令牌，**完全不参与**换色 |
| `ThemeControl.setDefaultTheme` 调用 | **0 处** | L4 层完全空缺 |

**结论直接决定了改造顺序**：不是「找出漏掉的两三处」，而是「92 处里绝大多数根本不在体系内」。这解释了「换肤只有个别页面有反应」的观感，也说明**先建 L4、再分级处理 92 处**才是正确路径。

> 注意：以上是**改造前**基线。v3.44 之后这些数字已变化；教程保留它们是因为「改造前有多糟」决定了「改造要分几步」。

#### 2.2 取证方法：递归计数，不要抽样

关键纪律：**用递归枚举全量文件，再逐文件匹配**，不要用抽查或只看 `features/`。本仓踩过这个坑——只看业务模块会漏掉 `commons/` 与 `product/` 里的重复实现。

可复现的口径（PowerShell，等价于任意 shell 的 `grep -r`）：

```
### ① 全量文件枚举（排除依赖与构建产物）
Get-ChildItem hm_easystart -Recurse -Include *.ets |
  Where-Object { $_.FullName -notmatch 'oh_modules|build\\' }

### ② 按 token 统计「文件数」与「处数」两个口径
... | Select-String -Pattern "qj_brand" -List   # 文件数
... | Select-String -Pattern "qj_brand"         # 处数
```

**必须同时报告「处数」和「文件数」**：处数说明工作量，文件数说明影响面。92 处集中在 48 个文件，意味着平均每文件不到 2 处——这种分布适合「按文件分级」，不适合「统一批量替换」。

#### 2.3 三个口径交叉验证：别只信一种 grep

单一 grep 会漏三类引用，必须交叉验证：

1. **`$r` 引用**：`qj_brand`（资源名）；
2. **十六进制字面量**：`'#0A59F7'` 之类直接写死的色值（本仓在 modifier 与部分自绘处存在）；
3. **系统色**：`$r('sys.color.*')`——这类**不吃 L1 也不吃 L3**，只能靠 L4 或显式传色。

第 3 类最隐蔽：它看起来「不是品牌色」，所以不会被搜 `qj_brand` 命中，但它在视觉上就是「本该跟主题却始终是系统蓝」的那部分。

#### 2.4 分级：把 92 处变成三张清单

取证的目的不是「全部改掉」，而是**分级**。本仓实际采用的三分法：

| 类别 | 判定标准 | 处置 | 例子 |
|---|---|---|---|
| **A. 品牌主体** | 视觉上是「品牌强调」，换肤后应当跟着变 | 改读 `theme.brandColor()` / 注入 | 首页图标 chip 底、场景页强调块、加载动画 |
| **B. 演示/对照** | 它展示的**就是令牌本身** | **保持 `$r` 写死** | `DesignTokensView`、`ComponentGalleryView` 的令牌对照区 |
| **C. 语义色** | 表达「危险/成功/警告/中性」 | **永远不跟主题** | 删除按钮红、成功勾绿、警示黄 |

B 和 C 是两类**必须拒绝改造**的地方。这一点常被误解为「改造不彻底」——恰恰相反，把令牌对照页也改成主题色，会让「这张表丧失了它存在的意义」。第 3 章会把这条判定写成可执行规则。

#### 2.5 第四类断点：页面裸用原生控件

取证时还要查一个反模式：**页面直接 `Toggle()` / `Slider()` / `Checkbox()`，不经过 `App*` 控件工厂**。

原生控件默认读 `sys.color.*`，与品牌色无关；一旦裸用，就等于绕开了所有注入口。本仓的纪律是「一律用工厂，需要原生必须在注释里写原因」。

> 注意一个被文档误导过的判断：曾有设计文档写「原生控件的选中色**不随**运行时强调色变化」，据此认为原生控件不可用。实测结论相反——原生控件可以通过 `.selectedColor()` / `.trackColor()` 等**逐点覆盖**，控件工厂正是这么做的（第 8 章）。所以问题不是「原生控件不可能跟随」，而是「必须经工厂」。

#### 2.6 注释漂移：比 bug 更容易误导决策

取证时顺手核对了注释与实现的一致性，发现两处真实漂移（保留在源码中，作为教材）：

| 位置 | 注释说 | 实现是 |
|---|---|---|
| `AppThemePreset.ets` 的 `appThemePresets()` 上方 | 「内置主题包（**4 套**：品牌紫 / 青碧 / 桃粉 / 高对比）」 | 实际返回 **5 套**（品牌蓝 / 靛紫 / 青碧 / 桃粉 / 高对比） |

## 第 3 章 L1 静态令牌：哪些该跟主题，哪些永远不跟


### 本章要解决的问题

**92 处硬编码，哪些必须改、哪些必须留着？**

这一章把第 2 章的分级结论变成可执行规则，并给出一个反直觉但正确的判断：**在换肤系统里，「不跟主题」的地方和「跟主题」的地方一样重要**。

### 读者收获

1. 三条判定规则（A/B/C 三类），能对任意一处颜色引用当场定级；
2. 理解「默认主题包回退 `$r`」这个设计为什么保住了深浅色；
3. 知道为什么令牌对照页保留 `$r` 不是妥协而是正解。

---

### 正文要点

#### 3.1 令牌层能做什么、不能做什么

`$r('app.color.qj_brand')` 这类资源引用的能力边界非常清晰：

| 能 | 不能 |
|---|---|
| 随 `resources/dark/` 限定词自动切换深浅色 | 随「用户在设置页改的颜色」变化 |
| 编译期校验（名字写错立刻报错） | 运行期改指向的值（无公开 API） |
| 零运行时开销、可被系统主题材质对齐 | 表达「一套主题包」的多色关系 |

所以 L1 的正确定位是：**承载「不随换肤变、但要随深浅色变」的那部分颜色**，以及**必须精确控制、不接受任何覆盖**的那部分（语义色、演示对照）。

#### 3.2 规则一：品牌主体 → 改读运行时

判定：**这个颜色的语义是「品牌强调」，且换肤后应当跟着变**。

典型：首页大卡的图标 chip 底、场景页强调块、选中态底、加载动画的主色。

改法不是「删掉 `$r` 换 hex」，而是**改读取源**：页面装饰色改读 `theme.brandColor()` / `theme.brandSoftColor()`（第 5 章）。这样它同时获得了两件事：随主题变、且默认主题包时仍回退令牌（深浅色照常工作）。

#### 3.3 规则二：演示/对照 → 保持 `$r` 写死

判定：**这个颜色展示的对象就是令牌本身**。

典型：`DesignTokensView`（令牌总览）、`ComponentGalleryView` 里的「令牌对照」区块。

这条规则容易被当成「没改干净」。反过来想：令牌总览页的功能是「让我看到 `qj_brand` 到底长什么样」。如果它跟着主题变，那它就变成了「当前主题色的自拍」——**功能被破坏**。

同理，第 10 章的 ArkTS 卡片保留 `$r` 也属于这一类：卡片框架只支持 V1（`@Entry` / `@Component` / `@LocalStorageProp`），接不上 V2 的 `@Local` 单例。在「卡片必须显示、主题色拿不到」的约束下，保留令牌是唯一正确解——它至少保证深浅色正确。

#### 3.4 规则三：语义色 → 永远不跟主题

判定：**这个颜色表达的是「状态」，不是「品牌」**。

典型：危险（删除/错误）、成功、警告、中性灰。

语义色跟主题走会产生真实事故：切换到「高对比」主题包（`#0A0A0A`）时，若危险红被主题色覆盖，用户就**看不出这是危险操作**。

本仓的实现纪律是：语义色一律 `$r`，且不进入任何注入面。`A8-components-teal2.png` 里可以验证——「危险」按钮仍是红、「成功」标签仍是绿，只有品牌类（主操作/次操作/加载中/品牌标签）转成青碧。

#### 3.5 一个关键设计：默认主题包回退 `$r`

`UiThemeManager.brandColor()` 里有一段看起来「多此一举」的判断：

```
若 无强调色 且 presetId === 默认主题包 → 返回 $r('app.color.qj_brand')
否则 → 返回具体 hex
```

为什么不让它永远返回 hex？因为**默认主题包必须保住深浅色**。默认主题包（品牌蓝 `#0A59F7`）在暗色模式下需要一个提亮版本，而提亮逻辑由 `resources/dark/element/color.json` 的限定词承担。如果这里返回写死的 `#0A59F7`，暗色下就会得到「暗底 + 偏暗蓝」，观感发闷。

代码注释把这条动机写得很清楚：「非默认主题包必须给具体色，否则换包对这类组件完全无效」。两句话合起来就是完整的取舍：

> **默认包走令牌（要深浅色）；非默认包走 hex（要换肤生效）。**

#### 3.6 由此带来的已知偏差（要敢于承认）

这条取舍有一个必然的副作用：**非默认主题包在暗色模式下，自绘品牌色不会自动提亮**——因为它返回的是同一个 hex，没有走 `dark` 限定词。

系统组件层不受影响（L4 的 `darkColors` 会提亮，第 6 章），但自绘层会与系统层出现轻微明度差。这是**已知偏差**，不是 bug；处理方式有两种：

1. 接受它（自绘品牌色用在中低面积，明度差可容忍）；
2. 在 L3 里补一层「按当前色彩模式选择 hex」的逻辑（会引入对 `ColorModeManager` 的依赖，破坏 VitalUI 的零 `@kit` 纪律）。

本仓选择方案 1，并在第 13 章的验收清单里把它列为「可接受偏差」。

#### 3.7 主题包数据结构：为什么只声明一个色

`AppThemePreset` 只有三个字段：`id` / `label` / `baseHex`。

**一套主题包 = 一个品牌色**，其余层（强调底 / 描边 / 选中态）由 `AppThemeController` 按比例派生（第 6 章）。这个设计换来两个好处：

- 新增一套主题 = 加一行数据（`#RRGGBB`），不需要手写几十个 token；
- 派生规则唯一，不会出现「A 主题的强调底偏亮、B 主题的偏暗」这种不一致。

代价是：**无法精细控制某套主题的特殊对比度**。高对比主题（`#0A0A0A`）就是典型——它靠「近黑品牌色」+ L4 的 `darkColors` 兜底，而不是靠一套手调 token。

`B1-presets-5.png` 展示了完整 5 套：品牌蓝 / 靛紫 / 青碧 / 桃粉 / 高对比。注意每个 chip 里的 16vp 圆点用的就是 `preset.baseHex`——**这是唯一允许直接把 `baseHex` 当背景色的地方**（它就是色卡本身）。

## 第 4 章 L2 AttributeModifier：无状态样式的取色通道


### 本章要解决的问题

**用 `AttributeModifier` 封装的按钮，为什么改了主题色完全不生效？能不能让 modifier 读主题单例？**

本章回答两个都容易答错的点：modifier **读不到** `@Trace`（读了也白读），而**能读**静态字段（但需要页面重建才刷新）。把这条边界讲清楚，才能理解为什么本仓要引入一个静态中转。

### 读者收获

1. 明白 `AttributeModifier` 为什么不在 ArkUI 观察依赖图里；
2. 掌握「静态中转 + 重建刷新」的取舍与适用边界；
3. 知道何时该改用「构造参数传入」（更显式）而非静态。

---

### 正文要点

#### 4.1 现象：同一页里，两个按钮两种命运

改造前的组件示例页有一个非常典型的对比（`A8-components-teal2.png` 是修复后的状态）：

- 用 `CommonButton`（VitalUI 原语）渲染的「主操作」→ 改主题后**变了**；
- 用 `SomeButton().attributeModifier(new AppButtonPrimaryModifier())` 渲染的按钮 → 改主题后**始终是默认品牌蓝**。

两者在同一屏、同一主题下行为不同。这不是渲染 bug，而是**取色路径不同**：前者读了 `@Trace` 单例，后者读的是写死的 `$r('app.color.qj_brand')`。

#### 4.2 机制：modifier 是普通类，不在观察图里

`AttributeModifier<T>` 的本质是一个「样式函数容器」：ArkUI 在需要应用样式时调用 `applyNormalAttribute(instance)`，把属性写进去。它带来两件事：

1. **调用时机由框架决定**——组件首次构建、状态变更导致重建时；**主题单例变化不会触发它**；
2. **它没有组件上下文**——不是 `@ComponentV2`，没有 `@Local`，因此即使你在里面写 `UiThemeManager.getInstance().brandColor()`，拿到的也只是「那一刻的值」，且**不会**因为 `@Trace` 变化而重新调用。

这就是为什么「让 modifier 直接读单例」看起来能编译、实际不生效。它甚至不是错误——只是**静态求值**。

#### 4.3 正解 A（本仓采用）：静态中转 + 重建刷新

`AppThemeApplier` 里加一个静态字段 `currentAccent`，并在 `apply()` 时写入：

- **写**：`apply()` 里 `currentAccent = theme.effectiveAccent()`，与 L3/L4 同一次调用完成；
- **读**：`AppThemeApplier.brandColor()` 返回 `currentAccent` 非空则用它，否则回退 `$r('app.color.qj_brand')`；
- **用**：所有 modifier 族在 `applyNormalAttribute` 里调这个静态方法。

为什么这样能刷新？因为 modifier 实例通常在页面 `build()` 里 `new` 出来，**页面重建时**会重新执行 `applyNormalAttribute`，此时读到的静态值已是最新。

对应的**已知限制**（源码注释里写明了）：改色后需要一次页面重建才刷新——典型触发是「从外观页返回」或「系统深浅色切换」。这不是偷懒，而是明确接受的行为边界。

#### 4.4 正解 B（更显式）：构造参数注入

`AppProgressModifier` 提供了另一种写法——把颜色作为构造参数，默认值取静态中转：

```
constructor(color: ResourceColor = AppThemeApplier.brandColor(), ...)
```

好处是：调用点可以显式传一个色（例如某处想特调），不传时自动跟随。缺点是：**每个调用点都要决定传不传**，一旦有调用点在页面重建之外被复用，仍会遇到同一个刷新时机问题。

本仓的实际选择是「**静态中转做默认，构造参数留口子**」——两种都在，按需要选。

#### 4.5 为什么不让页面传 `theme.accentColor` 进去

这是最直觉的方案：页面已经有 `@Local theme`，调用点写 `new AppButtonPrimaryModifier(this.theme.accentColor)` 就行。

它的问题在**维护成本**：

1. 34 个使用点全部要确认所在页面有 `@Local theme`（否则拿不到）；
2. 新增一个使用点就要记得传，忘传就静默回退到默认色——**没有编译期保护**；
3. 强调色变化时，页面重建才会重读 `this.theme.accentColor`——依然需要重建，**没有比静态方案更好**。

结论：静态中转在「正确性相同、改动面更小」的条件下胜出。

#### 4.6 静态状态的代价与纪律

引入静态字段换来了简洁，也带来两个必须守住的纪律：

1. **单一写入点**：只允许 `AppThemeApplier.apply()` 写 `currentAccent`，其它任何地方不得赋值。否则会出现「页面用自己的颜色覆盖了全局」的隐蔽 bug。
2. **静态值必须与单例同步**：`apply()` 里先 `setPresetId` / `setAccentColor`，**再**取 `effectiveAccent()` 写静态——顺序反了会写入上一次的值。

这两条在代码里是靠「唯一入口 + 注释」维持的，没有类型系统保护。第 13 章的验收清单把「modifier 与控制台颜色一致」列为必测项，就是为了兜住这个风险。

#### 4.7 判定：什么时候该用 modifier，什么时候别用

| 场景 | 建议 |
|---|---|
| 一组属性要复用到多处（描边 + 圆角 + 内边距） | 用 modifier + 静态中转 |
| 需要**即时**响应主题（不重建页面就变） | **别用 modifier**，改自绘组件读 `@Local theme` |
| 令牌对照/演示（要展示固定色） | 用 modifier，但色值写死（B 类，第 3 章） |
| 单个属性 | 直接写属性，不必上 modifier |

## 第 5 章 L3 UiThemeManager：一个能自动重渲染的单例


### 本章要解决的问题

**怎么让「用户改了一个字符串」，就让全应用所有自绘组件在同一帧换色？**

答案是：把颜色放进一个 `@ObservedV2` 的 `@Trace` 字段里，让组件用 `@Local` 持有它。本章逐方法拆解这个单例，并给出**组件侧必须遵守的读取约定**——违反约定会出现「主题包不生效」的诡异结果。

### 读者收获

1. 能独立写出一个可被 V2 组件观测的全局主题单例；
2. 理解 `effectiveAccent()` / `brandColor()` / `onBrandColor()` / `brandSoftColor()` 四个方法各自的回退链；
3. 知道「空串 = 清除覆盖」这个语义为什么是必需的（第 8 章的根因）；
4. 能识别最常见的错误写法：`accentColor.length > 0 ? accentColor : $r(...)`。

---

### 正文要点

#### 5.1 为什么是「单例 + @ObservedV2」，而不是 AppStorage

需求有三条硬约束：

1. **跨模块可见**：`VitalUI` 的原语要用、`AppComponent` 的工厂要用、`AppSettings` 的外观页要用；
2. **改动要能触发重渲染**，且**跨组件层级**（不是父子传参能解决的）；
3. **VitalUI 必须零 `@kit`**（这条决定了不能用带状态管理的系统设施）。

`@ObservedV2` 类 + 私有构造 + `getInstance()` 同时满足三条：它是纯 ArkTS（零 `@kit`），字段带 `@Trace` 就具备属性级观测能力，任何 `@ComponentV2` 里用 `@Local` 持有它即自动建立依赖。

> 反例提醒：`AppStorage` / `AppStorageV2` 也能做全局状态，但会把「表现层数据」推给平台层设施，且观测粒度是「键」而不是「类属性」，在本场景下不如 `@Trace` 直接。

#### 5.2 字段设计：两个 `@Trace`，一套语义

| 字段 | 类型 | 语义 |
|---|---|---|
| `accentColor` | `string` | 用户自选强调色，`'#RRGGBB'`；**空串 = 没有覆盖** |
| `presetId` | `string` | 当前主题包 id（`AppThemePreset.id`）；空串按默认包处理 |

两者是**叠加关系而非互斥**：主题包是基线，强调色是单点微调。这个语义决定了所有取色方法的**优先级顺序**——强调色永远先于主题包。

#### 5.3 `effectiveAccent()`：拿到「最终生效的品牌色」

逻辑只有两步：有强调色用它，否则取当前主题包的 `baseHex`。

它返回**纯字符串 hex**，用在两个地方：

1. 需要把颜色当数据用（持久化、比对、传给取色器显示）；
2. 传给只接受 `string` 的 `@Param accentColor` 口子。

`B1-presets-5.png` 里能看到它的一个可见后果：切到青碧后，取色块显示的是 `#12A594` 而不是空——因为取色器显示的是 `effectiveAccent()`，即「当前生效色」，而不是「用户是否设过强调色」。

#### 5.4 `brandColor()`：组件侧取色的**唯一**推荐方法

它比 `effectiveAccent()` 多一层判断，返回 `ResourceColor`：

```
有强调色        → 返回强调色 hex
默认主题包      → 返回 $r('app.color.qj_brand')   ← 保住深浅色（第 3 章）
非默认主题包    → 返回该包的 baseHex
```

**为什么它必须存在**：如果组件都自己写「有就用强调色，否则用 `$r`」，那么**主题包这一层就被漏掉了**——切主题包（不设强调色）时，所有这样写的组件都不动。

源码注释专门警告了这一点：

> 组件**不要**写 `accentColor.length > 0 ? … : $r(...)` 这类三元——那会把「主题包」漏掉。

这是本章最重要的一句话。它解释了第 8 章「切主题包没反应」的第二个成因（第一个成因是空串语义）。

#### 5.5 `onBrandColor()`：压在品牌色上的前景色

当文字/图标压在品牌色底上时，必须解决对比度：青碧底配白字尚可，桃粉底配白字就发糊，高对比（近黑）底配深色字则完全不可读。

实现方式是**感知亮度**：

```
luminance = 0.299·R + 0.587·G + 0.114·B      // R/G/B 归一到 0~1
luminance > 0.62 → 前景用 '#0A0A0A'（深）
否则           → 前景用 '#FFFFFF'（白）
```

三个细节值得学：

1. 权重是 sRGB 经典系数（人眼对绿最敏感），不是简单平均；
2. 阈值 `0.62` 是经验值，偏向「宁可早一点转深色字」；
3. **默认主题包 + 无强调色时直接回退 `$r('app.color.qj_on_brand')`**——把这件本该由设计决定的对比关系交给资源限定词，保证深浅色下都正确。

#### 5.6 `brandSoftColor()`：chip 底 / 选中底

原意是「品牌色的柔和层」。实际实现是：默认主题包 + 无强调色 → `$r('app.color.qj_brand_light')`；否则 → `effectiveAccent()`。

**这里有一处语义与名称不一致**：非默认主题包时返回的是**满强度色**，不是柔和色。`B1-presets-5.png` 中「品牌标签」的底偏深，与此一致。

教程在正文中的口径：**把它理解为「品牌底」，不要理解为「浅色叠层」**；若你的产品需要真正的柔和层，应自行按比例混合（第 6 章的 `mix()` 提供了现成算法）。

#### 5.7 `setAccentColor('')`：空串是一个**语义**，不是「无效输入」

这段代码是全系统里最容易被误读的十行之一：

```
setAccentColor(color) {
  空串            → accentColor = ''      // 清除覆盖，回退主题包
  '#RRGGBB'       → accentColor = 该值
  其它            → 忽略（保持原值）
}
```

如果把空串当成「非法输入忽略」，就得到一个致命后果：**切主题包时无法清空上一次的强调色**。而强调色优先级更高，于是「切了包却看起来没反应」。这正是第 8 章要展开的坑 1。

#### 5.8 组件侧的读取约定（必须遵守）

本仓把「谁读单例」按组件类型分成两种范式：

| 组件类型 | 范式 | 原因 |
|---|---|---|
| **VitalUI 原语**（`CommonButton` / `CommonTag` / `ActionCard` / `CommonLoading` / `CommonColorPickerSheet`） | 自己持有 `@Local theme` **且** 开 `@Param accentColor: string`（空串回退 `theme.brandColor()`） | 原语要保持「可被页面覆盖」的灵活性；同时不能因为页面忘传就丢主题 |
| **AppComponent 控件工厂**（`AppCheckbox` / `AppToggle` / `AppSlider` 等 13 个） | 内部 `@Local theme = UiThemeManager.getInstance()`，不给外部口子 | 原生控件的选中色要逐点覆盖，若让页面传参会**大量漏传** |

`CommonButton` 是这个范式的标准样本：

```
@Local theme = UiThemeManager.getInstance();     // 建立观察
@Param accentColor: string = '';                  // 允许页面覆盖
取色 = accentColor.length > 0 ? accentColor : this.theme.brandColor();
```

注意它与 §5.4 警告的区别：这里 `accentColor` 是**页面传入的覆盖值**，为空时才走 `brandColor()`（包含主题包判断）。所以这个三元是**正确**的；错误的三元是「为空时直接跳 `$r`，跳过单例」。

#### 5.9 一个必须知道的类型约束

`@ObservedV2` 的观测只在 **`@ComponentV2`** 里通过 `@Local` 生效。

V1 的 `@Component`（以及 `@Entry @Component` 的卡片框架）**无法**接这个单例。这不是配置问题，而是两套状态管理不互通。第 10 章会给出这条约束导致的真实取舍。

## 第 6 章 L4 ThemeControl：CustomTheme 必须成对给 darkColors


### 本章要解决的问题

**对话框主按钮、开关选中态、SnackBar 动作色——这些我没写颜色的地方，怎么让它们也跟着品牌色走？**

这是自绘体系（L1/L3）完全管不到的部分。答案是官方的 `ThemeControl.setDefaultTheme(CustomTheme)`：把「一个品牌色」翻译成 ArkUI 的 token 表。本章讲清翻译规则、为什么只覆盖 7 个 token、以及 `darkColors` 为什么必须成对。

### 读者收获

1. 能把一个 hex 翻译成合法的 `CustomTheme`（含暗色），并知道 7 个 token 的选择理由；
2. 理解 `applied` 缓存、`try/catch`、`undefined` 清除三个工程细节；
3. 明确 L4 的**能力边界**：它管不到的三种情况（显式属性、HDS 私有 token、V1 卡片）。

---

### 正文要点

#### 6.1 现象：为什么必须补这一层

改造前全仓 `ThemeControl.setDefaultTheme` 调用数为 **0**。后果是：

- `AppDialog` / `CommonDialog` 的「确认」按钮走系统默认蓝；
- 原生 `Toggle` 选中轨道、填充 `Button` 底色走 `sys.color.*`；
- `HdsSnackBar` 的动作色同理。

这些组件你没有显式指定颜色——**所以它们读的是「应用默认主题」**。不设，就是系统蓝；设了，才跟随品牌。

`A9-dialog-teal.png` 是这一层生效最直接的证据：统一对话框的「确认」按钮是青碧 `#12A594`，而该对话框的代码里并没有传这个色。

#### 6.2 API 形态与版本门槛

官方接口形态（`@ohos.arkui.theme`）：

| 类型 | 语义 |
|---|---|
| `CustomTheme` | `{ colors?: CustomColors; darkColors?: CustomDarkColors }` |
| `CustomColors` | `Partial<Colors>`——51 个 token 里**只覆盖你需要的** |
| `ThemeControl.setDefaultTheme(theme)` | 设置应用内默认主题；传 `undefined` 清除 |

版本要点：`CustomTheme.darkColors` 的引入版本**晚于** `colors`（`@since 20`）。这意味着：

- compatibleSdkVersion ≥ 20 时可以直接用；
- fork 方若把兼容版本降到 19 以下，`darkColors` 会编译失败，需要 `canIUse` 或版本分支。

> 本节版本门槛来自 `plan/换肤换主题-调研-2026-10-20.md`（本机 SDK `d.ts` 实录 + 官方文档）。正式发布前建议在自己的 SDK 上复核一次 `@since` 标记。

#### 6.3 为什么只覆盖 7 个 token

51 个 token 全填看起来「更彻底」，实际会引发对比度事故：例如把 `fontPrimary` / `backgroundPrimary` 也刷成品牌色，正文与背景的关系就崩了。

本仓的选择是「**只覆盖强调语义的 7 个 token**，其余 40+ 交给系统默认」：

| token | 作用 |
|---|---|
| `brand` | 填充按钮底、开关选中等主强调 |
| `fontEmphasize` | 强调文本 |
| `iconEmphasize` | 强调图标 |
| `backgroundEmphasize` | 强调底 |
| `compEmphasizeSecondary` | 组件强调层（次级，浅） |
| `compEmphasizeTertiary` | 组件强调层（三级，更浅） |
| `interactiveSelect` | 选中态 |

判定原则：**只覆盖「品牌色应当出现」的 token；凡是承担「可读性基线」的 token（正文、背景、分隔线）一律不碰。**

#### 6.4 浅色：品牌色 + 两档混合

浅色分支直接用品牌色填 4 个强调 token，再用**与白色线性混合**得到两档柔和层：

- `compEmphasizeSecondary` = `mix(hex, #FFFFFF, 0.82)`（82% 白）
- `compEmphasizeTertiary` = `mix(hex, #FFFFFF, 0.90)`
- `interactiveSelect` = 同 tertiary

`mix()` 的实现是标准线性插值：把两个 hex 拆成 RGB 三元组，按比例加权后取整再拼回 `#RRGGBB`。这段代码不到 15 行，但**它是整套「一个色生成一套色」的关键**（第 3 章说的「一套主题包只声明一个色」靠它兑现）。

#### 6.5 深色：先提亮，再用黑混合

深色分支不是把浅色值照搬，而是两步：

1. **提亮品牌色**：`lifted = mix(hex, #FFFFFF, 0.28)`——把暗底上发闷的原色抬亮一档；
2. **用黑做柔和层**：`soft = mix(lifted, #000000, 0.72)`、`soft2 = mix(lifted, #000000, 0.82)`。

为什么柔和层在深色下要「往黑混」而不是「往白混」？因为在暗色界面里，「柔和」意味着**向背景靠拢**，而背景是暗的。这一步做反了，深色下所有 chip 会发光。

#### 6.6 `darkColors` 不设会怎样（这是本章最重要的一节）

`CustomTheme` 的 `darkColors` 语义是：**不提供时，深色模式沿用 `colors` 的值**，不会自动变暗。

后果是「暗底亮字」——在深色模式下，品牌色的强调底仍按浅色逻辑算（偏亮），压在上面的前景色却按深色的白字渲染，对比度全崩。

所以本章有一条**硬规则**：

> `colors` 与 `darkColors` **必须成对提供**。只要其中一个存在，另一个就不能省。

本仓把这条规则固化在 `buildTheme()` 里——它一次性返回 `{ colors, darkColors }`，**从结构上让「只给一半」变得不可能**。这是比写注释更可靠的防错方式，值得照抄。

#### 6.7 三个工程细节

**① 归一化与拒绝非法值**：`normalize()` 接受 `#RRGGBB`，也接受 `#AARRGGBB`（去掉前两位 alpha）。非法输入返回空串，调用方据此**跳过设置**并记一条 warn——而不是把非法值塞给系统组件（那会得到一批不可预测的颜色）。

**② 重复调用短路**：静态 `applied` 记录上次生效值，值没变就直接返回 `true`。`setDefaultTheme` 本身支持重复调用，但每次调用都可能触发全局重算；短路能省掉「打开外观页又点了一次同色」这类无效重刷。

**③ 失败不阻塞启动**：整个调用包在 `try/catch` 里，失败只记 `warn` 并返回 `false`。理由是 L4 只是**兜底层**——它失败了，L1/L3 仍然工作，界面「大部分是对的」，绝不该因为主题失败导致白屏。

#### 6.8 调用时机：官方样例 vs 本仓实际

官方样例把 `setDefaultTheme` 放在 `windowStage.loadContent(...)` 的回调里，理由是「必须在 ArkUI 初始化之后」。

本仓把它放在 `EntryAbility.onCreate` 里通过 `AppBootstrap.restoreTheme().then(...)` 调用。这是**异步的**，实际执行时机取决于 Preferences 读取完成的时刻——可能早于也可能晚于 `loadContent`。

真机结果是可用的（`A9-dialog-teal.png` 取证：对话框按钮确实变了），但这属于「在另一个调用点验证通过」，与官方样例的严格姿势不同。教程把这条列为**需复核项**：

- 若出现「冷启动首屏闪一下系统蓝」的反馈，应把调用点迁到 `loadContent` 回调内；
- 迁移代价很小（`AppThemeApplier.apply` 是幂等的），属于低风险改动。

#### 6.9 L4 的能力边界（三条）

| 边界 | 表现 | 后续章节 |
|---|---|---|
| **显式设置过的属性不会被覆盖** | 你写了 `.backgroundColor('#xxx')`，主题改不动它 | 第 3 章（分级） |
| **HDS 私有 token 不吃这套** | `HdsListItemCard` 底色/分割线/chevron 不变 | 第 11 章 |
| **V1 卡片框架不参与** | ArkTS 卡片保持令牌色 | 第 10 章 |

把这三条写进文档，能省掉后来者大量「明明设了主题为什么这块不变」的排查时间。

## 第 7 章 编排与冷启动恢复：一个方法铺满四层


### 本章要解决的问题

**四层都建好了，谁负责按正确顺序调用？冷启动时怎么保证「打开就是上次的颜色」而不是「先闪一下默认蓝」？**

本章讲两个类：`AppThemeApplier`（落地器，一次调用铺四层）与 `AppBootstrap.restoreTheme()`（只读偏好、不碰表现层）。它们的分工是被**模块依赖方向**逼出来的，理解了这一点，你就不会想当然地把它塞进 `AppCommon`。

### 读者收获

1. 掌握「一次调用铺 L3 + L4」的顺序契约与幂等语义；
2. 理解「读偏好」与「注入表现层」为什么要拆成两个模块；
3. 能写出正确的冷启动恢复链路（含降级键兼容）。

---

### 正文要点

#### 7.1 为什么编排类必须放在 `AppComponent`

这是全章最值得先讲的设计因果，因为它决定了你能不能复用这套结构。

约束链：

```
VitalUI  不能依赖 Platform   （原语库要零 @kit）
AppCommon 不能依赖 VitalUI    （手表端要能用，手表不接主题）
```

而「铺四层」这件事需要**同时**操作：

- L3 → `UiThemeManager`（在 VitalUI）
- L4 → `AppThemeController`（在 Platform）

于是没有任何一个「更底层」的模块能同时持有两者。`AppComponent` 恰好同时依赖 VitalUI 与 Platform，因此它是唯一合法位置。

**推论**：如果你的工程没有这种分层，编排逻辑可以放在任意「同时可见两者」的地方；但只要你有「零依赖的 UI 原语库」，就必然会出现同样的选择。

#### 7.2 `apply()` 的顺序契约：先 L3，后 L4

```
① theme.setPresetId(presetId)             // 空串 → 默认包
② theme.setAccentColor(accentHex)         // 空串 → 清除覆盖
③ currentAccent = theme.effectiveAccent() // 写静态中转（第 4 章）
④ AppThemeController.applyPreset(...)     // 铺 L4
```

三条纪律：

1. **必须先写单例再取 `effectiveAccent()`**：反了就会把上一次的值塞进静态字段；
2. **L3 在前**：自绘组件在同一帧就能取到新色，不会出现「系统组件变了、自绘组件还旧」的错帧；
3. **两者互不依赖**：L4 失败不影响 L3（返回值只表示 L4 是否成功）。

`apply()` 的返回值语义也写清了：**返回 `false` 不代表「什么都没做」**——L3 一定被设置了，只是系统组件层没成功。调用方不应该因为 `false` 就回滚。

#### 7.3 三个入口方法：apply / applyAccent / applyPreset

| 方法 | 何时用 | 行为 |
|---|---|---|
| `apply(presetId, accentHex)` | 冷启动恢复、进外观页幂等再落地 | 全量：L3 + L4 + 静态中转 |
| `applyAccent(accentHex)` | 取色器确认 | 保留当前 `presetId`，只换强调色 |
| `applyPreset(presetId)` | 切换主题包 | 保留当前 `accentColor`，只换主题包 |

注意 `applyPreset` 的行为：**它不替你清强调色**。清不清是**业务决策**——外观页在切包时显式清了（第 8 章），但那属于页面职责，不是落地器职责。这条边界划得很干净：落地器只做「按给定参数铺层」，不猜用户意图。

#### 7.4 `restoreTheme()`：只读，不注入

`AppBootstrap.restoreTheme()` 返回一个纯数据对象 `AppThemeState { presetId, accentHex }`，**不调用任何表现层 API**。

读取顺序（含兼容）：

| 键 | 说明 |
|---|---|
| `accent_color` | 现行强调色键 |
| `accent_preset` | v2.1 历史枚举键，仅在现行键为空时回退；其值是 hex 直通，`'default'` 等非 hex 视为无记录 |
| `theme_preset` | 主题包 id |

强调色要先过 `ACCENT_HEX_PATTERN` 校验：合法才返回小写 `'#rrggbb'`，否则返回空串（控件回退主题包基准色）。

**为什么要校验而不是直接信任持久化值**：持久化数据可能来自旧版本、可能被外部写坏。一个非法 hex 传进 L4 会让 `normalize()` 返回空串、`applyPreset` 直接跳过，最终表现为「主题不生效」——在校验处拦掉，日志里还能看出一句明确的 warn。

#### 7.5 「只读不注入」的代价与收益

代价很明显：**每个入口 Ability 都要自己写三行**（`restoreTheme().then(state => AppThemeApplier.apply(...))`）。

收益是分层不被破坏：`AppCommon` 保持对 VitalUI 零依赖，手表端可以完全不用主题而共享同一套 bootstrap。

实际调用面：

| 入口 | 是否恢复主题 |
|---|---|
| `entry`（手机/平板/折叠） | ✅ `EntryAbility.onCreate` |
| `entry_pc`（2in1） | ✅ `PcAbility` 同样三行 |
| `entry_tv` | ✅ `EntryTvAbility` |
| `entry_wearable`（手表） | ❌ 明确不调用，保持默认主题 |

手表这条不是遗漏，而是**产品决策**：手表界面小、色块少，强行套主题收益低而风险高（HDS/XComponent 在小屏上的表现未验证）。

#### 7.6 幂等再落地：进外观页再铺一次

`AccentColorSetting.aboutToAppear()` 会做一串动作：读强调色（含 legacy 回退）→ 读主题包 → `setAccentColor` / `setPresetId` → **再调一次 `AppThemeApplier.apply()`**。

最后这一句是防御式的：**万一某个入口没调（例如新增端漏了）**，用户只要进一次外观页，四层就会被补齐。

这个模式值得抄：把「关键状态落地」做成**幂等 + 多触发点**，比追求「只在启动时调一次」更抗遗漏。

#### 7.7 冷启动时序与「闪一下」的可能

完整时序（手机端）：

```
onCreate
 ├─ AppBootstrap.prepare(context)               // 错误兜底、色彩模式、存储 init…
 ├─ AppBootstrap.restoreTheme()                 // 异步读偏好 → AppThemeState
 │    └─ .then(state => AppThemeApplier.apply)  // L3 + L4
 └─ captureCardTarget(want)                     // 卡片深链

onWindowStageCreate
 └─ loadContent('pages/Index', cb)              // 首帧渲染发生在这里
```

问题在于：**`restoreTheme()` 是异步的，首帧可能在它完成之前就渲染了**。此时页面看到的是默认主题色，等 `apply()` 完成后再刷新——观感上就是「闪一下」。

本仓在真机上未观察到明显闪色（Preferences 读取很快），但这是一个**结构性风险**，不是「已验证不会发生」。缓解方案（按代价排序）：

1. 把 `apply()` 提前到能同步拿到值的位置（需把主题值缓存进内存，代价是持久化层改造）；
2. 在 `loadContent` 回调里再调一次 `apply()`（幂等，几乎零成本）；
3. 启动页/骨架屏遮住首帧（成本最低，但只是掩盖）。

第 13 章把「冷启动不闪色」列入验收清单。

## 第 8 章 坑 1–2：切主题包「没反应」与「只改单例按钮仍蓝」


### 本章要解决的问题

两个症状，一个共同点——**代码跑了，但优先级盖住了效果**。

- **坑 1**：点「青碧」，外观页的选中态变了，但界面颜色几乎没动。
- **坑 2**：把主题色注入到单例后，大部分按钮变了，**VitalUI 的原语按钮仍然是蓝的**。

两个坑都不是「没接上」，而是「接上了，但被别人覆盖」。

---

### 坑 1：切主题包没反应

#### 现象

外观页点青碧 → 主题包 chip 的选中描边确实转成青碧 → 但**预览区、首页、组件页的主要颜色几乎没变**，观感像「只换了个选中框」。

`A1-appearance.png` 是这个问题最容易复现的状态：主题包选中的是「品牌紫」，而下方取色块显示 `#6c4de8`——**界面显示的颜色由强调色决定，主题包只是个背景设定**。

#### 根因：强调色优先级更高，而它没被清掉

系统的取值优先级是固定的：

```
强调色（非空） > 主题包 baseHex
```

所以「切主题包」这个动作，如果不动强调色，就等于「改了一个优先级更低的变量」——**结果当然没变化**。

更糟的是当时的 `setAccentColor` 实现是**严格校验**式的：

```
若 输入是合法 '#RRGGBB' → 赋值
否则                    → 忽略（保持原值）
```

空串落进了「否则」分支。于是「想清空强调色」这件事**在 API 层就做不到**——不是页面忘了清，而是没有能力清。

#### 正解：把空串定义为一个语义

改动很小，但语义变化很大：

```
空串 → accentColor = ''      // 显式清除覆盖，回退到主题包基准色
合法 hex → 赋值
非法输入 → 忽略
```

三态而非两态。这条改动让「清除」成为一个**可表达的操作**，而不是「什么都不做」。

#### 正解（续）：页面侧也要配合——切包时清强调色 + 清持久化

只改 API 还不够，业务侧要显式表达「切包 = 重置微调」：

```
切包动作 = setAccentColor('') → setPresetId(id) → applyPreset(id)
           + 写入 theme_preset
           + 把 accent_color 写成 ''      ← 容易漏
```

最后一步最容易漏，漏了会得到一个**只在重启后复现**的 bug：当前会话看着对，杀进程重进——`restoreTheme()` 读到旧强调色，又把主题包裹住了。

源码注释把这条动机写得很直白：

> 切包时**清掉强调色覆盖**：强调色是「在主题包之上的单点微调」，若保留上一套的强调色，用户切包后会看到颜色几乎没变（强调色优先级更高），这是实测踩到的真实困惑点。

#### 为什么这个坑值得写进教程

因为它是一个**语义层缺陷伪装成 UI 缺陷**的典型：现象在界面上，根因在「空串该不该算合法输入」。排查时你会一直盯着页面代码，而真正要改的是单例的一个 `if` 分支。

排查口诀：**「某个设置项改了没效果」时，先问「有没有更高优先级的设置项还非空」**。

---

### 坑 2：只改单例，VitalUI 原语按钮仍然蓝

#### 现象

按第 5 章把 `UiThemeManager` 建好，`AppComponent` 的控件工厂（`AppToggle` / `AppCheckbox` / `AppSlider`…）全部跟着变了——但 `CommonButton` 渲染出来的「主操作」按钮、`CommonTag` 的「品牌标签」**依然是默认品牌蓝**。

`A8-components-teal2.png` 是修复后的状态：主操作/次操作/加载中/品牌标签全部转青碧。

#### 根因：原语库是「零 @kit 的纯组件」，没有观测上下文

`VitalUI` 的设计纪律是零 `@kit`、只做表现原语。改造前它的按钮取色直接是 `$r('app.color.qj_brand')`——**它压根不认识 `UiThemeManager`**。

而当时的注入面统计（第 2 章）恰好会误导人：它列出「VitalUI 原语 5 个」在注入面上，但那指的是**通过 `@Param accentColor` 由页面传色**这条路径。**页面不传，原语就不变色**——而绝大多数页面都没传。

于是得到一个很典型的错觉：**「我已经把注入面覆盖了」，但注入面依赖调用方主动喂色**。

#### 正解：原语自己持有单例，同时保留外部覆盖口子

两件事同时做：

```
① @Local theme = UiThemeManager.getInstance()        // 自己建立观察
② @Param accentColor: string = ''                     // 保留页面覆盖能力
③ 取色 = accentColor 非空 ? accentColor : this.theme.brandColor()
```

为什么不是「只靠 `@Param`」？因为让所有页面都记得传 `accentColor` 是不可能的（漏传无编译错误、无运行时告警）。
为什么不是「只靠单例」？因为原语需要「这一处我想特调成别的色」的能力（例如危险场景用红色按钮但形状相同）。

**两者都要，且回退目标必须是 `brandColor()` 而不是 `$r`**——否则会掉进第 5 章 §5.4 那个陷阱（漏掉主题包层）。

#### 与坑 3 的区别（重要，别混）

| | 坑 2 | 坑 3（第 9 章） |
|---|---|---|
| 写法 | 原语**没读**单例，只读 `$r` | 原语读了单例，但读在 **`@Param` 默认值**里 |
| 结果 | 永远不响应 | 改色时**不重渲染**（首次求值后固定） |
| 修法 | 加 `@Local theme` | 把读取从「默认值」搬到「`build`/取色方法」 |

坑 2 是「没连上」，坑 3 是「连上了但不观察」。两者的现象几乎一样，修法完全不同——这是本教程把 `@Param` 陷阱单独成章的原因。

#### 为什么这个坑值得写进教程

因为它揭示了「注入面」这个指标的一个盲区：**注入面统计的是「谁读了单例」，不是「谁最终显示品牌色」**。

一个更可靠的度量是：**改动一次主题色，逐屏截图对比，看哪些像素变了**。这条方法在第 13 章的验收清单里被固化成「逐页 A/B 截图」。

---

### 修正后的调用链（两张图看懂）

**改造前**：

```
页面 ──?──> CommonButton ──> $r('app.color.qj_brand')      // 永远蓝
页面 ────> AppToggle      ──> UiThemeManager               // 跟随
```

**改造后**：

```
页面 ──(可选 accentColor)──> CommonButton
                                ├─ accentColor 非空 → 用它
                                └─ 否则 → @Local theme.brandColor()
                                             ├─ 有强调色 → hex
                                             ├─ 默认包   → $r（深浅色）
                                             └─ 非默认包 → baseHex（换肤生效）
```

## 第 9 章 坑 3–4：`@Param` 默认值读单例不响应，顶层 `@Builder` 用不了 `this`


### 本章要解决的问题

这两个坑的共同点是：**代码看起来完全正确，编译器也不报错，但就是不刷新。**

- **坑 3**：把主题色写在 `@Param` 的**默认值**里 → 首次求值后固定。
- **坑 4**：在**顶层 `@Builder`** 里想读单例 / 用 `this` → 两者都不存在。

### 读者收获

1. 掌握一条判定信号：「改色后重建页面就对了」= 求值时机问题；
2. 知道 `@Param` 默认值不参与依赖收集，必须把读取搬进 `build` 或取色方法；
3. 掌握「内容对象注入」这个让无上下文 `@Builder` 拿到主题色的标准手法。

---

### 坑 3：`@Param` 默认值读单例，改色不响应

#### 现象

组件这么写（**错误示范，仅 1 行**）：

```
@Param accentColor: string = UiThemeManager.getInstance().effectiveAccent();
```

第一次渲染颜色是对的（当前主题色）。之后在任何页面改主题色：**这个组件的颜色不动**。但如果切到别的页面再回来（组件重建），颜色就对了。

#### 根因：默认值只在实例化时求值一次

`@Param` 的默认值是**表达式**，在**创建组件实例时求值一次**，把结果赋给参数。它带来两个后果：

1. **值被固化**：后续单例变化不会回写到这个参数（参数只由父组件传入才会更新）；
2. **不建立依赖**：依赖收集发生在**读取 `@Trace` 字段的那次 `build` 执行**中。在「实例化求值」阶段读，不属于渲染期的读取，**不会被记入依赖图**。

所以这不是「响应式写法错了」，而是「用了求值时机不对的地方去读一个可观察值」。

#### 正解：`@Local` 持有单例，读取发生在渲染期

```
@Local theme = UiThemeManager.getInstance();     // 持有的是对象本身
取色方法() { return this.theme.brandColor(); }    // 读取发生在 build 调用链中
```

区别的关键：`@Local theme` 持有的是**对象引用**，`build` 执行时通过 `this.theme.brandColor()` 访问 `@Trace` 字段——这次访问发生在渲染期，依赖被正确记录，改色即重渲染。

这就是为什么 `CommonButton` 的写法是「`@Local theme` + `@Param accentColor` 双持」而不是「`@Param` 默认值读单例」（第 5 章 §5.8）。

#### 一条可复用的判定信号

> **「改色后，重建页面/重进页面就对了」→ 求值时机问题；「重建也不对」→ 根本没连上（坑 2）。**

这条信号能把 90% 的「主题不生效」问题在 5 分钟内分流。

#### 顺带一个同类陷阱：`@Builder` 参数按值传递

同源的坑还有 `@Builder` 的参数传递：**带值参数的 `@Builder` 调用会把值按值捕获**，父组件状态更新不会让它重算。表现是「点了按钮，`@Builder` 里的东西不跟着变」。

修法同理：**要么把读取搬进 `build` 内联**，要么**改传对象/回调**（对象是引用，字段变化可被观测）。本仓在动效演示页踩过这个坑（曲线方块点击不动），根因即此。

---

### 坑 4：顶层 `@Builder` 不能用 `this`，也读不到单例

#### 现象

一个全局悬浮球（`AppOverlay`）的品牌圆钮，无论怎么换主题，**底色恒为默认品牌蓝**。

#### 根因：顶层 `@Builder` 是「无组件上下文的函数」

`@Builder` 定义在文件顶层（不是 `struct` 成员）时：

1. **没有 `this`**——它不是组件方法，没有实例；
2. **不能在渲染期建立对单例的依赖**——它不属于任何组件的渲染作用域；
3. 它通常通过 `ComponentContent` / `wrapBuilder` 从**组件外部**注入，连父级状态都拿不到。

于是任何「在 builder 里读主题色」的尝试都会失败——不是写法问题，是**上下文不存在**。

#### 正解：内容对象注入（把「读色」搬到有上下文的一侧）

三步走：

**① 定义内容对象**（纯数据，含主题色字段）：

```
class AppFloatingBallContent {
  tint: ResourceColor = $r('app.color.qj_brand');    // 默认值只做兜底
  onTint: ResourceColor = $r('app.color.qj_on_brand');
}
```

**② builder 只消费字段，不读单例**：`appFloatingBallBuilder(content)` 内部用 `content.tint` / `content.onTint`。

**③ 调用侧（有组件上下文）填值**：

```
const theme = UiThemeManager.getInstance();
content.tint = theme.brandColor();
content.onTint = theme.onBrandColor();
// 再交给 ComponentContent 注入
```

这样「读取」发生在有上下文的一侧，「渲染」发生在无上下文的一侧，两侧通过**内容对象**这一份数据结构解耦。

源码注释把这条约束写得很清楚：

> `@Builder` 是顶层函数、不能读单例也不能用 `this`，故由 `show()` 侧读主题注入。

#### 补充：内容对象变了，builder 会跟着变吗

**不会自动变。** 这是坑 3 的同一机制的延伸：`ComponentContent` 一旦构建，builder 的参数按值捕获，字段后续变化不会触发重绘。

所以「悬浮球颜色」这类场景的正确预期是：**在下一次 `show()`（重建 `ComponentContent`）时取到新色**。若产品要求「开着悬浮球时切主题也立即变色」，就需要在切色后主动重建 `ComponentContent`——代价与收益需单独评估。

#### 同类样本：`splitPlaceholderBuilder`

`Index.ets` 里的分栏空态占位也是**顶层 `@Builder`**，它内部只用 `$r(...)`、不读单例、不用 `this`——这是「知道约束并主动规避」的写法，可作对照样本。

---

### 两个坑的对照表

| | 坑 3 | 坑 4 |
|---|---|---|
| 载体 | `@Param` 默认值 | 顶层 `@Builder` |
| 为什么失效 | 求值时机不在渲染期，依赖未被记录 | 没有组件上下文，无法建立依赖 |
| 重建后是否恢复 | ✅ 会恢复 | ✅ 会在下一次构建时取到 |
| 修法 | `@Local` 持有单例 + 渲染期读取 | 内容对象注入（读取搬到调用侧） |
| 判定信号 | 重建就好 | builder 里的色永远不变 |

## 第 10 章 坑 5–6：不设 `darkColors` 暗色沿用浅色；卡片 V1 接不上 V2 单例


### 本章要解决的问题

一个是**实现顺序坑**（你会先只给 `colors`），一个是**框架边界坑**（有些地方就是接不上，正确做法是「承认并保留」）。

- **坑 5**：`CustomTheme` 只给 `colors` 不给 `darkColors` → 暗色模式下亮底亮字。
- **坑 6**：ArkTS 卡片是 V1 框架 → 接不了 `@ObservedV2` 单例；此时**保留 `$r` 是正解**，不是妥协。

### 读者收获

1. 理解 `darkColors` 缺省时的行为，以及为什么「结构上不可能只给一半」比注释更可靠；
2. 能把「V1/V2 不互通」这条硬约束翻译成产品决策；
3. 顺手避掉卡片的第二个坑：`@Builder` 带值参数的载荷不更新。

---

### 坑 5：不设 `darkColors`，暗色下沿用浅色

#### 现象

浅色模式下一切正常；切到深色模式后：

- 品牌色的强调底仍然是「浅色逻辑算出来的偏亮值」；
- 压在上面的前景（白字/深字）按暗色渲染；
- 结果是对比度崩坏：深色页面里出现一块发亮的品牌色 + 看不清的按钮文字。

#### 根因：`darkColors` 的默认行为是「沿用 `colors`」

`CustomTheme` 的两个字段是**独立**的：

```
{ colors?: CustomColors; darkColors?: CustomDarkColors }
```

`darkColors` **不提供**时，系统在暗色模式下**沿用 `colors` 的值**——它不会自动帮你「按暗色重新算一遍」。这与很多人对「深色适配」的直觉相反（直觉是「系统会自己变暗」）。

浅色逻辑算出来的柔和层是「向白色混合」（82% / 90% 白），在暗色界面里等于**主动提亮**，与背景方向相反。这就是「亮底」的来源（第 6 章 §6.5 讲了正确做法：暗色要往黑混）。

#### 正解一：暗色单独算一套（内容层面）

深色分支做两步：先把品牌色提亮一档（`mix(hex, #FFF, 0.28)`），再用黑做柔和层（`mix(lifted, #000, 0.72/0.82)`）。这样柔和层向暗背景靠拢，而不是向白靠拢。

#### 正解二：让「只给一半」在结构上不可能（工程层面）

比写注释更可靠的做法：**不暴露 `lightColors` / `darkColors` 两个入口给别人拼装**，而是只暴露一个返回完整对象的方法：

```
buildTheme(hex) → { colors: lightColors(hex), darkColors: darkColors(hex) }
```

外层拿到的永远是成对的结果，**没有机会只传 `colors`**。本仓采用这种做法，第 6 章已述。

这类「用类型/结构固化约束」的手法，比「在文档里写『请务必成对』」有效一个数量级。

#### 为什么本仓没有「事故截图」

本仓从 L4 建立之初就是成对提供，因此**没有留下「暗色亮底」的现场截图**。这个坑的受众是：

- 正在照教程实现的人（会先只给 `colors`，因为编译能过）；
- fork 后重构 `CustomTheme` 的人（可能把 `buildTheme` 拆开）。

教程在正文中的处理方式：**讲机制 + 讲结构防错**，不虚构一张「修复前」的截图。

#### 与之相关的一条取舍

默认主题包（无强调色）时，L3 返回的是 `$r('app.color.qj_brand')` 而不是 hex——这让自绘层在暗色下也能拿到 `dark` 限定词里的提亮值。

代价是：**非默认主题包的自绘品牌色在暗色下不提亮**（第 3 章 §3.6 已列为已知偏差）。它与坑 5 是同一枚硬币的两面：**系统层靠 `darkColors` 解决，自绘层靠资源限定词解决，两者解法不同步**。

### 坑 6：ArkTS 卡片是 V1 框架，接不了 V2 单例

#### 现象

想让桌面卡片（服务卡片）的品牌色跟随应用内主题。照 L3 的做法给卡片加 `@Local theme = UiThemeManager.getInstance()`——**不生效**，甚至可能编译/运行异常。

#### 根因：卡片框架只支持 V1 装饰器，V1 与 V2 状态管理不互通

卡片入口是 V1 形态：

```
@Entry(cardStorage)
@Component
struct WidgetCard {
  @LocalStorageProp('themeText') themeText: string = '跟随系统';
  ...
}
```

约束有两条，缺一不可：

1. **卡片框架当前只支持 V1**（`@Entry` / `@Component` / `@LocalStorageProp` 等）；
2. **`@ObservedV2` + `@Trace` 只能在 `@ComponentV2` 里通过 `@Local` 观测**，V1 组件无法接。

两条叠加的结论：**卡片在架构上就不可能跟随运行时主题**。这不是配置问题，也不是写法问题。

#### 正解：保留 `$r` 令牌（并把它写成决策，而不是遗留）

卡片的做法是：**颜色继续用 `$r('app.color.*')` 令牌**。

为什么这是正解而非妥协：

| 维度 | 说明 |
|---|---|
| 深浅色 | ✅ 仍然正确（令牌随 `dark` 限定词切换） |
| 品牌一致性 | ⚠️ 只跟随「默认品牌色」，不跟随用户换肤 |
| 稳定性 | ✅ 卡片是系统进程渲染的独立入口，减少跨进程状态同步风险 |
| 成本 | ✅ 零改动；若强行做，需要「应用写偏好 → 卡片读偏好 → 重绘」的自建链路 |

如果产品**必须**让卡片跟随主题，可行的替代路径是：应用把当前主题色的 hex 写进卡片共享数据（`LocalStorage` / 持久化），卡片用 `@LocalStorageProp` 读取并直接当色值用。**注意这仍然是「数据注入」而不是「观测单例」**，并且要处理「应用未运行时卡片首次加载」的缺省值问题——属于独立课题，本仓未做。

#### 顺带一个卡片专属坑：`@Builder` 带值参数不更新

卡片里还有一个更容易踩的细节（源码注释已写明）：

> 若值经**带值参数的 `@Builder`**（如 `infoRow(label, this.themeText)`）转手，值会被按值捕获、**永不随载荷更新**。

也就是说：卡片收到新载荷 → `@LocalStorageProp` 更新 → 但如果这个值是通过带值参数的 `@Builder` 传进子结构的，**子结构不会重绘**。

这正是第 9 章坑 3 的同一机制在卡片场景的复现。修法同样是「读取搬进 `build` 内联」或「改传对象」。

#### 三张入口的 V1/V2 边界速查

| 入口 | 状态管理 | 能否接 L3 单例 |
|---|---|---|
| 应用内页面（`@Entry @ComponentV2`） | V2 | ✅ |
| 应用内 V1 组件（遗留 `@Component`） | V1 | ❌（需先迁 V2） |
| ArkTS 卡片（`@Entry(cardStorage) @Component`） | V1（框架限制） | ❌（不可迁） |

这张表能省掉大量「为什么这块就是不跟着变」的排查。

## 第 11 章 坑 7：HDS 私有 token 不吃 `ThemeControl`


### 本章要解决的问题

**系统组件的默认色已经被我接管了，为什么设置页的开关轨道还是系统蓝？**

因为那个开关不是「系统组件」，而是 **HDS 组件**。它读的是 HDS 自己的私有 token，既不吃 `ThemeControl`，也不认识你的 `UiThemeManager`。本章讲清这条第三体系的边界，以及**唯一的正解：显式传色**。

### 读者收获

1. 能区分三类颜色体系：原生 `sys.color` / HDS 私有 token / 自绘；
2. 掌握「查 d.ts 找显式传色入口」的排查路径（不靠猜属性名）；
3. 学会用真机 A/B 取证「某个 token 到底吃不吃主题」。

---

### 现象

切到青碧主题后走查设置页，发现：

| 位置 | 结果 |
|---|---|
| 触感反馈开关 ON 轨道 | **系统蓝** `#0A59F7`（应为青碧 `#12A594`） |
| 屏幕常亮开关 ON 轨道 | 同上 |
| HDS 行卡片底色 | 中性灰（不变） |
| 行分割线 | 中性灰（不变） |
| 行尾 chevron 箭头 | 中性灰（不变） |

而同一页里，其它自绘元素（图标 chip、页码等）已经正确转成青碧。**同页两种行为**，说明不是主题没生效，而是这些元素不属于同一个体系。

---

### 一次真实的误判（这段比结论更值得读）

第一反应是：「这个开关是我们自绘的 `SettingsSwitchRow`，它的 `.selectedColor(this.theme.brandColor())` 应该生效，为什么没变？」

于是检查了 `SettingsSwitchRow` —— 那条路径**本来就是对的**，其它页面用它的开关都正常变色。

继续查才发现：设置域是 **schema 驱动**的（`SchemaSettingsSection` 按 `rawfile/settings_schema.json` 渲染），而 `builtin: 'haptic'` / `builtin: 'keepScreenOn'` 这两行走的是：

```
HdsListItemCard({
  prefixItem: …,
  textItem: …,
  suffixItem: new SuffixSwitch({ isCheck: …, onChange: … })   // ← 这里没有颜色参数
})
```

也就是说：**页面上看到的开关根本不是自绘组件**，它来自 HDS 的 `SuffixSwitch`。自绘那条路径没问题——是我看错了对象。

> 教训：schema 驱动的页面，「看到的控件」与「以为的组件」经常不是同一个。排查前先确认这个像素是谁画的。

---

### 根因：三类体系，三种吃色的方式

| 体系 | 颜色来源 | 吃 `ThemeControl`？ | 吃 `UiThemeManager`？ | 正解 |
|---|---|---|---|---|
| 原生组件（`Toggle` / `Button`…） | `sys.color.*` → 应用默认主题 | ✅ 是 | ❌ | L4（第 6 章） |
| **HDS 组件**（`HdsListItemCard` / `HdsTabs` / `SuffixSwitch`…） | **HDS 私有 token** | ❌ **否** | ❌ | **显式传色参数 / Modifier** |
| 自绘组件 | 你写的取色逻辑 | — | ✅（若接了） | L3（第 5 章） |

`ThemeControl.setDefaultTheme` 覆盖的是 ArkUI 的 token 表（51 个 `Colors` 字段）。HDS 组件虽然画在 ArkUI 之上，但它内部用的是**自己的一套 token**，不在这张表里——所以主题对它无效。

这也解释了为什么「HDS 行卡片的底色/分割线/chevron 完全不随主题」：它们全部由 HDS 私有 token 决定。

---

### 正解：查 d.ts，找到显式传色入口

不要猜属性名（猜错的成本是半小时），直接查 HDS 的类型声明：

- 目标文件：本机 SDK 里的 `@hms.hds.hdsBaseComponent.d.ets`
- 要找的东西：`SuffixSwitch` 的构造参数类型（`CheckOptions`）
- 找到的属性：`selectColor?: ResourceColor` —— **HDS 自己提供了显式传色的口子**

于是修改只有两处（对应两个 `SuffixSwitch` 实例）：

```
new SuffixSwitch({
  isCheck: this.vm.hapticEnabled,
  selectColor: this.theme.brandColor(),    // ← 新增
  onChange: …
})
```

同时给 `SchemaSettingsSection` 补上观测上下文：

```
@Local theme: UiThemeManager = UiThemeManager.getInstance();   // 新增
```

**注意这一步不可省**：只传 `selectColor` 而不持有 `@Local theme`，首次渲染是对的，切主题时**不会重绘**（第 9 章坑 3 的同一机制）。

---

### 验证：真机 A/B

验证方式不是「看起来变了」，而是**取像素**：

| | 修复前 | 修复后 |
|---|---|---|
| 开关 ON 轨道 | `#0A59F7`（系统蓝，恒定） | `#12A594`（青碧，随主题） |

`G2-toggle-on-teal.png` 是修复后的取证：分栏右栏「通用设置」页里，「触感反馈」开关 ON 轨道为青碧，「屏幕常亮」为 OFF 灰态。

---

### 边界：修好开关 ≠ HDS 全部跟随

HDS 组件族里，**只有提供了显式传色参数的**才能跟随主题。当前状态：

| HDS 元素 | 能否跟随 | 路径 |
|---|---|---|
| `SuffixSwitch`（本仓两处） | ✅ 已跟随 | `CheckOptions.selectColor` |
| `HdsListItemCard` 卡片底色 / 分割线 / chevron | ❌ 仍不跟随 | 需 `HdsListItemCardModifier` 或显式 tint（**本仓未做**） |
| `HdsTabs` 页签选中色 | ⚠️ 未专门处理 | 需查其自身样式参数（**需复核**） |
| `HdsNavigation` titleBar 材质 | ⚠️ 计划以系统材质为主 | 材质色随系统，非品牌色（预期行为） |

教程口径：**HDS 的跟随是「逐组件、逐 token」的工程，不是一次开关**。谁提供了口子就接谁，没口子的不要硬试（下一节讲为什么）。

---

### 方法论：遇到「这块不吃主题」的四步法

1. **确认是谁画的**：schema 驱动 / 工厂封装 / 直接写——先定位到真实组件；
2. **判断体系**：原生 `sys.color` → 查 L4；HDS → 查私有 token；自绘 → 查是否读了单例；
3. **查 d.ts 找口子**：在 `@hms.hds.*.d.ets` 里搜组件名，看构造参数/Modifier 是否有 `ResourceColor` 字段；
4. **A/B 取像素验证**：不看「感觉变了」，看「色值变了」。

这套顺序能避免两种典型浪费：盲目给 HDS 组件套 `.backgroundColor()`（被其内部 token 覆盖），以及反复怀疑主题系统（其实是另一个体系）。

## 第 12 章 坑 8–9：响应式不能按窗口断点算栏宽/列数，页签不能按断点切位置


### 本章要解决的问题

这两个坑看起来是「布局问题」，与换肤无关——但它们在真机走查里**和主题问题混在一起**，让「主题没生效」的错觉成倍放大。

- **坑 8**：宽屏（`bp=lg`）分栏后，左栏实际只有约 420vp；按窗口断点算「lg = 4 列」会把卡片压到 ~100vp，标题截成「设…」。
- **坑 9**：宽屏时把 `HdsTabs.barPosition` 切成 `Start`，页签会飞到左栏**顶部**，夹在标题与列表之间。

### 读者收获

1. 分清「窗口断点」（设备形态）与「容器宽」（我实际能画多宽）；
2. 掌握「宿主下传容器宽 + 子视图按容器宽分档」的模式；
3. 知道 `barPosition` 在分栏下为什么必须恒定。

---

### 先看现象：两张图读懂坑 8

| 截图 | 你看到的 |
|---|---|
| `E3-pura-tools.png` | 阔折叠展开、分栏左栏里「开发工具」网格被压成 4 列，卡片窄、标题与描述大量截断 |
| `E4-pura-tools-fixed.png` | 同一页改为 2 列，卡片恢复可读（描述能显示两行） |

要点：**两次的窗口断点完全一样**（都是 `bp=lg`），变的只是「按什么宽度算列数」。

---

### 坑 8：窗口宽 ≠ 你有的宽度

#### 根因：分栏把可用宽度切走了

入口页在宽屏下进入 `NavigationMode.Split`：

```
.mode(this.breakpoint.isWide() ? NavigationMode.Split : NavigationMode.Stack)
```

一旦分栏，**左栏（navBar）只占窗口宽度的一部分**——而 `Navigation` 的默认左栏宽度在阔折叠这类设备上只有约 **320vp**。于是：

- 断点仍然是 `lg`（窗口足够宽）；
- 但页面实际容器只有 ~320–420vp。

如果子视图用「断点 → 列数」映射（`lg` → 4 列），列数按「大屏」给，容器按「小屏」算 → **每列被压扁**。

#### 正解一：把左栏宽度显式定下来

入口页不再依赖默认值，而是按「窗口宽的 32%，clamp 到 340–420vp」：

| 断点 | 左栏宽度 |
|---|---|
| `lg` / `xl` | `clamp(340, 窗口宽 × 0.32, 420)` |
| `md` | `44%`（比例，随窗口缩） |
| `sm` 及以下 | 不分栏（`Stack`） |

同时用 `navBarWidthRange({ minWidth: 300, maxWidth: 440 })` 兜住边界，避免极端窗口下越界。

为什么是 32% + clamp？因为**比例保证随窗口缩放，clamp 保证两端不发散**：窗口很宽时左栏不至于跟着无限变宽（420 封顶），窗口中等时也不至于被压到不可读（340 兜底）。

#### 正解二：把「容器宽」下传给子视图

关键设计：入口把**数值宽度**（`navPaneWidthVp()`，未分栏时返回 0）作为 `@Param paneWidthVp` 传给子视图。子视图按它分档：

| 容器宽 | 列数 |
|---|---|
| < 480 | 2 |
| < 760 | 3 |
| ≥ 760 | 4 |
| 宽为 0（拿不到） | 退回断点判断（sm=2 / md=3 / 其他=4） |

这套规则的要害是第一条：**420vp 的容器落到「< 480 → 2 列」**，于是修复了挤扁问题——`E4-pura-tools-fixed.png` 就是 2 列的结果。

#### 正解三（配套）：网格高度要自己算

`Grid` 被放进 `Scroll` 时不会自动撑高，会塌成 0 高度。本仓的处理是按「行数 × 行高 + 行间距」显式计算：

```
rows = ceil(条目数 / 列数)
height = rows × 卡片高 + (rows − 1) × 间距
```

注意这段计算**依赖列数**——列数一改，高度必须跟着改。这也是为什么「列数按容器宽算」必须和「高度显式计算」放在同一个视图里：两者是同一个决策的两个输出。

#### 一条可复用的判断规则

> **断点回答「设备是什么形态」（要不要分栏）；容器宽回答「我这一块有多少地方画」（列数、间距、字号档）。**

把这两件事混用，就会出现「大屏上被压扁、小屏上留白过多」的典型错位。

---

### 坑 9：`HdsTabs.barPosition` 不能按断点切

#### 现象

宽屏（分栏）下，底部页签「跑了」：`示例 / 学习 / 开发工具` 出现在**左栏顶部**，横在页面标题与内容卡片之间，看起来像一组次级导航。

`E2-pura-navwide.png` 就是这个现场（该图还是「网格已按容器宽修好、页签位置未修」的中间态）。

#### 根因：误把「宽屏」理解成「页签该在上方」

原写法是：

```
.barPosition(this.breakpoint.isWide() ? BarPosition.Start : BarPosition.End)
```

意图是「宽屏时页签放到上面，更符合平板习惯」。但在**分栏**语境下，`HdsTabs` 的容器已经不是整屏，而是**左栏**。此时 `Start` 把页签放到左栏顶部——正好插在标题与列表之间，既不像顶部导航，也不再是底部页签。

#### 正解：恒为 `BarPosition.End`

```
.barPosition(BarPosition.End)      // 恒定，不随断点变化
```

结果：分栏时页签落在**左栏底部**（浮动胶囊形态），与 2in1 端一致。`G0-pura-tabbar-bottom.png` 与 `G2-toggle-on-teal.png` 都能看到这个形态。

#### 为什么不是「宽屏时改成左侧竖排」

那是另一种设计（rail 导航），需要配套：图标+文字重排、宽度预算、选中指示器方向、内容区让位。**改 `barPosition` 一个属性得不到 rail**，只会得到「位置错了的底部页签」。要做 rail 就得单独设计组件。

#### 一个附带的观感细节

页签用了 `barOverlap(true)`（内容延伸到页签之下）+ 悬浮样式。因此底部页签会**覆盖在列表之上**——这是沉浸光感的既有设计，不是遮挡 bug：滚动到末尾时最后一行仍能完整看到（因为列表有底部 padding 预留）。改这块前先确认这个前提，否则容易把「设计意图」当成「布局缺陷」去修。

---

### 两个坑的共同教训

1. **真机走查要按「形态」分组**：手机竖屏 / 阔折叠展开（分栏）/ 2in1 宽屏 / 平板，每组的容器宽差异巨大，同一套断点逻辑在其中几组上必然出错。
2. **主题问题与布局问题必须分开取证**：先修布局（列数/页签位置），再看颜色。否则「文字被截断」会被误读为「主题把字变没了」。
3. **`E*` 与 `G*` 系列截图不可混用**：`E4` 修的是列数（此时页签仍在顶部），`G0/G2` 才是页签修复后的状态。写文档时标清「哪张图对应哪次修复」，否则会得出「改了 A 同时修好了 B」的错误因果。

## 第 13 章 验收清单、回归矩阵与 fork 接入顺序


### 本章要解决的问题

**怎么证明「换肤真的完整了」，而不是「我看的那几页对了」？**

2. 四端各自的「必测页面 + 已知差异」；
3. 一条「先做什么、后做什么」的接入顺序（顺序错了会重复踩坑）。

---

### 13.1 验收清单（逐条可勾）

#### A. 四层是否都接上

- [ ] 改强调色 → 自绘组件（按钮/标签/chip/加载）**立即**变（L3）
- [ ] 切主题包（不设强调色）→ 自绘组件变（验 `brandColor()` 回退链，第 5 章 §5.4）
- [ ] 对话框主按钮 / 填充按钮 / 开关选中（原生）变（L4）
- [ ] `AttributeModifier` 渲染的组件在**页面重建后**变（L2，接受延迟，第 4 章）
- [ ] 令牌对照页 / 语义色（危险/成功/警告）**不变**（B/C 类，第 3 章）
- [ ] HDS 组件：提供显式传色口子的变了（开关），未提供的**明确记为已知不跟随**（第 11 章）

#### B. 优先级与清除语义

- [ ] 设了强调色后切主题包 → 强调色被清，颜色跟随新主题包（坑 1，第 8 章）
- [ ] 点「恢复默认强调色」→ 回到**当前主题包**基准色，而不是回默认主题包（第 8 章）
- [ ] 杀进程重进 → 主题包 + 强调色都正确恢复（持久化与内存一致）
- [ ] 手动写入非法 hex 后启动 → 不崩、回退主题包、日志有 warn（第 7 章 §7.4）

#### C. 深浅色

- [ ] 浅 → 深 → 浅 往返切换，品牌色不发白/不刺眼（`darkColors` 生效，第 6 章）
- [ ] 深色下自绘品牌色与系统品牌色**明度差可接受**（第 3 章 §3.6 已知偏差）

### 13.3 fork 接入顺序（顺序错了会重复踩坑）

推荐的实施顺序及理由：

| 步骤 | 做什么 | 为什么必须在这个位置 |
|---|---|---|
| **1** | 建 L3 单例（`UiThemeManager`）+ 你的原语接入 `@Local theme` | 所有自绘组件的基础；先有它才能验证「谁没接」 |
| **2** | 建 L4（`CustomTheme` + `darkColors` 成对）+ 落地器 | 补系统组件断层；越晚做，走查时「系统蓝」的噪声越多 |
| **3** | 接冷启动恢复（`restoreTheme` + 各入口 `apply`） | 否则每次重启都要手动设，走查效率极低 |
| **4** | 全仓取证 + 分级（A/B/C 三类） | 有前三步才有「变/不变」的对照基线；分级避免误改演示页与语义色 |
| **5** | L2 modifier 接静态中转 | 改动面小、风险低，放中段 |
| **6** | HDS 逐组件找显式传色口子 | 需要逐个查 `d.ts`，最耗时，放后面 |
| **7** | 布局与容器宽修复（分栏/页签） | **放最后**：它会改变观感，提前做会污染主题走查的对照 |
| **8** | 验收清单逐条过 + 四端矩阵 | 收口 |

两条反直觉但重要的顺序约束：

- **第 4 步（取证分级）不能放到第 1 步之前**——没有 L3/L4，「变/不变」的对照无法建立，取证只能得到一堆静态色值；
- **第 7 步（布局）不能放到前面**——分栏会把「主题问题」与「截断问题」混在一起（第 12 章开头已述）。

### 13.4 已知遗留与决策记录（写进 README，别写进「待办」）

把「决策」与「缺陷」分开记，是这套系统能长期维护的关键：

| 项 | 类型 | 说明 |
|---|---|---|
| 卡片（ArkTS）不跟随主题 | **决策** | V1 框架限制，保留 `$r` 是正解（第 10 章） |

| modifier 需页面重建才刷新 | **已知限制** | 源码注释已声明（第 4 章） |

> 纪律：**「遗留」可以排期，「决策」不要排期**。把决策挂进待办清单，会让后来者反复尝试一件已经论证过不该做的事。

### 13.5 一句话总结全书

> 换肤不是「换一个颜色」，而是**四层各管一段、按顺序编排、逐体系取证**：
> L4 兜住系统组件，L3 管住自绘组件的即时性，L2 保留特调，L1 守住语义与深浅色；
> 优先级与清除语义要显式表达；HDS 与 V1 卡片的边界要承认；
> 最后用容器宽而不是窗口断点来画界面。
