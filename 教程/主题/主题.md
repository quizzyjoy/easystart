## 一、换肤要动哪几处：四层颜色模型

在 HarmonyOS 应用里，屏幕上的一处颜色可能来自四个互不相同的地方。换肤常常"只变一半"，是因为只处理了其中一个。

| 层 | 机制 | 由谁决定颜色 | 未处理时的表现 |
|---|---|---|---|
| L1 | 资源令牌 `$r('app.color.*')` | 资源编译器（编译期固化） | 只随深浅色变，不随主题变 |
| L2 | `AttributeModifier` 样式类 | 类中读取到的值 | 完全不参与运行时换色 |
| L3 | 运行时主题单例（`@ObservedV2`） | 应用内单例的当前值 | 只有接入了单例的组件会变 |
| L4 | `ThemeControl.setDefaultTheme` | ArkUI 全局主题表 | 系统控件保持系统默认色 |

四者是并列关系，不是优先级关系：某一层没有接入，对应位置的像素就不会变。

先看一组对照。默认主题下的首页：

![默认主题下的首页：图标底与强调块为品牌色](图片/B2-home-brandblue.png)

切换到另一套主题后：

![切换后：品牌类颜色同步变化，危险色与成功色保持不变](图片/A8-components-teal2.png)

对比可见变化是成组的：品牌装饰色跟随主题，语义色（危险 / 成功 / 警告）保持不变——后者是设计约束，不是遗漏。

**本教程的组织方式**：第二至五节分别实现四层，第六节把它们编排起来并处理冷启动，第七节汇总常见的错误写法。建议按顺序阅读，每节末尾给出可执行的验证方式。

## 二、第一层：静态令牌

最基础的着色方式是资源令牌：

```ts
Text('标题').fontColor($r('app.color.qj_brand'))
```

它在编译期固化，深浅色可通过 `resources/dark` 的资源限定词自动切换；但运行时修改主题不会影响它。因此需要先对工程中的令牌引用分类。

### 分类规则

| 类别 | 处理方式 | 判定依据 |
|---|---|---|
| 品牌装饰色（图标底、强调块、选中态） | 改读运行时主题色 | 该颜色本身应从属于主题 |
| 语义色（危险、成功、警告） | 保持令牌不变 | 语义固定，不应随主题改变 |
| 令牌对照页、设计规范演示页 | 保持令牌不变 | 该页面职责是展示令牌原值 |

一个色值可能同时出现在两类位置，因此应**按语义逐个判断**，而不是全局替换。

### 验证

分类完成后，工程中仍引用品牌令牌的位置应只剩语义色与演示页两类。改造前先统计引用数量作为基线，改造后再对比。

## 三、第二层：AttributeModifier

当一组样式需要在多处复用时，`AttributeModifier` 是合适的封装方式：

```ts
class PrimaryButtonModifier implements AttributeModifier<ButtonAttribute> {
  applyNormalAttribute(instance: ButtonAttribute): void {
    instance.backgroundColor(/* 取色 */);
  }
}
```

### 限制：它不参与观察

`AttributeModifier` 是普通类，不在组件的观察依赖图中。在其中读取单例的 `@Trace` 字段，字段变化不会触发重渲染，因为没有任何组件依赖它。

### 实现方式：静态中转

将最新色写入普通静态字段，页面重建时重新读取：

```ts
export class ThemeBridge {
  private static accent: string = '';        // 由铺层逻辑写入

  static brand(): ResourceColor {
    return ThemeBridge.accent.length > 0
      ? ThemeBridge.accent : $r('app.color.qj_brand');
  }
}
```

```ts
// modifier 内部
instance.backgroundColor(ThemeBridge.brand());
```

### 使用约束

切换主题后，已渲染的 modifier 样式不会立即更新，需等待页面重建。因此：

- modifier 适合结构性、不常变的样式；
- 若某处必须即时响应主题，应改用读取 `@Local theme` 的自绘组件，不要使用 modifier。

## 四、第三层：运行时主题单例

这是换肤的核心：用一个全局单例保存当前主题状态，组件读取它即可获得当帧响应。

### 单例定义

```ts
@ObservedV2
export class UiThemeManager {
  private static instance: UiThemeManager | undefined = undefined;

  @Trace presetId: string = DEFAULT_PRESET;   // 当前主题包
  @Trace accentColor: string = '';            // 强调色覆盖

  private constructor() {}

  static getInstance(): UiThemeManager {
    if (UiThemeManager.instance === undefined) {
      UiThemeManager.instance = new UiThemeManager();
    }
    return UiThemeManager.instance;
  }
}
```

要点：

- `@ObservedV2` 是类级装饰器（与 V1 的 `@Observed` 不同），使字段可被观察；
- `@Trace` 标注需要通知的字段；
- 构造器私有，保证全局唯一实例。

组件侧接入只需一行：

```ts
@Local theme: UiThemeManager = UiThemeManager.getInstance();
```

`@Local` 的作用是建立依赖：组件订阅了这两个字段，字段变化时读取过它们的位置当帧重渲染。

接入后，读取单例的组件会同时更新：

![切换主题后：取色块与预览组件同步变为新主题色](图片/A5-teal-applied.png)

### 主题包与强调色的叠加关系

两者是叠加而非互斥：强调色优先，其次主题包基准色，最后回退静态令牌。

```ts
brandColor(): ResourceColor {
  if (this.accentColor.length > 0) { return this.accentColor; }
  if (this.presetId === DEFAULT_PRESET) { return $r('app.color.qj_brand'); }
  return resolvePreset(this.presetId).baseHex;
}
```

注意默认主题包一支**回退到 `$r` 令牌**而非硬编码同值 hex，这样深浅色仍由资源限定词负责，两套机制互不干扰。

### 常用取色方法

| 方法 | 用途 | 实现要点 |
|---|---|---|
| `effectiveAccent()` | 返回当前生效的 hex 字符串 | 供取色器、持久化、日志使用 |
| `onBrandColor()` | 品牌色之上的前景色 | 按感知亮度 `0.299R + 0.587G + 0.114B > 0.62` 选择深色或白色 |
| `brandSoftColor()` | 柔和层（chip 底、选中底） | 默认包回退浅色令牌；自定义色用 15% 透明度叠色 |

`onBrandColor()` 保证用户在取色器中选了亮度较高的颜色时，前景文字仍然可读。

### 主题包定义

每套主题包只声明一个基准色，其余令牌由算法派生：

```ts
new Preset('brand',    '品牌蓝', '#0A59F7'),   // 默认，与令牌同值
new Preset('teal',     '青碧',   '#12A594'),
new Preset('violet',   '靛紫',   '#6c4de8'),
new Preset('pink',     '桃粉',   '#D6409F'),
new Preset('contrast', '高对比', '#0A0A0A'),
```

外观页中它们以 chips 形式排列，选中态使用对应主题色描边：

![五套主题包 chips，选中状态与当前生效色](图片/B1-presets-5.png)

若每套主题都手写全部令牌，五套 × 七个令牌会产生 35 个维护点，因此**派生优于枚举**。

### 为什么使用 `@ObservedV2` 而非 `AppStorage`

`AppStorage` 同样可以保存全局状态，但它属于 ArkUI 设施。若组件库要求零 `@kit` 依赖（便于跨工程复用），应采用纯 ArkTS 语言特性 `@ObservedV2` + `@Trace`。其附加优势是字段级观测：只有读取了该字段的组件会重渲染。

## 五、第四层：系统组件默认色

前三层处理应用自绘的颜色。原生控件、系统弹窗、滚动条等位置并非由应用绘制，其默认色来自 ArkUI 全局主题表，需要通过官方接口接管：

```ts
import { ThemeControl, CustomTheme } from '@kit.ArkUI';

ThemeControl.setDefaultTheme({
  colors: { brand: '#12A594' /* ... */ },
  darkColors: { brand: '#4FC3B5' /* ... */ }
} as CustomTheme);
```

建议至少覆盖以下七个令牌，足以处理大部分"看起来不一致"的位置：

```ts
brand, fontEmphasize, iconEmphasize, backgroundEmphasize,
compEmphasizeSecondary, compEmphasizeTertiary, interactiveSelect
```

生效后，系统弹窗中的主按钮也会跟随主题：

![统一对话框：确认按钮随主题变化](图片/A9-dialog-teal.png)

### `colors` 与 `darkColors` 必须成对

只提供 `colors` 时，深色模式仍会使用浅色值，出现亮底亮字的观感问题。两者也不能简单复用，深色版需重新计算：

```
浅色：brand = 基准色；柔和层 = 基准色混 28% 黑
深色：brand = 基准色混 28% 白；柔和层 = 再混 82% 黑
```

### 调用时机与容错

`setDefaultTheme` 需要在 ArkUI 初始化完成后调用（`loadContent` 回调中），并且应包裹 `try/catch`：该调用失败不应阻塞应用启动，前三层仍可正常工作。

## 六、编排与冷启动恢复

四层就绪后，需要一个统一入口按正确顺序铺开，并处理冷启动恢复。

### 铺层顺序

```ts
export class AppThemeApplier {
  private static currentAccent: string = '';

  static brandColor(): ResourceColor {                 // 供无状态样式读取
    return AppThemeApplier.currentAccent.length > 0
      ? AppThemeApplier.currentAccent : $r('app.color.qj_brand');
  }

  static apply(presetId: string, accentHex: string): void {
    const theme: UiThemeManager = UiThemeManager.getInstance();
    theme.setPresetId(presetId);                              // 1. 先写 L3
    theme.setAccentColor(accentHex);
    AppThemeApplier.currentAccent = theme.effectiveAccent();  // 2. 更新静态中转
    AppThemeController.applyPreset(theme.presetId, theme.accentColor);  // 3. 再铺 L4
  }
}
```

顺序不可颠倒：必须先写入单例再计算 `effectiveAccent()`，否则取得的是上一次的值，L4 会被铺成旧主题。

`setDefaultTheme` 具备幂等性（相同颜色短路），因此该方法可以安全地重复调用。

### 冷启动：读取与注入分离

主题值持久化在偏好中，启动时需恢复。建议将「读取」与「注入」分成两步：

```ts
// 启动封装：只读，返回纯数据
static async restoreTheme(): Promise<AppThemeState> { /* 读偏好 */ }

// 各入口 Ability：自行注入
AppBootstrap.restoreTheme().then((state: AppThemeState): void => {
  AppThemeApplier.apply(state.presetId, state.accentHex);
});
```

这样启动封装不依赖任何表现层 API，可被不需要 UI 主题的入口（例如手表）复用。

另外，在外观页的 `aboutToAppear()` 中再调用一次幂等的 `apply()` 是有效的兜底：即使某个入口漏调，用户进入外观页即可补齐。

### 整体效果

铺层完成后，整个窗口应呈现同一套配色，包括宽屏分栏的左右两侧：

![同一窗口切换主题后，列表、内容区与按钮保持同一色系](图片/D5-2in1-teal2.png)

## 七、常见错误与正确写法

以下四项是实现过程中最容易出错的地方，按「错误写法 / 现象 / 原因 / 正确写法」列出。

### 1. 强调色覆盖导致切换主题包无效

**错误写法**：`setAccentColor` 只接受 7 位十六进制色值。

```ts
if (lower.length === 7 && lower.startsWith('#')) { this.accentColor = lower; }
```

**现象**：切换主题包后，选中态与预览色块变化，页面颜色不变。

![该界面处于强调色覆盖主题包的状态：色块显示的是强调色，而非主题包基准色](图片/A1-appearance.png)

**原因**：切换主题包时需要清除强调色覆盖（传入空串），而空串被上述校验忽略，旧强调色仍然生效并压过新主题包。

**正确写法**：将空串定义为「清除覆盖」这一状态。

```ts
setAccentColor(color: string): void {
  const lower: string = color.trim().toLowerCase();
  if (lower.length === 0) { this.accentColor = ''; return; }
  if (lower.length === 7 && lower.startsWith('#')) { this.accentColor = lower; }
}
```

切换主题包时应同时清理内存与持久化值，否则重启后旧强调色会重新生效。

### 2. 组件未接入单例

**错误写法**：组件内直接使用静态令牌。

```ts
.backgroundColor($r('app.color.qj_brand'))
```

**现象**：页面装饰色随主题变化，但该组件保持默认品牌色。

**原因**：组件不认识运行时主题，只能依赖调用方传入颜色，而多数调用点不会传。

**正确写法**：组件自身持有单例，同时保留外部覆盖入口。

```ts
@Local theme: UiThemeManager = UiThemeManager.getInstance();
@Param accentColor: string = '';

private accent(): ResourceColor {
  return this.accentColor.length > 0 ? this.accentColor : this.theme.brandColor();
}
```

两者都保留的原因：仅靠传参容易漏传；仅靠单例则失去局部特调的能力。

### 3. 读取时机不在渲染路径上

**错误写法 A**：在 `@Param` 默认值中读取单例。

```ts
@Param accentColor: string = UiThemeManager.getInstance().effectiveAccent();
```

默认值只在组件构造时求值一次，之后单例变化不会重新计算。应改为 `@Local`，或在 `build()` 中通过方法读取。

**错误写法 B**：在顶层 `@Builder` 中读取单例。

```ts
@Builder
function floatingBall(content: BallContent) {
  .backgroundColor(UiThemeManager.getInstance().brandColor())   // 编译不通过 / 不响应
}
```

顶层 `@Builder` 没有组件上下文，也没有 `this`。正确做法是**在调用侧读取，通过数据对象传入**：

```ts
class BallContent {
  tint: ResourceColor = $r('app.color.qj_brand');
}

// 调用侧
const theme: UiThemeManager = UiThemeManager.getInstance();
content.tint = theme.brandColor();
```

响应式的前提是「读取时登记依赖」。求值时机不在渲染路径上的位置（默认值、顶层函数、无状态类），都需要改为「调用侧读取后传入」。

### 4. 缺少 `darkColors`

**错误写法**：`CustomTheme` 只提供 `colors`。

**现象**：浅色模式正常，深色模式下底色与文字都偏亮。

**原因**：系统在深色模式下取不到对应值，继续使用浅色配置。

**正确写法**：成对提供，并按第五节规则重新计算深色值。

任何配色配置都应确认深色模式下的取值——只写一半的方案很难在浅色环境测试中暴露问题。

---

## 小结

四层模型的落地顺序是：先分类静态令牌，再为无状态样式建立取色通道，然后接入运行时单例，最后用 `ThemeControl` 接管系统组件默认色，并由一个编排入口统一铺开、处理冷启动恢复。

排查换色问题时，可用两句判断快速定位：

> **页面重建后才正确 → 求值时机问题；重建后仍不正确 → 依赖没有接上。**
