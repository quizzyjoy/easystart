# 给自己的应用换一套颜色：HarmonyOS 主题换肤的四层模型实战

这份教程讲的是「用户在外观页点一下青碧，全应用跟着变」这件事在鸿蒙上到底要动几处代码。

它不是概念介绍。你会一行一行地看到：为什么只改一个地方不够、为什么有些位置改了也不生效、为什么有些位置**本来就不该变**。所有结论都对应 `hm_easystart/` 里的现有代码，或者本目录 `图片/` 下的真机、模拟器截图——你可以在自己的仓库里按图索骥，逐条核对。

开工前你需要准备：

1. 一份 [EasyStart](https://github.com/quizzyjoy/EasyStart) 的代码（示例工程在 `hm_easystart/`），能编译能跑；
2. 一台能装应用的设备或模拟器。手机就够，但如果你手上有阔折叠或 2in1，第九节的两个布局坑你会看得更清楚；
3. 大约 40 分钟，最好是一边读一边改。

官方那篇背景文档是 [应用内主题换肤](https://developer.huawei.com/consumer/cn/doc/harmonyos-guides/theme-skinning)，建议先扫一眼标题，再回来跟着做——直接读文档容易记住一堆 API 名字，却不知道它们分别管哪块像素。

## 一、为什么你改了一个颜色，界面上还是一半蓝一半绿

### 1.1 从一次「改完了但没改完」的走查说起

先还原一个几乎每个人都会遇到的场景。

你在外观页把主题切成青碧（`#12A594`），退出来，一个页面一个页面地看。这时候你会看到八种不同的结果，而且它们不是随机的：

- 首页那个圆形图标 chip 的底色、场景强调块、加载动画——**变了**，青绿青绿的；
- 组件示例页的主操作、次操作按钮，还有「品牌标签」——**变了**；
- 统一对话框里那颗「确认」按钮——**变了**；
- 你从来没写过颜色的原生控件（原生 `Toggle` 轨道、系统弹窗的按钮）——也**变了**；
- 但设置页里 HDS 的行卡片底色、行分割线、行尾那个 `>` 箭头——**一点没变**，还是中性灰；
- HDS 的「触感反馈」开关轨道——**也没变**；
- ArkTS 桌面卡片——**没变**；
- 而「危险」按钮还是红的、「成功」标签还是绿的、令牌对照页还是显示原始令牌值——**这些本来就不该变**。

同一个操作、同一套代码、同一时刻，八种结果。如果你不知道这八种结果分别归谁管，接下来的调试就会变成这样：随便挑一处改，改完发现别的又不对了，然后再改回来。

把这张对照表先记在心里（后面每一行都会单独解释）：

| 你看到的位置 | 切主题后 | 谁在管它 |
|---|---|---|
| 首页图标 chip 底、场景强调块、加载动画 | 变 | 运行时主题（L3） |
| 组件示例页的主/次按钮、品牌标签 | 变 | 运行时主题（L3） |
| 统一对话框的「确认」主按钮 | 变 | 运行时主题（L3，按钮自己取色） |
| 你没显式着色的原生控件、系统弹窗 | 变 | 系统组件默认色（L4） |
| HDS 行卡片底 / 分割线 / chevron | 不变 | HDS 私有 token（第八节坑 7） |
| HDS `SuffixSwitch` 开关轨道 | 不变 → 显式传色后才变 | HDS 私有 token（第八节坑 7） |
| ArkTS 桌面卡片 | 不变 | V1 卡片框架（第八节坑 6） |
| 危险/成功/警告、令牌对照页 | 不变（本就不该变） | 静态令牌与语义色（L1） |

先把「没换主题时的样子」也存一张，这是你后面所有对照的基线——默认品牌蓝 `#0A59F7` 的首页：

![默认品牌蓝 #0A59F7 下的首页：图标 chip、卡片强调块都是品牌蓝](图片/B2-home-brandblue.png)

### 1.2 四层模型：这是四支不同的笔，不是四个优先级

很多人第一反应是：「是不是有四个层级，优先级高的盖住优先级低的？那我合成一张大 token 表，让所有层都读它，就全变了。」

这个想法会把你带进沟里。因为这四层**画的不是同一个东西**，它们更像四个人拿着四支笔，各画各的纸：

**L1 静态令牌——印刷厂提前印好的色卡。**

你在 `AppScope/resources/base/element/color.json` 里写的 `qj_brand`，名字和值在**编译期**就被固化进包里了。好处是零运行时开销、写错名字立刻编译报错；坏处是运行期没有任何公开 API 能改它的值。它能做的唯一一件"动态"的事，是跟着 `resources/dark/` 这个限定词目录换色——也就是随深浅色变，不随你换主题变。

**L2 AttributeModifier——一次性贴纸。**

`AttributeModifier` 是一个普通类，里面有个 `applyNormalAttribute(instance)`，ArkUI 在需要的时候把属性贴到组件上。贴纸贴上去的那一刻用的是当时的值，之后没人通知它"颜色变了，重贴一遍"。

**L3 运行时主题——会自己刷新的电子屏。**

`UiThemeManager` 是个 `@ObservedV2` 单例，里面的 `accentColor` / `presetId` 带 `@Trace`。任何 `@ComponentV2` 组件用 `@Local` 持有它，就自动建立了依赖：字段一变，读它的组件当帧重渲染。这是"你改设置、界面立刻变"的唯一来源。

**L4 系统组件默认色——系统设置里的那套默认值。**

`ThemeControl.setDefaultTheme()` 改的是 ArkUI 的**应用内默认主题**：凡是组件自己没写颜色的地方，都从这里取。你不设，那些地方就恒为系统蓝。

把这四层摆在一起看，它们的边界就清楚了：

| 层 | 机制 | 谁决定颜色 | 只改这一层会怎样 |
|---|---|---|---|
| **L1 静态令牌** | `$r('app.color.qj_*')` + `resources/dark` 限定词 | 资源编译器，编译期固化 | 只随深浅色变，不随主题变 |
| **L2 AttributeModifier** | `AttributeModifier` 族（普通类） | `applyNormalAttribute` 里写的值 | 改主题后不重跑，要等页面重建 |
| **L3 运行时主题** | `UiThemeManager`（`@ObservedV2` + `@Trace`） | 运行时单例 | 只有读了它的组件会变 |
| **L4 系统组件默认色** | `ThemeControl.setDefaultTheme(CustomTheme)` | ArkUI 的 token 表 | 不设则系统组件恒为系统蓝 |

看清这张表，你就明白为什么"合成一张大 token 表"不成立：L1 的值在编译期就烧进包里了，L4 读的是 ArkUI 自己的 token 表，HDS 组件又读它自己那套私有 token——它们压根不是同一个来源，不可能被一张表统一。

所以真正要建立的直觉是：**L1 管编译期，L2 管样式封装，L3 管自绘组件的即时响应，L4 管系统组件的兜底默认。** 改颜色之前先问自己一句"这块像素是谁画的"，比记住 API 名字有用得多。

### 1.3 遇到「没跟着变」，按这个顺序自问

以后每次发现某处没变色，别急着翻代码，按顺序问，第一个命中就停：

1. **它是危险/成功/警告这类语义色吗？** 是的话，它本来就不该变，结束。切到「高对比」主题时，用户必须还能一眼看出哪颗按钮是危险操作。
2. **它是系统组件吗？**（系统弹窗按钮、原生控件轨道、填充式原生按钮）→ 去查 L4 有没有真的设上（第五节）。
3. **它是 HDS 组件吗？**（`HdsListItemCard`、`SuffixSwitch` 这些）→ HDS 读自己的私有 token，只能逐个显式传色（第八节坑 7）。
4. **它是自绘组件吗？** → 查它有没有真的读到 `UiThemeManager`（第四节）。
5. **它由 `AttributeModifier` 决定吗？** → 那是 L2 的静态中转没更新，或者页面没重建（第三节）。
6. **以上都不是** → 它就是 L1 里写死的引用，按第二节的规则分级处理。

这个顺序的价值在于：它把"为什么不变"从玄学变成了六个可判定的分支。你会发现绝大多数"主题失效"的 bug，在第 1 步和第 3 步就被排除掉了。

### 1.4 深浅色和换肤是两件正交的事

还有一个概念必须先拧清楚，否则后面全是浆糊。

**深浅色**决定"底色是白还是黑"，它由系统 `ColorMode` 驱动，在 EasyStart 里由 `ColorModeManager` 管理。**换肤**决定"品牌色是什么"，由上面那四层管。

两条链路互不驱动：切主题不会改显示模式，切显示模式也不会改主题。正因为如此，L1 令牌才能安稳地承担"随深浅色变"那部分颜色——它靠限定词切换，跟主题没关系：

| 令牌 | `base` | `dark` |
|---|---|---|
| `qj_brand` | `#0A59F7` | `#317AF7` |
| `qj_brand_light` | `#E8F0FE` | `#1D2B45` |
| `qj_on_brand` | `#FFFFFF` | `#FFFFFF` |

（这三行就在 `hm_easystart/AppScope/resources/{base,dark}/element/color.json` 里。）

注意 `qj_brand` 在暗色下是 `#317AF7`——比 `#0A59F7` 亮一档。这不是随手写的：品牌蓝在暗底上会显得发闷，提亮一档才够清楚。记住这个"提亮"动作，第四节和第五节会各出现一次它的变体。

### 1.5 动手：先量一遍自己的工程

改之前先拿基线数字，不然你不知道"改完了"是什么样。

以下命令在工程根（`hm_easystart/`）执行，排除依赖和构建产物：

```powershell
Get-ChildItem . -Recurse -Include *.ets | Where-Object { $_.FullName -notmatch 'oh_modules|\\build\\' } |
  Select-String -Pattern 'qj_brand' -List
Get-ChildItem . -Recurse -Include *.ets | Where-Object { $_.FullName -notmatch 'oh_modules|\\build\\' } |
  Select-String -Pattern 'ThemeControl.setDefaultTheme'
```

第一条给你"还有多少文件没进体系"，第二条回答"L4 到底建起来没有"。

**预期看到什么**：第一条会列出十几个文件；第二条应该只有 `AppThemeController.ets` 一个文件命中（也就是 L4 已经建好了）。如果第二条什么都没打印，说明 L4 还没接，第五节的活你必须做。

同时报告两个数：**处数**和**文件数**。处数说明工作量，文件数说明影响面，两者不会相等——一个文件里可能塞了五处硬引用。

还有一类引用最隐蔽，用 `qj_brand` 是搜不出来的：`$r('sys.color.*')` 和十六进制字面量。它们视觉上就是"本该跟主题、却始终是系统蓝"的那部分，比如组件示例页搜索框右边那个「取消」。这类只能靠逐屏对照发现——所以第 1.1 节那张对照表才是你真正的检测清单。

### 常见错误自查

- [ ] 我以为四层是"优先级覆盖"关系，正打算合成一张大 token 表统一管理。
- [ ] 我改完只截图了"改后"的样子，没有留"改前"的基线图。
- [ ] 我只统计了 `qj_brand` 命中处数，没统计文件数，评估工作量时按处数算了。
- [ ] 我没查 `$r('sys.color.*')` 和裸十六进制，以为搜完 `qj_brand` 就干净了。

### 本节小结

同一次换色出现的八种结果，对应四种不同来源的着色机制，而不是四种优先级；判断"这块像素谁画的"，比记住任何一个 API 都重要。

**动手练习**：在你自己的工程里跑 1.5 的两条命令，把两个数字记在便签上。然后切一次主题，逐屏走一遍，试着给每一处"没变"的位置归到 L1/L2/L3/L4/HDS/语义色里——归不进去的那一处，就是后面某节要讲的地方。

## 二、L1 静态令牌：哪些 `$r` 该留着，哪些必须搬走

### 2.1 令牌的本事和天花板

你 grep 完 `qj_brand`，会得到一屏结果。这时候最容易做的决定是：全部换成十六进制，或者全部换成 `theme.brandColor()`。两个都不对。

先把 L1 的能力边界说清楚。

**它能做三件事**：随 `resources/dark/` 限定词切换深浅色；编译期校验名字，写错立刻报错；零运行时开销。

**它做不到三件事**：随用户在设置页改的颜色变化（运行期没有公开 API 改它的值）；表达"一套主题包"的多色关系（一个令牌只有一个值）；在没有编译期资源系统的场合复用（比如你想在纯 TS 里算颜色）。

所以 L1 的正确定位是：**承载"不随换肤变、但要随深浅色变"的颜色，以及"必须精确控制、不接受任何覆盖"的颜色。**

### 2.2 三类位置：搬走、留着、永不跟

把仓库里的每一处 `$r('app.color.qj_brand')` 归到下面三类之一，规则就定死了。

**A 类·品牌主体 → 必须搬到运行时。**

语义是"品牌强调"、换肤后应该跟着变的位置：首页图标 chip 的底色、场景强调块、选中态底、加载动画主色。改法不是把 `$r` 换成 hex，而是把**读取源**换成 `theme.brandColor()` / `theme.brandSoftColor()`——具体怎么读见第四节。

**B 类·演示/对照 → 保留 `$r`。**

有些位置存在的意义**就是展示令牌本身**。比如 `features/DemoFeature/src/main/ets/view/DesignTokensView.ets` 的令牌对照区：它必须显示 `qj_brand` 的真实值，跟着主题变就等于把这个页面的功能毁了。同类还有组件示例页里的令牌展示、以及 ArkTS 卡片里的颜色（第八节坑 6 会讲为什么）。

**C 类·语义色 → 永不跟主题。**

危险、成功、警告、中性。这类颜色一旦被主题色覆盖，用户切到「高对比」（`#0A0A0A`）时就分不清哪颗按钮是危险操作了。语义色的价值恰恰在于"它不随风格漂移"。

下面这张图同屏验证了 A、C 两类同时成立：主操作、次操作、加载中、品牌标签都转成了青碧（A 类已迁），危险按钮还是红、成功标签还是绿（C 类没动）。

![组件示例页：品牌类全部转青碧，危险保持红、成功保持绿](图片/A8-components-teal2.png)

顺便留个心眼：同一张图里，搜索框右侧的「取消」还是系统蓝。这就是 1.5 说的"检索 `qj_brand` 扫不出来的遗漏"——它靠 `sys.color` 或默认色取色，只能逐屏对照抓。

### 2.3 跟着做：把一个 A 类位置迁走

拿首页卡片上那个圆形图标 chip 举例，三步。

**第一步，换读取源。** 先确认这个组件已经持有单例：

```
@Local theme: UiThemeManager = UiThemeManager.getInstance();
```

再改底色和它的取色：

```
Column()
  .backgroundColor(this.theme.brandSoftColor())   // 原来是 $r('app.color.qj_brand_light')
```

这块代码一共两行：第一行建立观察（组件变 `@ComponentV2` 后，`@Local` 持有单例就会订阅 `@Trace` 字段）；第二行把底色从"编译期令牌"换成"运行时算出来的柔和层"。为什么底色用 `brandSoftColor()` 而不是 `brandColor()`？因为 chip 是"浅色底 + 深色图标"的结构，用满强度品牌色会把它压成一个实心色块，跟原来 `qj_brand_light` 的观感对不上。

**预期看到什么**：切到青碧后，这颗 chip 的底色立刻变成淡青（`#26` 前缀的 15% 透明叠色），而不是实心青绿。

**第二步，补前景色。** 压在这块底上的图标或文字，同步换成 `this.theme.onBrandColor()`。这一步最容易被跳过，后果在深色主题下立刻显形：高对比主题（`#0A0A0A`）是深底，如果前景还写死白色就还好，但如果前景跟着成了深色，就是深底深字，什么都看不见。

**第三步，确认没顺手改语义色。** 同一个文件里如果还有 `app_danger` / `app_success` / `app_warning` 这类令牌，保持 `$r` 原样。迁 A 类时最容易连带把它们一起换掉——因为它们在代码里就挨着，看着都像"品牌色"。

**预期看到什么**：危险按钮在青碧、高对比两套主题下都是同一个红。

### 2.4 为什么默认主题包必须回退 `$r`

现在来看 `brandColor()` 里那个让人困惑的分支。它的判断不是"有强调色用强调色、否则一律返回 hex"，而是三段：

```
有强调色                  → 返回强调色 hex
无强调色 且 主题包 = brand → 返回 $r('app.color.qj_brand')
无强调色 且 主题包 ≠ brand → 返回该主题包的 baseHex
```

中间那一条是刻意的，不是漏写。**默认主题包必须保住深浅色**：品牌蓝在暗色下要提亮到 `#317AF7`，而这个提亮是由 `resources/dark/element/color.json` 的限定词完成的。如果这里直接返回 `#0A59F7`，暗色下就是"暗底 + 偏暗蓝"，用户会觉得主题发灰。

由此带来一个**已知偏差**，你迟早会碰到：非默认主题包返回的是同一个 hex，不走 `dark` 限定词，所以自绘品牌色在暗色下不会自动提亮。系统组件那一层不受影响（L4 的 `darkColors` 会负责提亮，见 5.5）。

这是取舍的必然结果，不是缺陷：要么让默认包享受限定词、非默认包牺牲暗色提亮；要么反过来把所有主题都改成两套 hex，代价是每加一套主题要维护两个值。

### 常见错误自查

- [ ] 我把 A 类位置的 `$r` 直接换成了 hex 字面量（而不是换成 `theme.brandColor()`）。
- [ ] 我改了品牌底色，但没改压在上面的前景色。
- [ ] 迁移时把同一个文件里的 `app_danger` / `app_success` 一起换掉了。
- [ ] 我去掉了 `brandColor()` 里"默认包回退 `$r`"那个分支，理由是"多一个分支没必要"。

### 本节小结

L1 不是"过时的写法"，它是深浅色的唯一承载者；要搬走的只是"品牌主体"这一类，演示位和语义色必须原样保留。

**动手练习**：把 `hm_easystart` 里检索到的 `qj_brand` 逐条标成 A / B / C，只改一条 A 类，然后切主题包 + 切深浅色各走一遍——A 类应该两次都变，B、C 类两次都不变。

## 三、L2 AttributeModifier：样式函数读不到 `@Trace`，怎么办

### 3.1 先把 modifier 想成"一次性贴纸"

`AttributeModifier<T>` 是 ArkUI 提供的一种"样式封装"手段：你把一组属性写进一个普通类，然后挂到组件上：

```
Text('保存')
  .attributeModifier(new AppButtonGhostModifier())
```

框架在需要的时候调 `applyNormalAttribute(instance)`，把你的样式一次性写进 `instance`。

这套机制很适合"一组属性复用到多处"：描边宽度、圆角、内边距、字重——这些是**应用级规范**，不该在每个调用点重复写。EasyStart 的 `commons/AppComponent/src/main/ets/modifier/` 下就有这么一族：`AppButtonModifier`、`AppDividerModifier`、`AppIconButtonModifier`、`AppImageModifier`、`AppInputModifier`、`AppProgressModifier`、`AppTextModifier`。

但"一次性"这三个字，就是它和主题的矛盾所在。

### 3.2 为什么在里面读单例没用

你第一次遇到这个问题，代码大概长这样：

```
applyNormalAttribute(instance: ButtonAttribute): void {
  instance.backgroundColor(UiThemeManager.getInstance().brandColor());
}
```

编译能过，首帧颜色也是对的。但你去外观页换成青碧，回来一看——还是蓝的。

两个原因叠在一起：

**第一，调用时机不由你决定。** `applyNormalAttribute` 是框架在"应用属性"时调的，典型时机是首次构建和组件重建。主题单例里的 `@Trace` 字段变化，根本不在它的触发条件里。

**第二，它不在观察依赖图里。** `AttributeModifier` 是普通类，不是 `@ComponentV2`，没有 `@Local`，框架不知道它读过哪个 `@Trace` 字段。所以你读到的是"调用那一瞬间的值"，之后没有任何机制会再叫它一次。

这里有个很有用的判别信号，后面第八节还会用到：**如果"重建页面就对了"，那是求值时机问题；如果"重建也不对"，那是根本没连上。** 这一节属于前者。

### 3.3 正解：静态中转 + 一次页面重建

既然 modifier 拿不到"变化通知"，那就别指望通知，改成"每次重建时去读一个最新的值"。EasyStart 的做法是在 `commons/AppComponent/src/main/ets/theme/AppThemeApplier.ets` 里放一个静态字段当中转站：

```
private static currentAccent: string = '';

static brandColor(): ResourceColor {
  return AppThemeApplier.currentAccent.length > 0
    ? AppThemeApplier.currentAccent
    : $r('app.color.qj_brand');
}
```

三行代码，各管一件事：

- `currentAccent` 是"最近一次生效的品牌色"，默认空串表示没设置过；
- 空串时回退 `$r('app.color.qj_brand')`，这样还没走过主题流程的页面也是品牌蓝，不会白屏或黑块；
- 非空时返回 hex——`ResourceColor` 同时接受 `Resource` 和字符串颜色，所以这个三元的两边类型是兼容的。

**写**的位置只有一处：`AppThemeApplier.apply()` 里那一行 `currentAccent = theme.effectiveAccent()`，它和 L3、L4 在同一次调用里完成。**读**的位置是所有 modifier 族的 `applyNormalAttribute`，你 grep `AppThemeApplier.brandColor` 会看到 `AppButtonModifier`、`AppDividerModifier`、`AppIconButtonModifier`、`AppInputModifier`、`AppProgressModifier` 都在读它。

**刷新靠什么**：modifier 实例通常在页面 `build()` 里 `new` 出来，页面重建时会重新执行 `applyNormalAttribute`，此时读到的就是最新静态值。典型的"重建"触发点是：从外观页返回、系统深浅色切换。

源码注释把这条限制写得很直白——**改色后需要一次页面重建才刷新**。这不是懒，是这个机制的上限。

### 3.4 备选：给构造参数留个口子

有时候某个调用点就是想特调一个颜色（比如某个进度条要固定成灰色）。`AppProgressModifier` 的做法是让构造参数的默认值取静态中转：

```
constructor(color: ResourceColor = AppThemeApplier.brandColor(),
            trackColor: ResourceColor = $r('app.color.app_fill_medium')) {
```

好处是特调不必绕开体系，坏处是每个调用点都要自己决定传不传，漏传就静默走默认值，没有编译期保护。

EasyStart 的选择是"静态中转做默认，构造参数留口子"——两条路都开着，但默认路径永远是最省事的那个。

### 3.5 什么时候别用 modifier

| 场景 | 选择 |
|---|---|
| 一组属性复用到多处（描边 + 圆角 + 内边距） | 用 modifier + 静态中转 |
| 需要**即时**响应主题（不重建页面就变） | **别用 modifier**，改成读 `@Local theme` 的自绘组件 |
| 令牌对照 / 演示（要展示固定色） | 用 modifier，但色值写死 |
| 只有一个属性 | 直接写属性，不必上 modifier |

第二行是关键判断。如果你做的是一个"用户拖动色轮、界面实时跟着变"的页面，modifier 一定会让你失望，因为它要等重建。这种情况请直接写组件（第四节）。

### 3.6 两条靠人守的纪律

**第一，单一写入点。** 只允许 `AppThemeApplier.apply()` 写 `currentAccent`，其它任何位置都不许赋值。一旦有第二处写入，你就会得到一个极难查的 bug：某个页面用自己的颜色覆盖了全局，退出该页后全应用还是那个颜色。

**第二，顺序不能反。** `apply()` 里必须**先** `setPresetId` / `setAccentColor`，**再**取 `effectiveAccent()` 写静态。反了写进去的是上一次的值——首帧看着对，第二次切换永远慢一拍。

这两条都没有类型系统保护，只能靠"唯一入口 + 注释 + 回归项"维持。所以它们必须进你的回归清单，而不是留在某个人的记忆里。

### 常见错误自查

- [ ] 我在 `applyNormalAttribute` 里直接读 `UiThemeManager.getInstance()`，并期待它随主题变化。
- [ ] 我发现了"切走再回来才对"，但把它当成偶发 bug 而不是求值时机问题。
- [ ] 我在 `apply()` 里先取了 `effectiveAccent()`、后写的 `setAccentColor`。
- [ ] 我在某个页面里给 `currentAccent` 赋了值，理由只是"这里想特殊一点"。

### 本节小结

`AttributeModifier` 是样式函数容器而不是响应式组件，所以主题色只能经静态字段中转，并在页面重建时生效；要即时响应，就换自绘组件。

**动手练习**：用 `AppButtonPrimaryModifier` 渲染一颗按钮，切主题后退出外观页再进入，确认颜色是新的；然后在同一屏放一颗 `CommonButton` 与它对照，重建后两者颜色应当一致。连续切两个主题（青碧 → 桃粉），每次都在重建后检查，确认没有"停在上一套颜色"的错帧。

## 四、L3 `UiThemeManager`：让自绘组件「自己」换色

### 4.1 一个单例，两个字段

先看这个东西长什么样。文件在 `hm_easystart/quizzyjoy/VitalUI/src/main/ets/theme/UiThemeManager.ets`：

```
@ObservedV2
export class UiThemeManager {
  private static instance: UiThemeManager | undefined = undefined;
  @Trace accentColor: string = '';
  @Trace presetId: string = DEFAULT_THEME_PRESET;
  private constructor() {}
  static getInstance(): UiThemeManager { /* 懒建单例 */ }
}
```

逐行读：

- `@ObservedV2` 让这个类"可被观察"——它是**类级**装饰器，不是 V1 的 `@Observed`；
- `@Trace` 标在两个字段上，表示"这两个字段变了，要通知读过我的组件"；
- 构造器私有，外面只能走 `getInstance()`，保证全应用只有一份主题状态；
- `presetId` 的初值是 `DEFAULT_THEME_PRESET`（即 `'brand'`），所以应用刚起来、什么都没设的时候是品牌蓝——这个默认值在 6.5 讲冷启动时序时还会出现一次。

组件侧用它只需要一行：

```
@Local theme: UiThemeManager = UiThemeManager.getInstance();
```

`@Local` 在这里的作用不是复制一份数据，而是**建立依赖**：这个 `@ComponentV2` 从此订阅了 `accentColor` 和 `presetId`。字段一变，读它的地方当帧重渲染。

### 4.2 为什么不用 `AppStorage`

`AppStorage` 也能存全局状态，看起来更"官方"。不用它的原因不在功能，而在**模块纪律**。

EasyStart 的分层是 `quizzyjoy` 三库（Foundation / Platform / VitalUI）→ `commons` → `features` → `product`。其中 VitalUI 是"原语库"，它的规矩是**零 `@kit`**：不 import 任何系统 kit，这样换一个 app、甚至换一个系统版本，它都能原样搬走。

`@ObservedV2` + `@Trace` 是纯 ArkTS 语言特性，不碰任何 kit；而 `AppStorage` 相关能力属于 ArkUI 的全局设施。选前者，原语库就保住了"纯组件库"的身份。

顺带的好处是**字段级观测**：`@Trace` 标在字段上，只有读了该字段的组件会重渲染，不像某些粗粒度方案那样一改就全树抖一遍。

### 4.3 两个字段是叠加关系，不是二选一

这是最容易理解错的一处。

| 字段 | 类型 | 语义 |
|---|---|---|
| `accentColor` | `string` | 用户自选的强调色 `'#RRGGBB'`；**空串 = 没有覆盖** |
| `presetId` | `string` | 当前主题包 id；空串按默认包处理 |

用摄影打比方：**主题包是"整卷胶片的色调"**，它决定整套基线；**强调色是"在某张照片上单独拉的一下滑块"**，它是单点微调。两者不是互斥的两个选项，而是"基线 + 微调"的叠加。

优先级固定：**强调色 > 主题包**。这条优先级本身没问题——问题出在"用户想清掉微调、只留基线"的时候，你有没有给他一条路。这条路的入口就是空串，见 4.5。

### 4.4 四个取色方法，四条不同的回退链

别被"四个方法"吓到，它们的差别只在"回退到哪"。记住一张表就够了：

| 方法 | 返回 | 回退链 |
|---|---|---|
| `effectiveAccent()` | `string` hex | 强调色 → 主题包 `baseHex` |
| `brandColor()` | `ResourceColor` | 强调色 → 默认包 `$r('app.color.qj_brand')` → 非默认包 `baseHex` |
| `onBrandColor()` | `ResourceColor` | 默认包且无强调色 → `$r('app.color.qj_on_brand')`；否则按感知亮度选 `#0A0A0A` / `#FFFFFF` |
| `brandSoftColor()` | `ResourceColor` | 默认包且无强调色 → `$r('app.color.qj_brand_light')`；否则 `#26` + 品牌色 |

第一行和第二行的区别值得单独说：`effectiveAccent()` 永远给**具体颜色字符串**，适合"我要拿这个色去算点别的"（比如传给取色器当前值、写进静态中转）；`brandColor()` 给 `ResourceColor`，在默认包时可以回退成资源引用，从而保留深浅色限定词的能力（这就是 2.4 那条分支的意义）。

**`onBrandColor()` 是这套体系里最像"常识"的一个方法。** 它的逻辑是：把品牌色拆成 R/G/B，按 sRGB 加权算一个感知亮度（`0.299R + 0.587G + 0.114B`），阈值取 `0.62`，亮底配深字（`#0A0A0A`），暗底配白字（`#FFFFFF`）。

为什么要这么麻烦？因为用户可以选任意颜色。桃粉（`#D6409F`）偏亮，压白字会发糊；高对比（`#0A0A0A`）几乎没有亮度，压白字才清楚。如果前景写死白色，你会在某套主题上看到"糊成一片"的按钮文字——那是用户投诉里最难解释的一类：**"我没改任何设置，字怎么看不清了？"**

**`brandSoftColor()` 给的是"柔和层"，不是满强度色。** 非默认包时它返回 `#26` + 品牌色，也就是 15% 透明度的叠色。为什么不用满强度？因为 chip 底、选中底这类位置原来是 `qj_brand_light` 那种浅色，直接铺满强度品牌色会把它们压成实心块，视觉层级一下子塌掉。用带 alpha 的叠色，深浅色两种背景下都成立。

### 4.5 `setAccentColor` 的三态：空串是语义，不是非法输入

这个方法的完整逻辑只有三种情况：

```
''                  → accentColor = ''（清除覆盖，回退主题包）
'#rrggbb'（7 位）    → 生效（trim + 转小写）
其它                → 忽略，保持原值
```

中间那行的细节：先 `trim()` 去掉两端空格，再 `toLowerCase()` 统一小写。这样 `'#12A594'` 和 `' #12a594 '` 都会被接受并归一化成后者，你后面比较字符串时不会因为大小写踩坑。

关键是第一行。**空串在这里是一个语义**——"清除覆盖"，而不是"用户输错了"。如果你把它当非法输入直接忽略，就会得到一个很具体的后果：**切主题包时清不掉上一套的强调色**，于是新的主题包永远被旧强调色压着，界面上看起来"点了青碧没反应"。

这个坑值得先说结论：它是第八节的坑 1，一个把"语义缺陷"伪装成"UI 缺陷"的典型案例。

配套的三个方法各管一件事，别混用：

| 方法 | 行为 |
|---|---|
| `setAccentColor('')` | 清除强调色，回退到**当前主题包**基准色 |
| `setPresetId('')` | 空串回退默认包 `brand` |
| `reset()` | 双清：`accentColor = ''` + `presetId = DEFAULT_THEME_PRESET` |

注意第一个和第三个的区别：前者只清强调色，主题包不动；后者连主题包一起回默认。你的"恢复默认"按钮想表达哪一个，取决于文案（7.4 会细说）。

### 4.6 组件侧两种读取范式

同样是"读主题"，**库内原语**和**应用级组件**走的是两种写法，原因很实际。（v3.48 起 `CommonButton` / `CommonTag` / `ActionCard` 已从 VitalUI 迁入 AppComponent：**应用级封装放 AppComponent，VitalUI 只留图表、Loading、取色器这类自定义组件**。）

**库内原语**（VitalUI 的 `CommonLoading` / `CommonColorPickerSheet` / 图表族）与应用级组件（`CommonButton` / `CommonTag` / `ActionCard`，已在 AppComponent）：自持 `@Local theme`，**同时**开一个 `@Param accentColor: string`，空串时回退 `brandColor()`。取色器 `CommonColorPickerSheet(Sheet)` 类似，但它自持单例、当前色由调用侧经 `@Param color` 传 `effectiveAccent()`。

为什么要两个都留？只靠 `@Param`，页面必然大量漏传（"注入面覆盖了"和"界面显示正确"是两件事）；只靠单例，就失去"某处特调成别的色"的能力。

`CommonButton` 是标准样本：

```
@Local theme: UiThemeManager = UiThemeManager.getInstance();   // 建立观察
@Param accentColor: string = '';                                // 允许页面覆盖
// 取色：this.accentColor.length > 0 ? this.accentColor : this.theme.brandColor()
```

三行分别对应：订阅、开口子、三元回退。注意最后那个三元的回退目标是 `brandColor()`（含主题包判断），所以这个写法是**对的**。反面写法是"空串直接跳 `$r`"——那样会漏掉"当前是哪个主题包"这一层，非默认包下按钮永远是品牌蓝。

**AppComponent 控件工厂**（`AppToggle` / `AppCheckbox` / `AppSlider` / `AppRadio` / `AppSelect` / `AppSegment` / `AppSearch` / `AppCounter` / `AppGauge` / `AppProgress` / `AppLoadingProgress` / `AppFormField` / `AppTextArea`）：内部 `@Local theme = UiThemeManager.getInstance()`，**不给外部口子**。

原因也很实际：这些是原生控件的封装，选中色需要逐点覆盖（轨道、滑块、勾选标记……），如果让页面传参，漏传的面会大到你根本查不完。干脆内部读，页面只当使用者。

### 4.7 五套主题包，一套只声明一个色

主题包的数据在 `hm_easystart/quizzyjoy/Foundation/src/main/ets/theme/AppThemePreset.ets`，纯数据 + 纯函数，零 `@kit`：

| id | 名称 | `baseHex` |
|---|---|---|
| `brand` | 品牌蓝（`DEFAULT_THEME_PRESET`） | `#0A59F7` |
| `violet` | 靛紫 | `#6c4de8` |
| `teal` | 青碧 | `#12A594` |
| `pink` | 桃粉 | `#D6409F` |
| `contrast` | 高对比 | `#0A0A0A` |

一套主题包只声明**一个颜色**。其余层级（强调底、描边、选中态）由 L4 按比例派生出来（第五节）。新增一套主题 = 加一行数据，这是"只声明一个色"最直接的兑现。

`resolveThemePreset(id)` 对未知 id 回退到第一套（品牌蓝）。这条容错很重要：持久化的 `presetId` 可能来自旧版本（比如以后你删掉了某套主题），读到一个不认识的 id 时不能崩，也不能变成透明——回退品牌蓝是最安全的行为。

顺便说一句：默认包就是原来的 `qj_brand` 令牌值 `#0A59F7`，所以整套改造做完之后，**默认观感和改造前完全一致**。这一点在迁移时特别有用——你可以随时判断"是我改坏了，还是本来就这样"。

### 4.8 动手：切到青碧，看三个预览控件

把主题包切到青碧后，外观页自己的预览区（主按钮 / 描边按钮 / 品牌标签）应当立刻转青碧——它们读的是 `effectiveAccent()`。

![切青碧后的外观页：预览区三个控件转为青碧，取色块显示 #12A594](图片/A5-teal-applied.png)

**这张图是旧版本界面**：只列了 4 套主题包（品牌紫 / 青碧 / 桃粉 / 高对比），紫色那套当时叫「品牌紫」。当前源码是 5 套、紫色叫「靛紫」、id 为 `violet`——用 B1 那张图对照就能看到差别。另外这张图里「更换」二字还是系统蓝，当前源码该处已经改成读 `theme.brandColor()`，所以在 B1、D5 里它跟着主题变色了。

接着验证三件事：

1. **改强调色**（取色器里选一个）→ 自绘组件应当立即变，不需要重建页面，因为它读的是 `@Trace` 字段；
2. **只切主题包、不设强调色** → 自绘组件也应当变，这验的是 `brandColor()` 的中间那条分支；
3. **打开任意页的 `AppToggle`，切主题后看选中轨道** → 应当立即变色，这验的是控件工厂范式（内部 `@Local theme`）。

### 常见错误自查

- [ ] 我在组件里用 `@Param` 传主题色，且以为 `@Param` 能订阅单例变化。
- [ ] 我把 `onBrandColor()` 当成"永远白色"，于是在桃粉主题上看到糊掉的文字。
- [ ] 我用 `brandSoftColor()` 的地方直接铺了满强度品牌色，chip 变成了实心块。
- [ ] 我在切主题包时忘了清强调色，然后开始怀疑是主题包没生效（见坑 1）。
- [ ] 我给控件工厂加了个 `accentColor` 参数，理由是"这样更灵活"。

### 本节小结

L3 的价值是把"用户改一个值"变成"所有订阅者当帧重渲染"，代价是每个读它的组件都必须显式建立依赖；四个取色方法只是四条不同的回退链，别混用。

**动手练习**：临时把 `onBrandColor()` 的阈值从 `0.62` 改成 `0.2`，切到桃粉和青碧各看一遍文字对比度，然后再改回来。你会立刻理解这个阈值在防什么。

## 五、L4 `ThemeControl`：把「一个色」翻译成一套 token

### 5.1 这一层管的，正是你没写过颜色的地方

到这里你可能会问：L1 管编译期、L3 管自绘组件，那我**没写颜色**的那些组件呢？

比如你随手放一个原生 `Toggle()`，不写任何颜色；比如系统弹窗的主按钮；比如输入框的光标。这些地方你没写色，ArkUI 就用默认主题——默认是系统蓝，跟你的品牌色没关系。

`ThemeControl.setDefaultTheme(CustomTheme)` 改的就是这个"应用内默认主题"。设了，那些地方就跟随品牌色；不设，恒为系统蓝。

但这里有个极易误判的点，必须先说清楚。这张图是统一对话框，主按钮「确认」是青碧色的：

![统一对话框：确认按钮为青碧主按钮变体](图片/A9-dialog-teal.png)

它**不是** L4 的功劳。这颗按钮是 `CommonButton`（`PRIMARY` 变体）渲染的，走的是 L3 显式取色。L4 的效果在这张图里根本看不到。

所以分工要这么记：

| 位置 | 谁在着色 |
|---|---|
| `CommonButton` 渲染的按钮（含统一对话框的「确认」） | **L3**，它显式取 `brandColor()` |
| `AppToggle` / `AppSlider` 等控件工厂 | **L3**，工厂里逐点覆盖了选中色 |
| 未显式着色的原生控件、系统弹窗 | **L4**，读应用默认主题 |
| HDS 组件 | 都不行，见第八节坑 7 |

这就是为什么 L4 在 EasyStart 里"效果不如 L3 抢眼"：绝大多数可见色块都走了显式路径。**L4 的真正价值是"以后新加一个没着色的原生控件时，不用再补一层代码"。**

顺带提醒一个取证方法上的坑：想验证 L4 是否生效，**不要拿自绘按钮当证据**——那验的是 L3。唯一直接的取证方式是临时放一个不设颜色的原生 `Toggle()`，切主题看它的轨道跟不跟。

### 5.2 API 形态与版本门槛

`ThemeControl` 来自 `@ohos.arkui.theme`。EasyStart 在 `hm_easystart/quizzyjoy/Platform/src/main/ets/theme/AppThemeController.ets` 里把它再导出一次，这样上层就不用满世界 import `@kit`：

| 类型 / 方法 | 语义 |
|---|---|
| `CustomTheme` | `{ colors?: CustomColors; darkColors?: CustomDarkColors }` |
| `CustomColors` / `CustomDarkColors` | 都是 `Partial<Colors>`，只覆盖你需要的 token |
| `ThemeControl.setDefaultTheme(theme)` | 设置应用内默认主题；传 `undefined` 清除 |

版本门槛要记住：`colors` 是 `@since 12`，`darkColors` 是 `@since 20`。这两个数字来自本机 SDK 的 `@ohos.arkui.theme.d.ts`。如果你的工程把 `compatibleSdkVersion` 降到 20 以下，`darkColors` 会直接编译失败——不是运行时才出问题，而是根本编不过。

### 5.3 为什么只覆盖 7 个 token

`Colors` 里有 51 个 token。全部填成品牌色会怎样？

想象一下：正文文字变品牌色、页面背景变品牌色、分隔线变品牌色。你会发现层级关系彻底崩了——标题和正文一样，卡片和背景一样，用户连"哪里可以点"都看不出来。这不是"换肤"了，这是"染色"。

所以 EasyStart 只覆盖"品牌色本来就应当出现"的 7 个：

| token | 作用 |
|---|---|
| `brand` | 填充按钮底、开关选中 |
| `fontEmphasize` | 强调文本 |
| `iconEmphasize` | 强调图标 |
| `backgroundEmphasize` | 强调底 |
| `compEmphasizeSecondary` | 组件强调层（次级） |
| `compEmphasizeTertiary` | 组件强调层（三级） |
| `interactiveSelect` | 选中态 |

判定原则一句话：**承担"可读性基线"的 token（正文、背景、分隔线）一律不碰。** 这条原则比记住 7 个名字更重要——将来系统加了新 token，你按这条原则判断就行。

### 5.4 浅色：品牌色 + 两档白混

浅色模式的取值是这么算的：

```
brand / fontEmphasize / iconEmphasize / backgroundEmphasize = hex
compEmphasizeSecondary = mix(hex, '#FFFFFF', 0.82)
compEmphasizeTertiary  = mix(hex, '#FFFFFF', 0.90)
interactiveSelect      = 同 tertiary
```

前四个直接用品牌色；后三个是"品牌色往白里混"，混 82% 和 90%。

`mix()` 的实现很朴素：两个 hex 拆成 RGB 三个数，按比例加权后四舍五入，再拼回 `#RRGGBB`。以青碧 `#12A594` 混 82% 白为例，结果是接近白的一点点青——这正是"强调层"该有的样子：它要让人看出"这是主题色的浅版本"，但不能抢主色的戏。

这十几行代码是整个方案的关键：**它让"主题包只声明一个色"这件事成立**。否则每套主题都要手写 7 个 token，5 套就是 35 个值，还得保证彼此协调。

### 5.5 深色：先提亮，再往黑混

深色模式要分两步，顺序不能反：

```
lifted = mix(hex, '#FFFFFF', 0.28)          // 暗底上原色会发闷，先抬亮一档
soft   = mix(lifted, '#000000', 0.72)
soft2  = mix(lifted, '#000000', 0.82)
```

**第一步提亮**，理由和 `qj_brand` 在暗色下用 `#317AF7` 是同一个：品牌蓝 `#0A59F7` 铺在深色背景上会显得又暗又闷，抬亮 28% 才有精神。

**第二步往黑混**，这一步方向最容易搞错。深色界面里，"柔和层"应当**向背景靠拢**，而背景是暗的，所以往黑混。如果照抄浅色的逻辑（往白混），深色下所有 chip 都会发光——亮底配亮界面，看起来像贴纸。

一句话记住：**浅色往白混，深色先提亮再往黑混。** 方向反了，问题不会报错，只会"看起来怪"。

### 5.6 三个工程细节

**第一，归一化 + 拒绝非法值。** `normalize()` 接受 `#RRGGBB`，也接受 9 位 `#AARRGGBB`（它会把 alpha 去掉，取后 6 位）；非法输入返回空串，`applyPreset` 记一条 warn 后直接跳过。为什么不"尽力而为"？因为把一个非法值塞给系统组件，得到的是不可预测的渲染结果，比不生效更糟。宁可保持现状。

**第二，重复调用短路。** 静态字段 `applied` 记着上次生效的值，值没变就直接返回 `true`。这省掉了"打开外观页又点了一次同一个主题包"的无效全局重算——那是一次遍历 51 个 token 的活，没必要做两遍。

**第三，失败不阻塞启动。** 整段包在 `try/catch` 里，失败只记 warn 并返回 `false`。这条纪律很重要：L4 是兜底层，它失败的时候 L1 和 L3 还在工作，界面照样能用。**绝不该因为主题设置失败而白屏。**

顺便说清返回值的语义：`applyPreset` 返回的是"L4 是否成功"。返回 `false` 不代表什么都没做——L3 已经设好了。所以调用方**不该**根据这个返回值回滚什么。

### 5.7 它盖不住什么

L4 不是万能的，有三条边界：

| 边界 | 表现 | 去哪看 |
|---|---|---|
| 显式 set 过的属性不被覆盖 | 你写了 `.backgroundColor(...)`，主题改不动它 | 第二节的 A/B/C 分级 |
| **HDS 私有 token 不吃这套** | `HdsListItemCard` 底色 / 分割线 / chevron 不变 | 第八节坑 7 |
| **V1 卡片框架不参与** | ArkTS 卡片保持令牌色 | 第八节坑 6 |

第一条其实是好事：显式 > 默认，这符合直觉。麻烦的是第二条——HDS 组件看起来像"系统组件"，但它读自己的 token 表，`ThemeControl` 对它无效。这个反直觉的事实，是第八节那个坑的全部由来。

### 常见错误自查

- [ ] 我拿自绘按钮的变化当证据，宣称"L4 生效了"。
- [ ] 我把 51 个 token 全填成品牌色，然后疑惑为什么界面看不清了。
- [ ] 我在深色模式下照抄了浅色的"往白混"，chip 全在发光。
- [ ] 我的 `applyPreset` 没有 `try/catch`，主题失败直接把启动带崩。
- [ ] 我在 `applyPreset` 返回 `false` 时回滚了 L3 的设置。

### 本节小结

L4 只负责"你没写过颜色的地方"，它的正确姿势是少覆盖、给两套色、失败不阻塞；而它的边界（HDS、V1 卡片）恰恰是后面两个坑的源头。

**动手练习**：在任意页面临时放一个不设颜色的原生 `Toggle()`，切主题看它的选中轨道。然后注释掉 `AppThemeController.applyPreset` 的调用，再看一次——轨道变回系统蓝，这就是 L4 存在的证据。

## 六、编排与冷启动：谁在什么时候把四层铺上去

### 6.1 位置被依赖关系锁死了

四层都能各自工作了，接下来的问题是：**谁按什么顺序把它们铺上去？**

这个类不能随便放。先看两条硬约束：

```
VitalUI   不能依赖 Platform（原语库要零 @kit）
AppCommon 不能依赖 VitalUI（手表要能用）
```

而"铺层"这件事需要**同时**操作 L3（`UiThemeManager`，在 VitalUI）和 L4（`AppThemeController`，在 Platform）。VitalUI 碰不到 Platform，AppCommon 碰不到 VitalUI——两边都做不了这件事。

只有 `commons/AppComponent` 同时依赖这两者，所以 `commons/AppComponent/src/main/ets/theme/AppThemeApplier.ets` 是唯一合法的位置。这不是"选了个好地方"，而是被依赖图逼出来的唯一解。

好处也很明显：四个端（手机/2in1/TV/手表）的入口 Ability 都只调一个方法，顺序只写一遍。

### 6.2 `apply()` 的四步顺序

```
theme.setPresetId(presetId);                // 空串 → 默认包
theme.setAccentColor(accentHex);            // 空串 → 清除覆盖
AppThemeApplier.currentAccent = theme.effectiveAccent();   // 静态中转（第三节）
AppThemeController.applyPreset(theme.presetId, theme.accentColor);  // L4
```

四行，每一步都不能挪位置：

- **第 1、2 行**先把状态写进单例。之所以先写，是因为第 3 行要读它——顺序反了，写进静态中转的是**上一次**的值，表现就是"第一次切对了，第二次慢一拍"。
- **第 3 行**给 L2 的 modifier 族备好最新的颜色。这一行和 L3 是同一帧完成的，所以自绘组件和 modifier 读到的是同一个值。
- **第 4 行**才去设置系统组件默认色。L3 在前、L4 在后，是为了让自绘组件在同一帧就能取到新色；L4 慢一点没影响，因为它是兜底层。

还有一条纪律要一起守住：**两者互不依赖**。L4 失败不影响 L3——这一点在 5.6 已经说了，但值得再强调一次，因为它是"主题失败不白屏"的根据。

### 6.3 三个入口方法怎么分工

| 方法 | 何时用 | 行为 |
|---|---|---|
| `apply(presetId, accentHex)` | 冷启动恢复、外观页幂等再落地 | L3 + L4 + 静态中转 |
| `applyAccent(accentHex)` | 取色器确认 | 保留当前 `presetId`，只换强调色 |
| `applyPreset(presetId)` | 切换主题包 | 保留当前 `accentColor`，只换主题包 |

看起来 `applyPreset` 应该顺手帮你把强调色清掉？它不。**它只做"按给定参数铺层"这件事，不猜用户意图。**

清不清强调色，是页面的职责（7.2 会讲）。这个分工看起来啰嗦，但它避免了一类经典事故：某个调用点只想换主题包、却意外清掉了用户精心调的强调色。

### 6.4 `restoreTheme()`：只读，不注入

冷启动恢复的入口在 `hm_easystart/commons/AppCommon/src/main/ets/bootstrap/AppBootstrap.ets`：

```
static async restoreTheme(): Promise<AppThemeState> { /* 读偏好 → 返回纯数据 */ }
```

它返回一个纯数据对象 `AppThemeState { presetId, accentHex }`，**不碰任何表现层 API**。这是 AppCommon"不依赖 VitalUI"那条纪律的直接体现：AppCommon 只负责"读出来"，注入由入口 Ability 做。

读取顺序是三段：

| 键 | 说明 |
|---|---|
| `accent_color` | 现行的强调色键 |
| `accent_preset` | 历史枚举键，只在现行键为空时回退；它的值本身就是 hex 直通，`'default'` 这类非 hex 视为无记录 |
| `theme_preset` | 主题包 id（空串 = 默认品牌蓝） |

强调色要过一道校验：`ACCENT_HEX_PATTERN`（`/^#[0-9a-f]{6}$/`）。合法才返回小写 `'#rrggbb'`，否则返回空串。

为什么要校验？因为这两个键是**持久化的用户数据**，可能来自旧版本、可能被写坏、也可能被手动改过。在校验处拦掉，日志里还能留一条明确的 warn；不拦，就是一个非法色悄悄流进渲染链路。

### 6.5 冷启动时序：为什么要接受「异步恢复」

这是本教程里唯一一个"设计上就该有点不完美"的地方，值得讲透。

冷启动的时序大致是这样：

```
onCreate
 ├─ AppBootstrap.prepare(this.context)
 ├─ AppBootstrap.restoreTheme().then(state => AppThemeApplier.apply(...))   // 异步
 └─ captureCardTarget(want)
onWindowStageCreate
 └─ windowStage.loadContent('pages/Index', cb)                              // 首帧渲染
```

`restoreTheme()` 内部要 `await` 持久化读取，而 `loadContent` 在 `onWindowStageCreate` 里调用。**两者的先后取决于读取什么时候完成，代码不保证 `apply()` 一定早于首帧。**

如果 `apply()` 落在首帧之后会怎样？第一帧渲染用的是默认包（`presetId` 的初值 `brand`）的颜色，随后再重渲染成上次的颜色。用户看到的是"闪一下蓝，然后变青"。

要不要修？先把事实确认下来：

1. 用 `hilog` 对比两条日志的时间戳——`theme restored: preset=…` 和首帧渲染日志，先确认你的设备上是否真的发生了；
2. 如果确实有先后问题，最省事的做法是在 `loadContent` 的回调里再调一次 `AppThemeApplier.apply(...)`。它是幂等的，而且几乎零成本（`AppThemeController` 的 `applied` 短路会挡掉重复设置）；
3. 更彻底的做法是把主题值在 `prepare()` 阶段同步读进内存，代价是持久化层要改造。EasyStart 没走这条路。

这里的态度值得学：**先取证再决定要不要修。** "理论上可能闪一下"和"我的设备上确实闪了一下"是两件事，前者不值得为它改架构。

### 6.6 各端接入

每个入口 Ability 自己写这一句，`AppCommon` 保持对 VitalUI 零依赖：

```
AppBootstrap.restoreTheme().then((state: AppThemeState): void => {
  AppThemeApplier.apply(state.presetId, state.accentHex);
});
```

四个端的情况：

| 入口 | 是否恢复主题 |
|---|---|
| `entry`（手机/平板/折叠） | 是，`EntryAbility.onCreate` |
| `entry_pc`（2in1） | 是，`PcAbility` |
| `entry_tv` | 是，`EntryTvAbility` |
| `entry_wearable`（手表） | 否，保持默认主题（源码注释即此决策） |

手表不恢复是刻意的：手表端的界面元素少、强调色在圆表盘上收益有限，而多一条持久化读取链路就多一份启动开销。

2in1 宽屏下同一套编排同样生效，左边设置列表、右边外观页分栏：

![2in1 宽屏下的外观页：左侧设置列表与右侧主题面板分栏](图片/D3-2in1-appearance.png)

切到青碧后，同一台 2in1 上的分栏仍在，两边都跟着变色：

![同一 2in1 窗口切到青碧：#0A59F7 变为 #12A594，整窗协调](图片/D5-2in1-teal2.png)

对比这两张图能看出一个细节：切换的是主题，**布局一点没动**。这正是 1.4 说的"换肤与其它维度正交"的实证。

### 6.7 进外观页，再幂等地落地一次

`AccentColorSetting.aboutToAppear()` 的顺序是：读强调色（含历史键回退）→ 读主题包 → `setAccentColor` / `setPresetId` → **再调一次 `AppThemeApplier.apply()`**。

最后那一句是防御式的：万一某个入口漏调了，用户进一次外观页，四层就被补齐了。

这背后是一种工程态度：**把"关键状态落地"做成幂等 + 多触发点，比追求"只在启动时调一次"更抗遗漏。** 因为"只在某处调一次"的方案，一旦那一处漏了，你得到的 bug 是"某些设备上主题不恢复"，而复现条件取决于用户走哪条路径——这类 bug 最难查。

### 常见错误自查

- [ ] 我把 `AppThemeApplier` 放进了 VitalUI 或 AppCommon，然后为了 import 到处破纪律。
- [ ] 我在 `apply()` 里先算 `effectiveAccent()`、后写 `setAccentColor`。
- [ ] 我让 `restoreTheme()` 直接去调 `UiThemeManager`，理由是"少一层调用"。
- [ ] 我一发现"理论上首帧可能闪一下"就去改造持久化层。
- [ ] 我假设四个端都会恢复主题（手表不会，且是刻意的）。

### 本节小结

编排类的唯一合法位置是由依赖图决定的；`apply()` 的四步顺序里，前两步是"先写后读"的因果，后两步是"L3 先、L4 后"的因果；冷启动接受异步恢复，但要用日志确认它到底有没有影响你。

**动手练习**：设成青碧 → 杀掉进程 → 冷启动，用 `hilog` 抓 `theme restored: preset=teal` 和首帧日志的先后。然后手机、2in1 各走一遍；如果你有手表端，确认它启动后是默认品牌蓝。

## 七、外观页：主题包 chips + 取色器

### 7.1 页面要回答两个不同的问题

用户打开外观页，其实想解决两件事：

- **"我想要一整套风格。"** 一键换掉全部品牌色，别让我一个个调。
- **"我只要那个绿色，但别的都别动。"** 单点微调。

这两件事对应两个不同的控件：**主题包 chips** 和 **取色器**。EasyStart 把它们放在同一张卡片里，顺序是：说明文案 → 主题包 → 取色器 → 恢复默认 → 效果预览。

代码在 `hm_easystart/commons/AppSettings/src/main/ets/component/AccentColorSetting.ets`，四块按顺序落：

1. **说明文案**：一行 `settings_accent_desc`，告诉用户"点按色块唤起取色面板"；
2. **主题包 chips**：`Flex({ wrap: FlexWrap.Wrap })` + `ForEach(appThemePresets())`，每颗 chip = 一个 16vp 的圆点 + 名称；
3. **取色器**：`CommonColorPickerSheet({ color: this.theme.effectiveAccent(), ... })`；
4. **恢复默认 + 预览区**：一行 `CommonButton(TEXT)`，下面是 `PRIMARY` / `SECONDARY` / `BRAND` 三个预览，都显式传 `accentColor: this.theme.effectiveAccent()`。

第 2 块里有个细节值得单独说：圆点的底色直接用了 `preset.baseHex`。

```
Column()
  .width(16).height(16).borderRadius(8)
  .backgroundColor(preset.baseHex)     // 这里就是要显示色卡本身
```

这是全仓**唯一允许把 `baseHex` 直接当背景色**的地方——因为它画的就是"这张色卡长什么样"，它不该跟着当前主题变。这跟第二节的 B 类（演示/对照保留原值）是同一个道理。

选中态的处理是：`border` 宽度 `1.5` + 颜色用 `preset.baseHex`；未选中是 `1` + `app_divider`。用"边框变粗变彩"而不是"填充变彩"，是为了让 chip 在深浅色下都保持同样的可读性——如果选中态改成填充，深色下品牌蓝底 + 白字的对比度就需要额外计算了。

五套主题包齐备、选中青碧时的样子：

![五套主题包 chips + 取色块 #12A594：选中态用 1.5vp 主题色描边](图片/B1-presets-5.png)

**预期看到什么**：chip 行自动换行（`FlexWrap.Wrap`），青碧那颗有主题色描边；下面的取色块显示 `#12A594`；预览区三个控件全是青碧。

### 7.2 切包：清强调色 + 落库也清

这是本节最容易漏的一步。`applyPreset(presetId)` 一共四步：

```
this.theme.setAccentColor('');                                   // 1 清内存覆盖
this.theme.setPresetId(presetId);                                // 2 换主题包
AppThemeApplier.applyPreset(presetId);                           // 3 落地
PreferencesStore.put(PreferenceKeys.THEME_PRESET, presetId);     // 4 落库
PreferencesStore.put(PreferenceKeys.ACCENT_COLOR, '');           // 4' 落库也清
```

前两步是内存，第三步是铺层，第四步是持久化。**第 4' 步最容易漏**，而漏了它的后果非常典型：当前会话看起来完全正确（因为内存清了），但杀掉进程重进——`restoreTheme()` 读到旧的强调色，又把新主题包盖住了。

于是你得到一个"只在重启后复现"的 bug：测试时怎么点都对，用户第二天打开发现主题回退了。这类 bug 的排查成本极高，因为你的复现动作和 bug 出现的时机隔了一次进程生命周期。

**记住这条纪律：内存和落库必须同步修改，任何"只改了一个"的地方都会在重启时收账。**

### 7.3 取色器：draft 确认制

`CommonColorPickerSheet`（`quizzyjoy/VitalUI/src/main/ets/component/CommonColorPickerSheet.ets`）的交互契约是"拖动只写内部 `draft`，点确认才回调 `onColorChange`，取消则丢弃"。

为什么这么设计？因为取色是连续的：用户拖动色轮时会经过几百个中间色。如果每经过一个色就落地一次，你会得到几百次全局重算 + 几百次持久化写入，而且用户"随手一拖又拖回来"的操作也会被记录。

调用侧因此只需要做一件事：

```
applyColor(color) →
  setAccentColor(color) → apply(presetId, accentColor) → put(ACCENT_COLOR, color)
```

三步：写内存、铺层、落库。`color` 为空串时走的是"清强调色"分支（4.5 的语义），这条分支同时被"恢复默认"按钮复用。

### 7.4 「恢复默认」是回主题包，不是回默认主题包

这是个语义问题，很容易做错。

`applyColor('')` 走的是"清强调色"，所以界面回到**当前主题包**的基准色。这意味着：如果你当前是青碧 + 一个自定义强调色，点"恢复默认"之后你得到的是**青碧**，不是品牌蓝。

所以按钮文案必须和这个行为一致。写「恢复默认强调色」是对的（清的是覆盖）；写「恢复默认主题」就错了（那会让人以为连主题包一起回 `brand`）。

想真的"全部回默认"，你需要的是 `theme.reset()`（双清），并且要把 `THEME_PRESET` 也写回 `'brand'`。这是两个不同的功能，别合并成一个按钮。

### 7.5 收藏色：单键逗号拼接，读的时候必须逐项校验

取色器里还有一份收藏色列表。存储方式是**单键 + 逗号拼接**（`PreferenceKeys.FAVORITE_COLORS` = `favorite_colors`，上限 `FAVORITE_MAX` = 6）。

为什么不用数组类型？因为 Preferences 的简单键值存储里，字符串是最稳的：没有序列化版本问题，跨版本读写不会因为结构变了而失败。

读的时候要做五件事，一件都不能省：

1. `split(',')` 拆开；
2. 逐项 `trim()` + `toLowerCase()`；
3. 只保留 7 位、`#` 开头的；
4. 去重；
5. 截断到 `FAVORITE_MAX`。

写的时候（`saveFavorites()`）先截断再 `put(...join(','))`，同时回写本地 `@Local favorites`。

**第 3 步不能省**：这个键是"用户可以手动改的文本"。一条脏数据（比如旧版本写进去的 `'default'`）会让取色器渲染出一个非法色块，甚至让整个面板取色失败。校验的成本是几行代码，不校验的成本是一个只在特定用户设备上出现的白块。

### 常见错误自查

- [ ] 我切主题包时只清了内存，忘了清 `ACCENT_COLOR` 的落库值。
- [ ] 我把主题包圆点的底色也改成了 `theme.brandColor()`，结果 chips 全变成同一个颜色。
- [ ] 我让取色器拖动时实时落地，然后困惑为什么卡顿。
- [ ] 我的"恢复默认"按钮实际把主题包也重置了，但文案没写清楚。
- [ ] 我读收藏色时直接 `split(',')` 就用，没有逐项校验。

### 本节小结

外观页是两个问题（整套 / 单点）的组合，所以切包要清强调色、且内存与落库同步；取色器用 draft 确认制，把"连续交互"和"一次提交"分开。

**动手练习**：先设一个自定义强调色，再点另一套主题包，然后杀掉进程重进——确认还是新主题包（这一步验的是 7.2 的第 4' 步）。接着拖动取色器但点取消，确认界面颜色没变（验 draft 语义）。

## 八、七个主题链路的坑

这一节的七个坑，全部来自真机实测。每个坑按四段写：**我怎么发现的 → 根因 → 怎么改（前后对照）→ 怎么避免**。你可以照着复现，也可以只记住最后的纪律。

### 坑 1：切主题包「没反应」，只换了个选中框

**现象。** 外观页点青碧，chip 的选中描边变了、取色块变成 `#12A594`，但预览区、首页、组件页几乎没变。感觉像"只换了个框"。

**根因。** `effectiveAccent()` 的优先级是"强调色 > 主题包"。切包时如果不处理强调色，你改的是优先级更低的那个变量——旧的强调色还在，它永远赢。更糟的是，如果 `setAccentColor` 把空串当非法输入忽略，"清除强调色"这件事在 API 层就根本做不到：页面想清，API 不收。

这条是**语义缺陷伪装成 UI 缺陷**的教科书案例：现象在界面，根因在单例里一个 `if` 分支。

下面这张图是理解该坑的关键。主题包选中「品牌紫」，取色块显示 `#6c4de8`——这正是该主题包的 `baseHex`，也就是**当前生效色**，而不是用户设过的强调色：

![外观页：取色块显示的是当前生效色，不是用户设过的强调色](图片/A1-appearance.png)

看懂这张图，你就明白"切包看起来没反应"只能从优先级和清除逻辑上找原因——因为生效色本身已经跟着主题包变了，说明 L3 是对的，不对的是别的地方还压着旧值。

（这张图是旧版本界面：只有 4 套主题包、紫色包叫「品牌紫」。当前源码是 5 套、叫「靛紫」、id 为 `violet`。）

**改法。** 两件事一起做：把空串定义成第三种语义（4.5），并在页面切包时显式清内存 + 清落库（7.2）。

**怎么避免。** 凡是"一个值有'未设置'状态"的地方，都要在设计 API 时就把这个状态做成一等公民。别等 UI 层来补救——UI 层补不了语义。

### 坑 2：只改单例，VitalUI 原语按钮还是蓝

**现象。** `UiThemeManager` 建好了，`AppComponent` 的控件工厂全都跟着变了，但 `CommonButton` 渲染的「主操作」、`CommonTag` 的「品牌标签」还是默认品牌蓝。

**根因。** 原语如果只读 `$r('app.color.qj_brand')`，它就不认识单例。这时候"跟随主题"只能靠页面传 `@Param accentColor`，而绝大多数页面不会传——于是你看到的是"注入面覆盖了"和"界面显示品牌色"这两件事的差距（4.6 讲过）。

**改法。** 原语自己持有单例，同时保留外部覆盖口子。

```
@Local theme: UiThemeManager = UiThemeManager.getInstance();
@Param accentColor: string = '';
// 取色：this.accentColor.length > 0 ? this.accentColor : this.theme.brandColor()
```

两者都要：只靠 `@Param` 必然大量漏传，只靠单例则失去"某处特调"的能力。而且回退目标必须是 `brandColor()`，不能是 `$r`。

**怎么避免。** 用 3.2 那条判别信号：**"重建页面就对了"= 求值时机问题（坑 3）；"重建也不对"= 根本没连上（本坑）。** 这一条能帮你把两个长得很像的 bug 分开。

### 坑 3：`@Param` 默认值读单例，改色不响应

**现象。** 组件首帧颜色完全正确，之后任何页面改主题都不动它；切走再回来（组件重建）又对了。错误写法只有一行：

```
@Param accentColor: string = UiThemeManager.getInstance().effectiveAccent();
```

**根因。** `@Param` 的默认值是**表达式**，只在创建组件实例时求值一次。值被固化（后续变化不会回写），而且这次读取发生在渲染期之外，依赖没有被记进观察图。所以它既不会更新，也不会重渲染。

**改法。** 用 `@Local` 持有对象本身，把读取放进 `build` 的调用链：

```
@Local theme: UiThemeManager = UiThemeManager.getInstance();
// 取色：this.theme.brandColor()
```

注意 `@Param accentColor: string = ''` 是**安全的**（默认值是常量），只有"默认值里读单例"才是坑。这个区别很容易被误记成"`@Param` 不能用来传主题色"。

**怎么避免。** 一条口诀：**默认值只放常量，动态读取放 `build`。** 任何在装饰器默认值里调用方法、访问单例、算表达式的写法，都要先怀疑一遍。

### 坑 4：顶层 `@Builder` 不能用 `this`，也读不到单例

**现象。** 全局悬浮球（`commons/AppComponent/src/main/ets/feedback/AppOverlay.ets`）上的品牌圆钮，无论怎么换主题，底色恒为默认品牌蓝。

**根因。** 这个 `@Builder` 定义在**文件顶层**，不是某个 `struct` 的成员。它没有 `this`，不属于任何组件的渲染作用域，而且通常还经 `ComponentContent` 从组件外部注入——"在 builder 里读主题色"缺的不是写法，是上下文。

**改法。** 把"读色"搬到有上下文的一侧，用内容对象注入：

```
class AppFloatingBallContent {
  tint: ResourceColor = $r('app.color.qj_brand');
  onTint: ResourceColor = $r('app.color.qj_on_brand');
}
// builder 内只用 content.tint / content.onTint
// show() 侧：content.tint = theme.brandColor(); content.onTint = theme.onBrandColor();
```

这里有个必须知道的预期：`ComponentContent` 构建之后，内容对象字段的后续变化**不会重绘** builder。所以正确预期是"下一次 `show()` 生效"，而不是"改完立刻变"。

顺便给一个反向样本：`product/entry/src/main/ets/pages/Index.ets` 里的 `splitPlaceholderBuilder` 只用 `$r`、不用 `this`——它是主动规避这条约束的写法，所以它也不跟主题（但它本来也不需要）。

**怎么避免。** 见到文件顶层的 `@Builder`，先默认它"读不到任何组件状态"。要给它的东西，一律走参数或内容对象。

### 坑 5：只给 `colors` 不给 `darkColors`，暗色下亮底亮字

**现象。** 浅色一切正常；切到深色后，强调底还是"按浅色逻辑算出来的偏亮值"，压在上面的前景按暗色渲染，对比度直接崩。

**根因。** `darkColors` 不提供时，暗色模式**沿用 `colors` 的值**，不会自动帮你变暗。官方 d.ts 对此有明文：不设 `darkColors` 时颜色值与浅色一致、且不随色彩模式变化，除非该色由 `dark` 目录的资源指定。

而浅色的柔和层是"往白混"（82% / 90% 白），放到深色界面里，等于主动提亮。

**改法。** 两层都要做：内容层在深色下单独算一套（5.5，先提亮再往黑混）；结构层只暴露一个返回完整对象的方法，让"只给一半"在代码上不可能发生：

```
static buildTheme(hex: string): CustomTheme {
  return {
    colors: AppThemeController.lightColors(hex),
    darkColors: AppThemeController.darkColors(hex)
  };
}
```

`lightColors` / `darkColors` 都设成 `private`，外部只能调 `buildTheme`。**用结构固化约束，比在文档里写"请务必成对"有效得多。**

**怎么避免。** 凡是"两个必须成对提供"的 API，都在你自己的封装里合成一个函数。让错误的写法根本写不出来，而不是靠代码评审抓。

### 坑 6：ArkTS 卡片是 V1，接不上 V2 单例

**现象。** 想让桌面卡片的品牌色跟随应用内主题，照 4.1 加一行 `@Local theme = UiThemeManager.getInstance()`，不生效——卡片纹丝不动。

**根因。** 卡片入口是 `@Entry(cardStorage) @Component` + `@LocalStorageProp`，框架当前只支持 V1（`product/entry/src/main/ets/widget/pages/WidgetCard.ets` 的注释写明了这一点）。而 `@ObservedV2` + `@Trace` 只在 `@ComponentV2` 里通过 `@Local` 才能被观测。两条叠加：**这不是配置问题，也不是写法问题，是架构上接不上。**

| 入口 | 状态管理 | 能否接 L3 单例 |
|---|---|---|
| 应用内页面（`@Entry @ComponentV2`） | V2 | 能 |
| 应用内遗留 V1 组件（`@Component`） | V1 | 不能，需先迁 V2 |
| ArkTS 卡片（`@Entry(cardStorage) @Component`） | V1（框架限制） | 不能，不可迁 |

**改法。** 既然接不上单例，就换一条链路：**让颜色跟着数据载荷进来。**

`features/WidgetCommon/src/main/ets/card/WidgetCardBuilder.ets` 在构建卡片数据时读偏好：

- 从 `PreferencesStore` 读 `ACCENT_COLOR`，为空时回退历史键 `ACCENT_COLOR_LEGACY`；
- 用 `ACCENT_HEX_PATTERN` 校验，不合法就落到 `BRAND_FALLBACK_HEX`（`#0a59f7`，与 `qj_brand` 同值）；
- 结果写进载荷字段 `accentText`。

卡片侧则用 `@LocalStorageProp('accentText')` 接住它，画在"强调色圆点"和宽卡片的色块上：

```
@LocalStorageProp('accentText') accentText: string = '#0a59f7';
// 圆点：.backgroundColor(this.accentText)
```

其余颜色继续用 `$r('app.color.*')` 令牌，深浅色仍然正确。

**这条链路的边界要说清楚**：卡片上的强调色只忠实于"强调色"这一个值。切主题包会把 `ACCENT_COLOR` 清空（7.2），于是卡片回退到 `#0a59f7`——也就是显示品牌蓝。这不是 bug，是这套链路的边界：**卡片认"强调色"，不认"主题包"。**

同一个页面还有一条卡片专属的坑，值得一起记住：`@LocalStorageProp` 的值如果经**带值参数的 `@Builder`**（比如 `rowValue(this.themeText)`）转手，会被按值捕获、永不重渲染。源码注释记录了真机现象：标题、时间这些直读字段正常，显示模式、语言、字号恒为默认值。修法是为每个状态行写**无参数**的 `@Builder`、内部直读状态——和坑 3 是同一机制。

**怎么避免。** 见到"框架限定 V1"的入口，别再试图接 V2 的单例，直接走"数据载荷"这条路。同时把"哪些值能拿到、哪些拿不到"写在组件注释里，省得下一个人再试一遍。

### 坑 7：HDS 私有 token 不吃 `ThemeControl`

**现象。** 切到青碧后走查设置页，同一页里自绘元素已经转青碧，但下面这些位置纹丝不动：开关 ON 轨道（系统蓝）、HDS 行卡片底色（中性灰）、行分割线（中性灰）、行尾 chevron（中性灰）。

切青碧后的设置页（深色模式），HDS 行卡片底色与 chevron 仍是中性灰：

![切青碧后的设置页：HDS 行卡片底色、分割线、chevron 仍为中性灰](图片/C2-hds-teal.png)

**根因。** 页面上看到的开关，并不是 EasyStart 自绘的 `SettingsSwitchRow`，而是 HDS 的 `SuffixSwitch`。设置域是 schema 驱动的（`SchemaSettingsSection` 按 `rawfile/settings_schema.json` 渲染），`builtin: 'haptic'` / `'keepScreenOn'` 两行走的是：

```
HdsListItemCard({
  suffixItem: new SuffixSwitch({ isCheck, onChange })   // 没有任何颜色参数
})
```

HDS 组件画在 ArkUI 之上，但读的是**自己的私有 token**——它不在这张 51 项的 `Colors` 表里，所以 `ThemeControl` 对它无效。

这里有条重要的排查纪律：**先确认这个像素是谁画的。** 你以为是 A 组件画的，实际是 B 组件，那你改 A 改到天亮也没用。

**改法。** HDS 只认显式传色，去 d.ts 找口子，而不是猜属性名。本机 SDK 的 `@hms.hds.hdsBaseComponent.d.ets` 里，`CheckOptions.selectColor?: ResourceColor`（`@since 6.0.0(20)`）就是入口。两处实例各补一行：

```
new SuffixSwitch({
  isCheck: this.vm.hapticEnabled,
  selectColor: this.theme.brandColor(),   // 新增
  onChange: (on: boolean): void => { this.vm.toggleHaptic(on); }
})
```

同时要给 `SchemaSettingsSection` 补上观测上下文：

```
@Local theme: UiThemeManager = UiThemeManager.getInstance();
```

**只传 `selectColor` 而不持有 `@Local theme`，首帧是对的，但切主题不重绘**——这正是坑 3 的同一机制，只是换了个位置。

修好之后，「触感反馈」的 ON 轨道是青碧，「屏幕常亮」是 OFF 灰态：

![分栏右栏：触感反馈开关 ON 轨道为青碧，屏幕常亮为 OFF 灰态](图片/G2-toggle-on-teal.png)

HDS 各元素的跟随情况：

| HDS 元素 | 能否跟随 | 路径 |
|---|---|---|
| `SuffixSwitch`（本仓两处） | 能，已跟随 | `CheckOptions.selectColor` |
| `HdsListItemCard` 底色 / 分割线 / chevron | 不能，仍不跟随 | 需 `HdsListItemCardModifier` 或显式 tint（本仓未做） |

**怎么避免。** 把"HDS 跟随"当成**逐组件、逐 token** 的工程：谁提供了 `ResourceColor` 口子就接谁；没口子的，别给它套 `.backgroundColor()`（会被它内部 token 覆盖，白忙一场）。验证一律取像素，而不是"看起来变了"。

### 常见错误自查

- [ ] 我用"重建页面能好"来解释一个"根本没连上"的 bug。
- [ ] 我在 `@Param` 的默认值里调了 `getInstance()`。
- [ ] 我给顶层的 `@Builder` 传了 `this.xxx`，还在等它重绘。
- [ ] 我只设了 `colors`，打算"以后再补 `darkColors`"。
- [ ] 我给 HDS 组件套了 `.backgroundColor()`，并相信它生效了。

### 本节小结

七个坑可以归成三句话：**读不到通知的（L2、`@Param`、顶层 `@Builder`）靠"换求值位置"解决；读不到值的（V1 卡片、HDS）靠"换传递链路"解决；配错方向的（缺 `darkColors`、空串语义）靠"该成对的成对、该是三态的三态"解决。**

## 九、两个布局坑：它们会让主题问题看起来更严重

### 9.1 为什么布局坑要放在主题教程里

因为它们在真机走查里**同时出现**，而且会成倍放大"主题没生效"的错觉。

想象一下：你在阔折叠上展开分栏，发现工具网格的卡片被压得很窄、标题被截成「设…」「图…」「转…」。你会先怀疑什么？大概率是"主题把字变没了"或"这页没适配主题"。你会去查颜色，查很久，然后发现跟颜色毫无关系。

所以这一节的第一条纪律是：**先修布局，再看颜色。** 分栏后文字被截断会被误读成"主题问题"，两者混在一起极难定位。

### 坑 8：列数要按容器宽算，不能按窗口断点算

**现象。** 阔折叠展开、进入分栏后，左栏里「开发工具」网格被压成 4 列：卡片很窄，标题和描述大量截断。

![按窗口断点算 4 列：左栏被挤压，标题截成「设…」「图…」「转…」](图片/E3-pura-tools.png)

注意这张图里还有一个"顺带"的现象：页签跑到了标题下面（坑 9 会讲）。两个坑在同一屏里同时存在，这正是"混在一起极难定位"的典型。

**根因。** 入口页在宽屏下进入 `NavigationMode.Split`，左栏只占窗口宽度的一部分——`Navigation` 默认左栏在 Pura X Max 这类设备上只有约 320vp（`Index.ets` 注释记录的实测值）。

于是出现了一个矛盾：**断点仍然是 `lg`**（窗口确实足够宽），但页面实际容器只有 320–420vp。列数是按"大屏"给的，容器是按"小屏"算的，每列自然被压扁。

**改法。** 三步一起做，缺一步都不完整。

**第一步，把左栏宽度显式定下来。** `Index.ets` 里的 `navBarWidthValue()` / `navPaneWidthVp()`：

```
lg/xl → clamp(窗口宽 × 0.32, 340, 420)
md    → 44%
sm    → 100%（不分栏）
```

比例保证随窗口缩放，clamp 保证两端不发散（窗口再宽也不会超过 420vp）。另外用 `navBarWidthRange({ minWidth: 300, maxWidth: 440 })` 兜住边界，防止用户拖动分隔条时把左栏拖到不可用。

**第二步，把数值容器宽下传。** 未分栏时 `navPaneWidthVp()` 返回 0，分栏时返回同一套算式的结果，作为 `@Param paneWidthVp` 传给子视图：

```
ToolsView({ paneWidthVp: this.navPaneWidthVp(), /* ... */ })
```

**第三步，子视图按容器宽分档。** `features/DemoFeature/src/main/ets/view/ToolsView.ets` 的 `columns()`：

```
const w: number = this.paneWidthVp > 0 ? this.paneWidthVp : this.breakpoint.windowWidthVp;
if (w > 0) {
  if (w < 480) { return 2; }
  if (w < 760) { return 3; }
  return 4;
}
// 宽度未知时退回断点判定：sm → 2、md → 3、其它 → 4
```

`w` 的取法就是这条坑的核心：**优先用容器宽，容器宽拿不到才退回窗口宽**。420vp 的容器落在 `< 480` 这一档，于是得到 2 列：

![改按容器宽分档后的 2 列：标题与描述完整显示](图片/E4-pura-tools-fixed.png)

两次的窗口断点完全相同，变的只是"按什么宽度算列数"。

还有一条配套的坑中坑：`Grid` 放进 `Scroll` 里**不会自动撑高**，会塌成 0。所以高度必须显式算，而高度计算依赖列数：

```
rows = ceil(条目数 / columns());
height = rows * CARD_HEIGHT + (rows - 1) * CARD_GAP;
```

这两行和 `columns()` 是同一个决策的两个输出，必须写在同一个视图里。如果把它们拆到两个文件，你迟早会改了一个忘了另一个。

**怎么避免。** 记住一条分工：**断点回答"设备是什么形态、要不要分栏"，容器宽回答"我这一块有多少地方画、能放几列"。** 涉及"排几个"的时候，永远用容器宽。

### 坑 9：`HdsTabs.barPosition` 必须恒定，不能按断点切

**现象。** 宽屏分栏下，底部页签"跑了"——`示例 / 学习 / 开发工具` 出现在左栏**顶部**，横在页面标题和内容卡片之间，看起来像一组次级导航。

![宽屏分栏下页签被挤到左栏顶部，夹在标题与列表之间](图片/E2-pura-navwide.png)

**根因。** 原来的写法是：

```
.barPosition(this.breakpoint.isWide() ? BarPosition.Start : BarPosition.End)
```

意图很合理："宽屏时页签放到上面，更符合平板习惯。"但分栏语境下，`HdsTabs` 的容器已经不是整屏而是左栏，`Start` 于是把页签放到**左栏顶部**——正好插在标题与列表之间。它既不像顶部导航（因为没有占满整宽），也不再是底部页签（因为不在底部）。

这个坑的教训不在于"参数写错了"，而在于**一个布局决策在换了容器之后，语义完全变了**。

**改法。** 恒为底部，与 2in1 端保持一致：

```
.barPosition(BarPosition.End)   // 恒定，不随断点变化
```

![页签回到左栏底部（浮动胶囊）](图片/G0-pura-tabbar-bottom.png)

**预期看到什么**：页签变成左栏底部的一颗浮动胶囊，图标 + 文字，选中项高亮；滚动到列表末尾，最后一行完整可见。

顺带说清两件容易被误判的事：

- **想做 rail 导航，改一个 `barPosition` 得不到。** rail 是另一套设计：图标 + 文字要重排、宽度要预算、选中指示器方向要改、内容区要让位。这是一个组件级的活，不是一个枚举值的活。
- **页签压在列表上不是 bug。** 这里用了 `barOverlap(true)` + `barFloatingStyle`，是沉浸式的既有设计。前提是列表底部留了 padding——这也是为什么"滚动到末尾最后一行完整可见"要作为验收项。

2in1 端页签天生在底部、分栏是常态，可以当对照组看：

![2in1 宽屏：开发工具网格 3 项在 4 列布局中占前三列](图片/D1-2in1-tools.png)

### 9.2 取证纪律：两组截图不能混用

这一节有两组容易混淆的截图，必须分开引用：

- `E3` / `E4` 这一组，修的是**网格列数**。看这两张图你会发现，**页签还在顶部**——因为拍这两张的时候，坑 9 还没修。
- `G0` / `G2` 这一组，才是**页签位置修复后**的状态。

如果把 `E4`（列数已修、页签未修）和 `G0`（页签已修）当成同一次修复的证据，你会得出一个错误结论："改了列数，页签也顺带修好了。"这不成立，页签是另一处独立改动。

走查本身也要按形态分组：**手机竖屏 / 阔折叠展开（分栏）/ 2in1 宽屏**。这三组的容器宽差得很大，同一套断点逻辑在其中几组上必然出错。分组走查，才能让"哪一组出错"变成有效信息。

最后看一眼青碧主题在阔折叠分栏下的整体效果：

![阔折叠分栏：青碧主题整体效果，页签在左栏底部](图片/E7-pura-teal.png)

**预期看到什么**：左栏首页与右栏外观页都是青碧，页签在左栏底部；HDS 灰色行卡片（如设置页）仍然不跟主题——这是坑 7 的既定边界，不是这一节没修好。

### 常见错误自查

- [ ] 我用窗口断点算列数，因为"断点不就是用来做适配的吗"。
- [ ] 我改了 `columns()`，但没同步 `gridHeight()`。
- [ ] 我在宽屏下把 `barPosition` 切成了 `Start`，期待它变成顶部导航。
- [ ] 我拿 `E4` 当"页签也修好了"的证据。
- [ ] 我把手机、折叠、2in1 混在一起走查，得到一组无法定位的结论。

### 本节小结

断点管形态、容器宽管排版，两者不能互换；`barPosition` 这类"位置决策"在容器变化后语义会变，只能恒定；取证要按设备形态分组，并且分清哪张截图属于哪一次修复。

**动手练习**：在手机竖屏、阔折叠展开、2in1 三个形态下各截一次工具页，量一下左栏实际宽度，验证它是否落在 340–420vp 之间；然后把窗口从窄拖到宽，观察列数是在哪个宽度跳变的。

到这里，四层模型的每一层你都亲手碰过了：L1 决定哪些颜色"就该是固定的"，L2 用静态中转绕开无状态样式的限制，L3 用 `@ObservedV2` + `@Trace` 换来当帧响应，L4 用 7 个 token 接住系统组件的默认色。九个案子里最有价值的其实不是改法，而是那三句判别：**重建才好 = 时机问题；重建也不好 = 没连上；先看布局，再看颜色。**

回到开头那个场景：你切到青碧，八种结果各归其位。这时候你不再需要背 API——你只需要问一句"这块像素是谁画的"。
